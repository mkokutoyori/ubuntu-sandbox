# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A browser-based network simulator (Ubuntu Sandbox) built with React + TypeScript. Users drag-and-drop network devices (routers, switches, PCs, servers) onto a canvas, cable them together, and interact via in-browser terminal emulators that simulate Cisco IOS, Huawei VRP, Linux bash, Windows cmd/PowerShell, and Oracle SQL*Plus. The simulation runs entirely client-side — protocols (OSPF, BGP, EIGRP, STP, DHCP, IPSec, etc.), shells, and the Oracle database engine are all reimplemented from scratch in TypeScript.


**`tsc --noEmit -p tsconfig.json` checks NOTHING.** The root `tsconfig.json`
is a solution-style file (`"files": []` plus `references`), so pointing
`tsc` at it succeeds instantly having compiled zero files — a green
typecheck that means nothing. Use `npm run typecheck`
(`tsc --noEmit -p tsconfig.app.json`). The repo carries a standing backlog
of type errors, almost all in tests; the rule is not "zero errors" but
**no more than before your change** — count with
`npm run typecheck 2>&1 | grep -c "error TS"` on your branch and on its
base.

## Architecture

**Path alias:** `@/` maps to `src/`.

### Network simulation layer (`src/network/`)

Equipment-driven architecture — no central simulator mediator. Devices process and forward frames themselves, peer-to-peer over cabled ports.

- `equipment/Equipment.ts` — abstract base class for all devices; maintains a static `EquipmentRegistry` for topology traversal. Subclasses implement `handleFrame()`.
- `equipment/HostCapabilities.ts` / `equipment/RouterServiceCapabilities.ts` — segregated optional-capability interfaces + accessor functions (`isCredentialAuthenticator(dev)`, `getManagementService(dev)`, `getHsrpAgent(dev)`, …) for reaching a concrete device's methods from code typed against a narrower shared interface (`CiscoDevice`, `ICLIDevice`, raw `Equipment`). Prefer extending these over a fresh inline `dev as unknown as { getXxx?: () => Yyy }` at the call site (rapport 08 audit: reduce unencapsulated casts).
- `hardware/Port.ts`, `hardware/Cable.ts`, `hardware/PortSecurity.ts` — physical layer; Cables connect Ports for direct device-to-device frame delivery.
  - **Une interface de bouclage est un vrai port** (`docs/PRD-Loopback.md`), sur les quatre plateformes. Ce que la mesure a trouvé, en rejouant le tutoriel loopback comme laboratoire : sous Linux, `lo` était une FICTION DE RENDU — `getInterfaceInfo('lo')` fabriquait un objet à la demande sans qu'aucun port n'existe derrière, si bien que `ip link show lo` décrivait la boucle pendant que `ip addr add 10.0.0.1/32 dev lo` répondait `Cannot find device "lo"` sur la même machine au même instant. `LinuxMachine.createLoopbackPort()` la crée au démarrage comme le noyau le fait (MTU 65536, MAC nulle, 127.0.0.1/8 + ::1/128, indestructible). `Port` a dû nommer deux notions distinctes, chacune pour ce qu'elle décide : **`loopback`** fixe le plafond de MTU (9216 est la taille d'une trame Ethernet jumbo — sans objet pour une interface qui n'émet pas de trame, et poser 65536 échouait sur un plafond emprunté à un autre médium), **`carrierless`** fixe l'état rapporté (`UNKNOWN`, jamais `UP`/`DOWN`, et `NOARP` au lieu de `MULTICAST` — vrai de `lo` comme d'une interface `dummy`, qui sortait `<NO-CARRIER…> state DOWN`). **`lo` est créée APRÈS les ports physiques**, mesuré et non supposé : la créer en premier faisait câbler `lo` au commutateur dans les laboratoires qui désignent « la première carte » par `getPorts()[0]` et faisait tomber 170 cas ; l'affichage la place en tête explicitement, comme le vrai, et son index reste 1 sans occuper un rang dans la numérotation des autres. Deux défauts GÉNÉRAUX (non propres à la boucle) trouvés en chemin : `buildFullRoutingTable` ne posait de route que pour l'adresse PRIMAIRE d'un port, et `getPortOwningIP` ne consultait que la primaire — donc toute adresse ajoutée par `ip addr add`, sur n'importe quelle interface, existait sans être joignable, y compris par la machine qui la portait (`Port.ownsIPv4` portait déjà le prédicat exact) ; et `valid_lft` manquait sur TOUTES les adresses IPv4, ce que seule la comparaison avec un `eth0` réel a révélé. Le `scope` vient de l'ADRESSE et non de l'interface (127.0.0.0/8 → `host`, le reste `global`) : le déduire de l'interface annonçait `scope host` pour une adresse posée sur `lo`, donc la décrivait comme injoignable alors qu'elle est là pour être annoncée. `formeLien()` est la règle unique d'état/file/longueur de file, lue par `ip addr`, `ip link` et `ip -br`, qui la calculaient chacun de leur côté et se contredisaient. `modprobe` n'existait pas sur une machine où `ip link add … type dummy` fonctionne : `KernelModuleTable.load()` et son catalogue `CHARGEABLES` décrivent ce que l'image porte VRAIMENT (`dummy` seul, parce qu'un vrai comportement existe derrière), un `modprobe` d'autre chose échoue en nommant le répertoire, et `ip link add … type dummy` charge le module tout seul par la même table. Références mesurées contre `iproute2` installé, pas de mémoire.
  - **Côté Cisco et Huawei** (même PRD) : le type de réseau OSPF `loopback` n'existait pas, donc une loopback était `broadcast`, passait par l'élection et se déclarait DR d'elle-même. La conséquence n'est pas cosmétique — RFC 2328 §12.4.1.1 fait annoncer une loopback en HÔTE ISOLÉ /32 quel que soit son masque, et `ip ospf network point-to-point` fait annoncer le préfixe configuré ; les deux moitiés sont vérifiées sur la table du VOISIN. `setInterfaceNetworkType` relance la machine à états (l'écriture directe laissait l'état et les minuteurs d'avant). MTU 1514 / BW 8000000 / DLY 5000 sont posés sur le PORT à sa création, donc `bandwidth`/`delay`/`mtu` les surchargent par la voie normale et EIGRP lit la même valeur que la vue affiche. `show ip interface <nom>` rendait le texte de `show interfaces` — l'AUTRE commande — et écrivait `MTU is 1500`/`Proxy ARP is enabled` en dur, contredisant la configuration de la même machine. `passive-interface` était accepté, honoré, et rendu NULLE PART (EIGRP et RIP le rendent tous deux dans le même sérialiseur), donc perdu à la relecture d'une topologie. Sur VRP, `protocoleSpoofe` est la règle unique derrière `up(s)` et `UP (spoofing)` — la façon dont VRP dit que l'état est DÉCRÉTÉ, donc la propriété qui rend une loopback utilisable comme Router ID — étendue aux vues de détail qui répondaient `UP` sec ; portée à `LoopBack` et `NULL`, `Tunnel` restant dehors faute de référence. `source LoopBack 0` ne gardait que le premier mot (configuration rendue : `source LoopBack`, une interface inexistante) et `undo interface LoopBack 0` était accepté sans rien supprimer — il supprime, refuse un port physique, et prévient avant par le mécanisme de plans qui portait déjà `save`/`reboot`. **Côté Windows**, `route print` sortait une table `Active Routes:` VIDE pendant que `Get-NetRoute` déclarait une route en dur et que le fournisseur PowerShell en déclarait une troisième avec une autre métrique : `WindowsLoopbackRoutes.ts` les déclare une fois, les trois vues les lisent. Limite assumée et écrite dans le PRD : `netsh`/`New-NetIPAddress` sur `Loopback Pseudo-Interface 1` et `Get-NetAdapter -IncludeHidden` restent hors de portée tant que cette pseudo-interface n'est pas un vrai port de `WindowsPC` — une quatrième copie écrite en dur serait exactement le défaut qu'on vient de refermer.
  - No FCS field exists on `EthernetFrame` (rapport 04, item #45), and adding a bare one would be decorative — there's no byte-level frame encoding to corrupt against. Instead, `Cable` now has a `corruptionRate` knob mirroring the pre-existing `packetLossRate` one (`setCorruptionRate`/`getCorruptionRate`, `CableStats.framesCorrupted`): a "corrupted" frame never reaches the receiver's `handleFrame()` (same observable effect as a real NIC silently discarding a bad-FCS frame) and increments the previously-dead `Port.errorsIn` counter, distinct from generic simulated loss. Also fixed: `Cable.transmit`/`Port.sendFrame`/`receiveFrame` intentionally deliver the *same* frame object end to end (asserted by identity in `hardware.test.ts`, kept that way — cloning every frame would be the hottest path in the simulator for no observed bug), but several **fan-out** call sites were handing that same object to *multiple* destinations instead of a fresh one per destination: `Hub.handleFrame`, `Switch.floodFrame`'s `stripTag`/`stripOuterTag` (returned the input frame unchanged for the common untagged case), `Switch.emitMirror` (SPAN destination shared the real egress frame), and `Router.forwardMulticast` (one `IPv4Packet` object reused as the `payload` of every OIF's frame). Nothing currently mutates a frame/packet in place post-handoff, so this was latent rather than an active bug — but a landmine for the next feature that does. Fixed by giving each fan-out destination its own shallow copy; BGP/IS-IS-style deep immutability (`Object.freeze`, already used elsewhere for config objects) was not applied to the hot data-plane path.
- **Une sous-interface VLAN emet par sa PROPRE prise de capture.**
  `LinuxMachine.sendFrame` etiquette la trame, l'emet par le port PARENT
  — ce qui est juste, la sous-interface n'a pas de cable — puis publiait
  a la main un `port.frame.tx-requested` « de capture » sur le bus. Ce
  signal etait un DOUBLON synthetique de ce que `Port.sendFrame` publie
  pour un vrai port, et surtout il n'atteignait pas la prise de capture :
  `tcpdump -i eth0.10 tcp` capturait ZERO alors que `tcpdump -i eth0.10`
  sans filtre voyait passer l'ARP entrant (la reception, elle, passe bien
  par le port de la sous-interface). La moitie observabilite de
  `Port.sendFrame` est extraite en `recordOutboundFrame` — compteurs,
  journal, evenement, prise — et la sous-interface l'appelle sur son
  propre port : une seule ecriture, deux appelants, et la capture voit
  desormais la trame non etiquetee comme le fait un vrai `eth0.10`.

- `core/types.ts` — frame/packet structures (`EthernetFrame`, `IPv4Packet`, `ARPPacket`, `ICMPPacket`, `UDPPacket`, `RIPPacket`), address types (`MACAddress`, `IPAddress`, `SubnetMask`), protocol constants, ID/checksum helpers.
- `core/` also holds shared infra: `Logger.ts` (pub/sub network event log), `RoutingTable.ts`, `PacketQueue.ts`, `SocketTable.ts`, `TcpConnection.ts`, `FilterChain.ts`, `NeighborResolver.ts`, `WellKnownPorts.ts`, `Ipv4Fragmentation.ts` (RFC 791 §3.2 `fragmentIPv4`/`IPv4Reassembler` — used by `Router.forwardPacket` and `EndHost.forwardIPv4` when a datagram crosses onto a smaller-MTU link with DF clear; DF=1 still gets ICMP Fragmentation Needed instead).
- UDP checksum (RFC 768) — `computeUdpChecksum`/`verifyUdpChecksum` live in `tcp/types.ts` (shared L4-checksum module with TCP's `computeTcpChecksum`, despite the filename). `EndHost.sendUdpDatagram` stamps a real checksum; `EndHost.deliverUDP` and `Router`'s self-destined UDP dispatch verify and silently drop a mismatch. Internal protocol agents (RIP, DHCP, IKE, SNMP, …) still build `UDPPacket`s with `checksum: 0` — that's RFC 768's IPv4 "not computed" opt-out and is accepted unconditionally, same as those agents' payloads not being real serialized bytes in the first place.
- `devices/` — concrete device classes (`LinuxPC`, `WindowsPC`, `LinuxServer`, `CiscoRouter`, `HuaweiRouter`, `CiscoSwitch`, `HuaweiSwitch`, `GenericSwitch`, `Hub`, `Router`, `Switch`, `EndHost`). Instantiated via `DeviceFactory.createDevice(type)` (see `core/types.ts` for the `DeviceType` union — note some types like `firewall-*` are currently stubbed as `LinuxPC`).

This is UI-reachable, not dead code (draggable from the palette today), but already honestly disclosed there: `DevicePalette.tsx` renders an amber "Limited simulation" badge via `isFullyImplemented()` for exactly these types. Deliberately not attempted: per the audit's own prioritization (`docs/audit/04-equipements-data-plane.md` §5.7 — this item doesn't even make the audit's own "top 10 recommended actions"), and given each vendor's CLI grammar + security model is genuinely distinct (ASA security-levels/object-NAT, FortiOS VDOMs/`config firewall policy`, PAN-OS zones/rulebase) and comparable in scope to the multi-session Huawei-router-CLI or SSH-unification efforts — not a bounded single-session slice. Le constructeur de `Firewall` posait l'adresse d'usine du profil (`port1` = `192.168.1.99/24` sur un FortiGate 60F) dans cette table SEULE, si bien qu'un pare-feu sorti d'usine repondait `set ip 192.168.1.99 255.255.255.0` a `show system interface port1` pendant que `port1.getIPAddress()` rendait `null` sur la meme machine au meme instant. **La consequence n'etait pas cosmetique, et elle touchait trois choses a la fois** : l'UI construit `NetworkDeviceUI.interfaces` en lisant `port.getIPAddress()` (`networkStore.ts`), donc la liste des interfaces affichait le port sans adresse ; `HostLookup` resout un equipement par IP en parcourant `dev.getPorts()`, donc le pare-feu etait INVISIBLE a toute resolution et `ssh admin@192.168.1.99` repondait `No route to host` — le diagnostic qui envoie verifier un cablage quand la machine est la ; et un vrai appel TCP vers `:22`, `:80` ou `:443` n'aboutissait pas, alors que les ecouteurs etaient bel et bien lies (mesure : `tcp.listeners` = `0.0.0.0:22,23,80,443`).   - `Router.ts`'s RIB (`private routingTable: RouteEntry[]`) has no separate FIB and no next-hop recursion: `lookupRoute()` (the data-plane forwarding seam) reads the very same live array every protocol integration mutates directly, and it's called on *every* forwarding decision, which in turn calls `dynamicRouting.refresh()` — control-plane recomputation triggered by data-plane packet processing, backwards from a real router's independent timer-driven control plane. There's also no recursive next-hop resolution: every route's next-hop must be on a directly-connected subnet, so a classic recursive static route (`ip route <net> <mask> <off-link-ip>`) or loopback-to-loopback iBGP is accepted by the CLI but never actually resolves/forwards. Real ECMP (ties on prefix/AD/metric round-robin across all tied RIB entries — see `lookupRoute`'s `candidates` array and `RouterOSPFIntegration.installRoutes`'s per-nextHop loop over `OSPFRouteEntry.nextHops[]`) was fixed; full RIB/FIB separation and route recursion were not — both are genuine architectural gaps (rapport 02 audit item #40), not bounded fixes.

  - **`archive` writes a real file, and `rate-limit` really polices** (audit 13). `ArchiveService.capture()` was written and called from nowhere, so no revision could exist: `show archive` said "No archives configured" while the same machine's running-config listed the `archive` block with its path, `archive config` did not exist, and `write-memory` — whose meaning IS "archive on every save" — was stored and read by nobody. Before it, the in-memory maps were the sole source of truth and `/etc/passwd` was a rendering of them: `vim /etc/passwd`, `sed -i`, `rm /etc/shadow` or `cp /etc/passwd- /etc/passwd` changed the text and nothing else, so the machine kept behaving as though the edit had never happened — and the next `useradd` silently erased it by re-rendering the whole file from memory. Now `LinuxUserManager` treats the four files as the store and its maps as a cache: `reloadIfChanged()` (called by every read path — `getUser`, `getUserByUid`, `getAllUsers`, `getGroup`, `getGroupByGid`, `getUserGroups`, `checkPassword`) compares the on-disk text against what the manager last wrote or read and re-parses when they differ, so an external edit takes effect on the very next lookup, at the cost of one string compare when nothing changed. `syncToFilesystem()` restamps after writing so the manager never mistakes its own projection for an operator's edit. Four behaviours are deliberate and each is pinned by test: a **duplicated** name resolves to the FIRST line (libc stops at the first match — getting this backwards would let anyone append a line to hijack an existing name); a **malformed** line is skipped without taking the rest of the file down (one typo must not lock everybody out); an account present in `/etc/passwd` with **no `/etc/shadow` line** still exists and simply has no password (that is an inconsistency `pwck` names, not a deleted user); and the **password round-trips** because `passwd` stores the secret as `$6$simulated$<clear>` — a secret that is not in that shape (an opaque hash pasted in from another machine, `*`, `!`) yields no recoverable cleartext, so the account stops authenticating by password, which is the real consequence of hand-editing a hash rather than a parser limitation. Fields no file carries (`lastLoginAt`, the faillock tally, `createdAt`) are carried over from the account of the same name rather than reset, because on a real system they live outside `/etc` too (`/var/log/lastlog`, faillock's tally directory). This is what makes `docs/PRD-Pannes.md` §F7.3/§F7.4 real rather than staged: nothing special-cases "the file is missing" — parsing nothing yields nothing, exactly as NSS does with no source, so `rm /etc/passwd` gives numeric `id`/`ls -l` output and `whoami: cannot find name for user ID 1000`, while `rm /etc/shadow` leaves every identity resolvable and only kills password verification (SSH public-key auth, which never reads shadow, keeps working). Note `nss-systemd(8)`'s synthetic `root`/`nobody` still answer with no `/etc/passwd` at all — that is real behaviour, deliberately preserved, and losing it would be a bug. Two consequences of "the files are the store" that the parser alone does not give you are handled in `LinuxUserManager` itself. **UID/GID allocation scans the live database** rather than a stored cursor: `allocateUid`/`allocateGid` implement shadow-utils' own `find_new_uid()` — highest id already used inside `[MIN, MAX]` plus one, falling back to the lowest free id only once the range is exhausted — so an id an operator added or freed by editing `/etc/passwd` is visible to the very next `useradd`, and the range being full is a real error (`useradd: can't get unique UID …`) instead of an out-of-range id. A forward-only cursor could not see either edit and would eventually hand out an id already in the file; note also that this makes "delete the highest account, then `useradd`" reuse that id (correct, and what real `useradd` does) while a hole in the middle of the range stays unfilled. **`useradd -r` searches the opposite way** — downward from `SYS_UID_MAX`, taking the highest free system id (999, 998, 997…) — because the two ranges are adjacent (…999 | 1000…) and growing them towards each other would have them collide as soon as either filled up; growing them apart preserves the gap, which is why a real Debian box numbers daemons downwards and users upwards. **`/etc/nsswitch.conf` governs this manager too**, not just `getent`: `filesSourceEnabled()` reads the `passwd:`/`group:`/`shadow:`/`gshadow:` lines and a database whose `files` source is switched off reads as empty however intact the file is, so `passwd: systemd` alone makes `id`/`su`/every permission check stop resolving accounts while `/etc/passwd` still lists them — the confusing failure that line exists to cause. `compat` counts as files (the historical spelling), an absent `nsswitch.conf` falls back to glibc's compiled-in default rather than disabling name resolution, and the file's text is part of the reload stamp so editing it takes effect on the next lookup. The chain does not stop at `files` either, and it does not blindly run every source: `walkNssChain()` builds each table by running `nss/chainWalk.ts`'s `startNssWalk()` once per name — the very same walk object `NameServiceSwitch` drives for `getent`/`ping`/the resolver, extracted so the two callers cannot drift (a machine where `getent passwd alice` and `id alice` disagree is worse than one where both are wrong, because nothing in the diagnosis adds up; `nss-chain-is-one-implementation.test.ts` pins both the rule and the agreement). The walk looks each source's outcome up in that source's own action table (`[NOTFOUND=return]`, `[SUCCESS=continue]`, `[UNAVAIL=return]`, `[SUCCESS=merge]`) via `effectiveAction()`, defaults being SUCCESS=return / NOTFOUND=continue / UNAVAIL=continue / TRYAGAIN=continue. **The distinction that actually bites is UNAVAIL vs NOTFOUND**, which is why the chain callback returns `null` rather than an empty map for a source that cannot answer at all: a MISSING `/etc/passwd` makes the files source UNAVAILABLE, while a present file that merely lacks the name is NOTFOUND — so `passwd: files [NOTFOUND=return] systemd` still lets systemd synthesise root once the file is deleted (the `NOTFOUND=return` never fires, because files never got as far as "not found"), whereas `[UNAVAIL=return]` does stop it. Collapsing the two would lock that machine out for good. `[SUCCESS=continue]` lets a later source override an earlier answer (glibc's last-wins) — extracting the walk exposed that the original `NameServiceSwitch` copy returned on any non-`merge` action, which made `continue` behave exactly like `return`; the shared rule distinguishes all three (`return` settles, `merge` combines, `continue` replaces). `[SUCCESS=merge]` unions group member lists, the one database glibc implements it for. What the later sources contribute — for `systemd`, the `root`/`nobody` records `nss-systemd(8)` synthesises precisely so a corrupt or missing `/etc/passwd` does not leave a machine with no root (`SYNTH_PASSWD`/`SYNTH_GROUP` are exported from `SystemdNssSource` so there is one definition, not two that can drift). A name found earlier is never overwritten, matching nss-systemd's own rule that it synthesises those two only when they are not defined by other means, so the `/etc/passwd` entry always wins. The synthetic records carry no secret (`password: '*'`, locked), so `id root` answers on a machine with no `/etc/passwd` while `checkPassword('root', …)` still fails — resolving a name and authenticating it are different questions. Relatedly, root's *own* seeded secret is now written as `$6$simulated$admin` rather than a bare `x`: it used to be the one account the file could not describe (password in memory only), so the first reload silently lost it — if the files are the store, root has to be in them too. One visible consequence, asserted by test rather than papered over: with `/etc/passwd` deleted, `ls -l` shows `root` for a root-owned file (synthesised) and a bare `1000` for a regular user's — both halves are real, and only the regular account actually loses its name.
  - `devices/linux/service/CriticalFiles.ts` (docs/PRD-Pannes.md §6.2, §13) is the single declarative place saying which files a service or a command cannot work without, so that deleting one **actually breaks the feature** rather than merely being reported somewhere. Before it, every config reader in the codebase did `vfs.readFile(path) ?? ''`, which makes "file deleted" indistinguishable from "file empty" — `rm /etc/ssh/sshd_config` had literally no effect. Both halves of that distinction are real behaviour and both are now modelled: a MISSING sshd config is a start-up failure (`/etc/ssh/sshd_config: No such file or directory`), an EMPTY one is legal and starts on built-in defaults, so the check is existence and never emptiness. The two failures are deliberately distinct because they are distinct on a real system: a missing executable is the shell failing to exec (`bash: /bin/ls: No such file or directory`, exit 127), a missing data file is the program itself refusing (`sudo: /etc/sudoers is required`, exit 1). `canonicalBinPath()` exists because the VFS ships the real merged-`/usr` layout (`/bin` → `usr/bin`, `/sbin` → `usr/sbin`) and `resolveInode` follows a symlink in the LAST path component but not an intermediate one — so `exists('/bin/ls')` answers false for a file genuinely present at `/usr/bin/ls`; normalising keeps this module agreeing with the filesystem instead of second-guessing it, and has the side benefit that `rm /bin/ls` and `rm /usr/bin/ls` are treated as what they are, the same file.     - **Une vue REMPLACE l'arbre visible, la ou un niveau de privilege AJOUTE au socle** (`docs/PRD-Acces-Privileges-Cisco.md` §8). Le sous-systeme des CLI Views etait entierement absent — `parser view`, `commands exec include|exclude`, `enable view`, `show parser view`, `username X view Y` repondaient tous `% Invalid input detected` — et ce n'etait pas une commande manquante mais un SECOND mecanisme d'autorisation a cote des niveaux de privilege. **La difference entre les deux EST le mecanisme, et c'est la seule chose qu'il ne fallait pas rater** : un niveau ajoute des commandes au socle du niveau 1, une vue remplace l'arbre visible par ce qu'elle inclut et rien d'autre — c'est ce qui la rend utilisable pour decrire un role, on enonce ce que le role a le droit de faire au lieu de l'ajouter par-dessus un socle qu'on n'a pas choisi. La consequence est observable : une commande hors de la vue n'est pas « refusee » mais ABSENTE, IOS rendant le meme `% Invalid input detected` que pour une commande qui n'existe pas. La porte est branchee la ou le filtrage par niveau l'etait deja (`executeOnTrie`) et **hors d'une vue elle rend `true` sans rien consulter**, de sorte que tout le reste du depot ne traverse aucune logique nouvelle (deux cas de non-regression le verifient). Quatre decisions, chacune parce que l'inverse etait possible : `parser view` **exige `aaa new-model`** (une vue vit dans AAA) ; une commande inconnue est **refusee a l'inclusion** (`%Command not found`, validee contre le trie privilegie) — sans quoi une faute de frappe produirait une vue silencieusement vide, exactement le defaut que ce mecanisme referme ; **on ne declare pas une vue depuis une vue**, sinon une vue restreinte s'octroierait des commandes ; et **on sort toujours d'une vue** (`exit`/`end`/`logout`/`disable`/`enable`/`show parser view` sont hors du filtre) — une vue dont on ne peut pas sortir n'est plus un role mais une souriciere, et `show parser view` doit repondre de l'interieur sans quoi on ne sait pas ou l'on est. `username X view NOM` est rendue sur une ligne SEPAREE comme IOS, la fondre dans la precedente donnant une ligne qu'un import ne saurait pas rejouer, et la vue referencee doit exister. `NetworkOsAccount.view` traverse `snapshot()`/`mutate()` comme les autres champs. `tuto-cli-views-cisco.test.ts` (18 cas) est discrimine : 14 tombent avant correctif, et les 4 restants sont nommes dans l'en-tete du fichier plutot que laisses a decouvrir — deux sont les cas de non-regression, les deux autres passaient avant pour une raison qui ne prouve rien du mecanisme (`parser view` etait deja refusee ; `enable view` ne faisait rien, donc on restait a la racine ou tout fonctionne).
    - **`?` walks past an argument, and never invents a command** (`docs/PRD-CLI-Fidelite-IOS.md` §1.1/§2.9). `CommandTrie.getCompletions()` abandoned its walk on the first token that wasn't a keyword, so `ip address 192.168.10.1 ?` — an argument already typed — answered nothing at all; it now consumes the argument and keeps walking, which fixed a whole class of help failures at one point rather than command by command. `describeArgs(path, specs)` is the declarative half (`cisco/ciscoArgumentHelp.ts`): it renders IOS's own argument *types* (`A.B.C.D`, `<1-4094>`, `WORD`, `LINE` — note `ParamType` has **no `'LINE'`**, the type that renders `LINE` is `'STRING'`, and getting that wrong silently falls through to `WORD`), creating `_hintOnly` nodes where a greedy parent absorbs the keyword. Two traps this exposed, both fixed: `_hintOnly` nodes were skipped by `prefixMatch` but **not** by the help renderer, so declaring a switch-only command on the router's trie made `?` offer a `switchport` the router does not have, description-less; and `autoContinuations` — which scrapes keywords out of a greedy handler's own source text — offered whatever it could not describe, so `password ?` in `line` mode listed ten words that are not arguments of `password`. Both of those workarounds are **gone**, and so is the mechanism behind them: see the completion campaign below — continuations are declared, not scraped, and the switch shell **does** receive `describeCiscoArguments` (`CiscoSwitchShell.ts`, after every registration).
    - **Une plage annoncee par `?` est une plage APPLIQUEE** (`CommandTrie.finish`, `CiscoShellBase`). Les declarations d'arguments etaient faites pour DECRIRE et jamais pour DECIDER : en parcourant `cliHelp`, 99 places annoncent leur valeur par un `<min-max>`, et quinze acceptaient une valeur au-dessus du maximum qu'elles venaient d'afficher — `ip ssh time-out 121` alors que l'aide dit `<1-120>`, `track 1001` pour `<1-1000>`, `radius-server acct-port 65536` pour `<0-65535>`, `router bgp 65536`, `access-list 2700`, `priority-list 17`, `queue-list 17`. Le controle vit desormais dans `finish`, seul passage commun aux quatre sites qui terminent une commande greedy, et il lit les DEUX mecanismes de declaration que porte ce fichier : `node.params` (`describeArgs`) et les continuations a `valeur` (`valeurAttendue`, reutilisee telle quelle plutot que recopiee). **La regle est deliberement etroite, et la premiere version ne l'etait pas** : appliquer toutes les declarations a la lettre faisait tomber 215 cas — `delete flash:jamais.cfg` refuse parce que le type `WORD` n'admet ni `:` ni `.`, `disconnect all` refuse parce que la place est declaree `<1-16>` alors que `all` est un mot-cle legitime. Seul un jeton NUMERIQUE hors d'un intervalle annonce est donc refuse : un jeton non numerique n'est jamais juge par cette regle, ce qui laisse intacts les mots-cles que les declarations ignorent. **Une regression introduite puis refermee dans le meme lot, et gardee par test** : un refus d'argument venu d'un sous-mode etait rejoue contre l'arbre GLOBAL par `tryGlobalConfigNavigation` — `spanning-tree cost 0` en interface repartait vers le `spanning-tree` global, qui l'acceptait en silence.     - **L'aide et la complétion répondent à la même question, et ne peuvent plus se contredire** (`docs/AUDIT-Completion-Aide-CLI.md`, dix étapes). Le point de départ mesuré : `?` et `Tab` étaient deux implémentations d'une même décision, si bien qu'une **vue CLI** filtrait `?` et pas `Tab` (une vue restreinte se voyait donc compléter une commande qu'elle exclut), et qu'un niveau de privilège divulguait par `?` des branches dont **aucune** feuille n'était atteignable. Elles passent désormais par un seul prédicat, `commandVisibleToNow`, et un nœud intermédiaire est visible **s'il mène à quelque chose de visible** — le repli restant délibérément OUVERT, masquer n'étant pas ici une frontière de sécurité (l'exécution l'est, et elle refuse). **Trois garde-fous par balayage** remplacent la correction au cas par cas, et chacun exige l'égalité exacte plutôt qu'un plafond, donc leur liste ne peut que décroître : tout mot que `?` propose est **exécuté** et ne doit pas répondre `% Invalid input` (soixante-dix promesses non tenues au départ, liste aujourd'hui vide) ; tout `<cr>` annoncé est **validé** sur une machine neuve (trente-deux menteurs, liste vide) ; tout mot offert porte une description. L'invariant du premier est ce qui le rend utile : `% Incomplete command.` est une **bonne** réponse — le mot-clé est bon, il en manque d'autres — tandis que `% Invalid input` dit que le mot n'existe pas ; les confondre était d'ailleurs le défaut le plus répandu, vingt-huit gestionnaires refusant leur sous-commande par `throw new CliInvalidInput({ token: args[0] })` avec un `args[0]` indéfini, ce que `CliInvalidInput.motAbsent()` distingue maintenant en un seul endroit (et le prédicat exige que le jeton ait été **nommé**, un `throw` nu voulant dire « invalide » et non « incomplet »). Deux règles structurelles ont emporté le gros du reste : **un nœud qui déclare des paramètres n'accepte ses enfants qu'au rang zéro** (`ip address 10.0.0.1 255.255.255.0 dhcp` n'existe pas, tandis que `show interfaces Gi0/0 accounting`, dont le nœud ne déclare aucun paramètre, reste atteignable), et **un aiguillage pris ferme ses autres branches** (dès qu'un des mots d'une famille est sur la ligne, les autres en sont les alternatives et non les suites). Les commandes que le répartiteur traite AVANT l'arbre — `exit`, `end`, `help`, `do`, `default` — n'avaient aucun nœud donc aucune aide ; ce que chacune rend est **lu sur ce qu'elle fait** (`do X` s'exécute sur l'arbre privilégié, donc `do ?` rend cet arbre à toute profondeur ; `default X` s'exécute comme `no X`, donc son aide est celle de `no`). `ParamSpec.alternatives` existe parce qu'une place accepte parfois **plusieurs formes** (`ip access-group ?` en rend trois) : ce n'est pas un `ENUM`, qui liste des valeurs admises là où ce sont des types, et le rendu seul est concerné — le type déclaré reste `WORD`, donc l'analyseur accepte `10` comme avant. `neJamaisAnnoncer` marque une commande enregistrée **pour être refusée** (`show ip sla monitor`, supprimée par IOS 15, existe seulement pour que le glouton `show ip sla` ne réponde pas à sa place) : elle est retirée de `?`, de la tabulation et du décompte des chemins exécutables. **Le point de génie logiciel le plus lourd** : l'aide d'un nœud glouton était DÉRIVÉE du texte source de son gestionnaire, donc une réécriture de code la défaisait en silence — ce dépôt l'avait déjà payé, la réécriture de `no privilege` ayant fait disparaître le mot `level` de son source, donc de son aide. Ce que l'extraction produisait au moment de la retirer était pourtant **juste** (344 paires côté routeur, 213 côté commutateur, toutes de vrais mots-clés d'IOS) : le défaut n'était pas ce qu'elle disait mais d'où elle le tenait. Les paires sont relevées et écrites dans `cisco/ciscoContinuations.ts` (`SOCLE` pour ce que les deux plateformes portent, deux tables par plateforme pour le reste, afin qu'une déclaration ne fabrique jamais un nœud sur une machine qui n'a pas la commande), `HandlerKeywordExtractor` est supprimé, et le filtre « pas de description, pas d'annonce » part avec lui — il compensait l'extraction, alors qu'une suite déclarée est un vrai mot-clé par construction ; à sa place un test exige que **chaque mot déclaré porte une description**, ce qui a fait écrire les 71 qui n'en avaient pas et que `Tab` complétait pendant que `?` les taisait. Piège appris deux fois plutôt qu'une : les arbres sont **relevés sur l'objet** (`tousLesArbres()`) et non nommés à la main — le premier relevé n'en avait parcouru que cinq, là où le routeur en porte cinquante-deux, et quarante-sept modes se sont retrouvés sans suites. Enfin le rendu : `<cr>` est **placé** en dernier et jamais trié, l'ordre est celui des **octets** (`/` < majuscules < minuscules, un `localeCompare` mettrait `a` avant `B`), et la tabulation trie comme l'aide — deux fois, car les commandes universelles et celles descendues par un niveau de privilège arrivent en queue. Côté valeurs vivantes, le `DynamicParamResolver` existait et fonctionnait : ce qui manquait était que `?` sur un mot **partiel** ne le consultait pas (la même machine complétait `G` par `Tab` et répondait « ce mot n'existe pas » à `G?`), et que la place d'une interface était reconnue au **singulier**, donc `show interfaces` — la commande la plus tapée de toutes — ne recevait jamais rien. Ce que les sondes ne demandent délibérément PAS, et qui est écrit dans leur en-tête : qu'une ligne finie par un blanc complète quelque chose — une vraie machine n'y complète rien, elle émet un bip.

  - `http/curl/` (`docs/PRD-Curl.md`) — **`curl` is one engine serving two platforms**, because `curl` is not a Linux command: Windows has shipped `curl.exe` since 1803, and a Windows machine here had none. Duplicating it would have produced the drift this project keeps undoing elsewhere (two Windows registries, two SSH implementations) — two `curl`s that eventually disagree about the same situation. So the engine sits next to `HttpClient.ts`, which both platforms already share: `CurlArgs.ts` (parsing, short clusters included), `CurlTransfer.ts` (the real HTTP/1.1 + TLS request, redirects, the `-v` trace), `CurlWriteOut.ts` (`-w`), `CurlEngine.ts` (output/stderr/exit code), and `CurlHost.ts`, the narrow port each platform fills — name resolution, TCP stack, trust anchors, file write. Linux plugs in through `commands/net/Curl.ts` (a `LinuxCommand`), Windows through `WindowsPC.cmdCurl` (cmd.exe, `curl.exe`, and PowerShell's native passthrough). What the PRD fixed: `-s` and `-v` were parsed then **discarded**, and `run()` returned a `string` so the command had **no exit code** at all — `curl … || echo KO` could never fire. `-v` writes to stderr (the bash interpreter's `stderr` field carries it), so `curl -v url > f` puts only the body in the file. **Three families of options, not two**: implemented ones act; ones curl knows but this build doesn't implement are refused with `curl: option -x: is not implemented in this simulator`; genuinely nonexistent ones get curl's own `curl: option -Z: is unknown`. The middle message is deliberately not a curl message — no real curl is ever in that situation, and answering `is unknown` for an option curl knows would be a second lie. P4 (proxy, cookies, `--retry`, forms) is not implemented and falls in that middle family. Honest limits: only `%{time_total}` is offered among the timing variables (making `time_connect`/`time_namelookup` all equal to it would be an invented breakdown; an unknown `-w` variable is reported, never guessed), and PowerShell treats `curl` as `curl.exe` (PowerShell 7 behaviour) rather than as 5.1's `Invoke-WebRequest` alias. The old `cmdCurl` stub in `LinuxNetCommands.ts` — which answered `<h1>It works!</h1>` to any `curl localhost` on a machine where nothing was listening — is deleted.
  - **`--cacert` is the first thing in this codebase that VERIFIES a certificate rather than merely negotiating TLS with one**, and that single fact explains a family of defects rather than one. Every HTTPS lab reached its server with `-k`, and `-k` means "do not check": a handshake succeeded because the two ends agreed, never because the certificate was usable. Three defects were sitting in exactly that blind spot and all three surfaced within one session, none of them in curl. (1) `subjectAltName` is stored as openssl spells it on the command line (`DNS:lab.local`) and `certificateMatchesHostname` compared the whole stored string, so a certificate carrying a SAN matched no host at all — and since SAN takes precedence over the common name, *adding* one made the certificate worse. (2) The common-name fallback looked for a bare `CN=` while RFC 4514 permits whitespace and this simulator's own `openssl req` renders `CN = lab.local`, so no certificate issued here could ever match by common name; only a SAN worked, and only by accident. (3) `openssl req -x509 -addext subjectAltName=...` grafted the extension onto the certificate AFTER `generateSelfSignedCertificate` had signed it, and `tbsPayload` covers the extensions — so the file on disk no longer matched what was signed and no verifier could accept it; `SelfSignedCertificateOptions.subjectAltName` now carries the names in before signing (the two CSR-signing paths, `x509 -req` and `ca`, already built extensions into the signed fields and needed no change). This is the same shape as the two openssl defects nginx §P5 found (mismatched key pair, `rsa -modulus` printing the private material): a value displayed that nothing checks stays wrong until something checks it. `--cacert` itself REPLACES the trust store rather than adding to it — otherwise passing the wrong bundle would still succeed through the system anchors and the option would be a decorated `-k` — and a bundle that does not exist fails before the handshake with curl's own error 77. Note what the tests can and cannot discriminate, stated rather than implied: a Linux machine's store is empty here, so replace-vs-merge is not observable yet; the two matcher fixes are pinned by neutralization (3 of 9 cases fall without them). `CurlHost` gained `readFile`, filled on both platforms, since it is one engine. The corollary for the rest of `docs/PRD-OpenSSL.md`: `pkcs8`, `pkeyutl` and `crl` sit in precisely that unverified state today — their output has never been consumed by anything that checks it.

They share port 80 and therefore its conflict, **in both directions** — whichever starts second loses, with its OWN wording (`(98)Address already in use: AH00072: make_sock: could not bind to address 0.0.0.0:80` for Apache, nginx's own for nginx), because that message is what an operator searches their log for. No new TLS engine — `HttpsServerSession` already drove a real `TlsServerSession` record by record; it only lacked the listener identity, so `ss -ltnp` would have shown an ownerless `:443` beside an owned `:80`. **The load-bearing decision is that `tlsMaterialFor` has THREE outcomes, not two**: `'error'` is not a variant of `null`, so a port declared `ssl` whose certificate cannot be read stays SHUT instead of falling back to plain HTTP on 443 — the worst available answer, since everything downstream treats 443 as encrypted.   - `crypto/openssl/` (`docs/PRD-OpenSSL.md`) — **`openssl` did not exist as a command at all** — no file, no `case`, no entry point — while `PackageDatabase.ts` declared the package `installed: true`: a machine claiming through `dpkg -l` to hold a tool whose binary was absent. The single lock was PEM, and `src/network/pki/pem.ts` lifts it: real RFC 7468 armour in 64-column base64, with a JSON payload rather than DER — the signature being simulated (this directory's stated convention), an exact DER would not be verifiable by a real openssl either, and an honestly non-DER payload beats a DER claiming interoperability it does not have. That file is what unblocks anything needing a certificate ON DISK (nginx HTTPS, sshd host keys, `curl --cacert`, any lab PKI). What is REAL rather than simulated, because `src/crypto/` already implemented it: `dgst` (md4/md5/sha1/sha256/sha512), `hmac` (the real RFC 2104, taking the algorithm object — block and output size both matter — not its name), `base64`, `rand`, `passwd -1` (md5Crypt), and `enc`'s AES-CBC + PBKDF2. The contract pinned by test: `sha256sum f` and `openssl dgst -sha256 f` return the SAME digest because they call the same engine — a simulator where they differed would teach that a digest depends on the tool. `OpenSslArgs.ts` reuses `PRD-Curl`'s three families of options (implemented / known-but-unimplemented / nonexistent), the middle message deliberately not an openssl one. Two honest limits, each written where it applies: **`enc` refuses raw binary output to a file** and says why — the VFS stores UTF-8 strings, so arbitrary bytes would be replaced on read and decryption would silently return something else; `-a` (a real openssl option) lifts it, and the armoured output is exactly the real tool's. **3DES is absent**, and the PRD's own §8.3 was wrong to announce it real: `src/crypto/cipher/des.ts` exports `desCbcEncrypt` and no `desCbcDecrypt`, so `enc -des-ede3-cbc` would encrypt without being able to decrypt — a command that loses the data entrusted to it, worse than its absence. **Two defects in this command were found only when nginx §P5 made something USE its output together**, and both are the same shape as the gaps this repo keeps closing — a fact displayed that nothing backs. (1) `req -x509 -keyout k -out c` wrote one private key to disk and built the certificate from a DIFFERENT keypair generated inside `generateSelfSignedCertificate`, whose returned `privateKey` was discarded: every command reading one file without the other was happy (`x509 -noout -subject` printed the subject, `verify` self-verified) and the pair failed the instant a TLS server presented it. `SelfSignedCertificateOptions.keyPair` now lets a caller certify the key it already holds, rather than duplicating the signing logic. `x509 -req` was already correct — it signs the CSR's own public key. (2) `rsa -modulus` printed the PRIVATE material where `x509 -modulus` prints the public one, so the canonical pairing check every admin runs (`openssl x509 -noout -modulus | openssl md5` against `openssl rsa -noout -modulus | openssl md5`) reported a matching pair as mismatched — and leaked the secret into output people routinely paste around. The modulus is half of the public key; both now print it.
  - **La cryptographie asymétrique et TLS sont RÉELS** (`src/crypto/ecc/`, `src/crypto/rsa/`, `src/network/tls/hkdf.ts`, `src/network/tls/recordProtection.ts`, `src/network/tls/keyExchange.ts`). Ils ne l'étaient pas : une clé de `PkiKeyPair` était `pub:<graine>`/`priv:<graine>` — la même graine des deux côtés — et `verify()` reconstituait le matériel privé depuis le public, si bien que **quiconque tenait la clé publique pouvait forger** ; la protection des enregistrements TLS était un XOR de flux sans authentification ; le calendrier de clés et le secret DHE des `simulatedDigest` des valeurs publiques. Cinq étages ont été rendus réels, chacun confronté à des vecteurs PUBLIÉS plutôt qu'à lui-même — c'est ce qui distingue une implémentation d'une invention plausible, une arithmétique écrite de mémoire donnant des résultats parfaitement déterministes et parfaitement faux : **HKDF-SHA256** (RFC 5869 §A.1/2/3, dont le cas à 82 octets qui exerce trois tours du compteur), **AES-128-GCM** sur les enregistrements (clé et nonce du §7.3/§5.3, données additionnelles du §5.2), **X25519** (RFC 7748 §5.2 et l'échange complet §6.1), **RSA PKCS#1 v1.5/SHA-256** (RFC 8017 §8.2/§9.2), **ECDSA P-256** à `k` déterministe (RFC 6979 §A.2.5) et l'**ECDH P-256** qui va avec (`secp256r1`). **Il ne reste plus rien de simulé** : les groupes TLS que ni X25519 ni P-256 ne servent (`secp384r1`, `ffdhe2048`…) retombaient sur le condensé des valeurs publiques, et une session configurée des DEUX côtés sur `secp384r1` réussissait donc sur un secret que n'importe quel témoin recalculait — mesuré, et invisible jusque-là parce que les seuls tests nommant ce groupe s'en servaient pour provoquer une ABSENCE de groupe commun, jamais des deux côtés à la fois. Le correctif n'est pas d'écrire P-384 mais de cesser de prétendre : `IMPLEMENTED_GROUPS` (`keyExchange.ts`) dit lesquels sont réels, le client ne les offre plus dans son `ClientHello`, le serveur ne les sélectionne plus (ni par `key_share` ni par `HelloRetryRequest`), `sharedSecret` rend `null` — donc une alerte — au lieu d'une valeur, et un client n'ayant que des groupes non implémentés n'émet rien du tout, comme une vraie pile dans la même situation. `tls-implemented-groups-only.test.ts` garde la référence `x25519` dans le même laboratoire, sans quoi un labo mal monté et un refus correct seraient indiscernables. Trouvé au passage : l'alerte `illegal_parameter`, déjà émise par les deux sessions quand l'échange de clés ne rend pas de secret, ne figurait ni dans le type `AlertDescription` ni dans le registre des codes du §6 — son code numérique était `undefined`. **Rien n'est à temps constant** : arithmétique juste, pas bibliothèque de sécurité ; les PEM restent du JSON armuré et non du DER, donc rien n'est interopérable avec un vrai openssl. **La taille de clé RSA par défaut est 512 bits, et c'est un choix MESURÉ** : une clé de 2048 coûte 460 ms en moyenne à fabriquer en JavaScript (médiane 403, p90 893) et la suite en génère 2154 rien que sur les fichiers PKI, soit un quart d'heure ; la taille DEMANDÉE est toujours honorée (`openssl genrsa 2048`, `req -newkey rsa:2048` font un vrai module de 2048 bits, que `rsa -text` affiche en le MESURANT), seules les clés dont personne n'a précisé la taille prennent la petite. **La leçon vaut au-delà de la crypto** : chaque étage rendu réel a fait tomber un défaut que l'étage simulé rendait invisible, jamais l'inverse — `ZERO_IKM` faisait seize octets là où la RFC en veut trente-deux ; les données additionnelles portaient `0` pour tous les types (`ContentType` est un NOM, pas le code du fil), donc le type n'était pas authentifié et mentir dessus passait inaperçu ; la part de clé du serveur partait sans son groupe ; cinq endroits dérivaient la clé publique par `material.replace('priv:', 'pub:')`, ce qui laissait l'exposant PRIVÉ dans la moitié « publique » ; `x509 -modulus` n'imprimait pas la même chose que `rsa -modulus`, cassant le contrôle canonique d'appariement clé/certificat. Aucun des cinq ne pouvait se voir tant que rien ne vérifiait pour de bon. Un corollaire opérationnel : `decryptApplicationData` peut désormais ÉCHOUER (`BadRecordMacError`) — un octet retourné, une étiquette tronquée, un rejeu ou un type modifié sont DÉTECTÉS, ce qu'un XOR ne pouvait pas offrir.
  - `llmnr/LlmnrAgent.ts` (RFC 4795, UDP/5355 on 224.0.0.252) and `mdns/MdnsAgent.ts` (RFC 6762, UDP/5353 on 224.0.0.251) are real responders/queriers sharing one transport, `dns/transport/MulticastDnsTransport.ts`. A host answers only for the name it owns — its single-label hostname for LLMNR, `<hostname>.local` for mDNS — and stays **silent** otherwise (a NXDOMAIN on a group would speak for the whole link). LLMNR replies unicast to the asker; mDNS replies on the group, except to a one-shot query from an ephemeral source port, which gets a unicast reply with a 10s-capped TTL (§6.7), and announces itself unsolicited at start with the cache-flush bit (§8.3). Wired into `ResolvedService` by systemd's own rule — `.local` goes to mDNS and never to a unicast server (RFC 6762 §3), a single-label name falls back to LLMNR when DNS has nothing — so `resolvectl query`, `getent hosts` and `ping <name>` all reach them; `resolvectl query` names the protocol used (`-- Information acquired via protocol LLMNR/IPv4`), and a link-local answer is never reported as authenticated since nobody signs it. **The global `LLMNR=`/`MulticastDNS=` setting is the default for links, not an independent switch**: a protocol is on as soon as one link allows it, and the global decides only while no link is configured — without that rule `resolvectl llmnr eth0 no` on the only link closed nothing, and `resolvectl mdns eth0 yes` did nothing on a machine with no DNS server. **Name conflict is handled, and the two RFCs diverge there.** LLMNR *signals*: at start the host asks the link for its own name three times (§4.1); an answer means someone else holds it, so it sets the `C` bit in its replies and lets the asker decide — it never renames. mDNS *arbitrates*: it probes three times 250ms apart (§8.1) with an `ANY` question carrying its intended records in the Authority section, and on conflict moves to `alpha-2.local` and re-probes (§9); two hosts probing at once can't rely on each other to answer, so they compare proposed records and the greater one wins (§8.2). While probing, a host does **not** answer for the name — that would assert the ownership it is still verifying. **Header trap, and a real bug this fixed:** LLMNR redefines bit 10 as `C` (Conflict) where DNS has `AA`, and bit 8 as `T` (Tentative) where DNS has `RD`. The responder set `aa: true` on every reply "because an LLMNR responder is authoritative" — so it announced a conflict every time; `llmnrFlagOverrides`/`readLlmnrBits` in `llmnr/types.ts` exist so the aliasing is written down rather than guessed. **Known-answer suppression** (§7.1) is implemented: a querier attaches what it already knows, the responder drops those records and stays fully silent if nothing is left. The threshold is the RFC's — the querier's copy only counts if its TTL exceeds half the TTL *we would have served*, which for a one-shot query is the §6.7-capped 10s, not 120. **DNS-SD** (RFC 6763) lives in `dnssd/`: `DnsSdRegistry` synthesises PTR/SRV/TXT (plus the `_services._dns-sd._udp.local` type enumeration of §9) and `MdnsAgent` answers from it alongside its own address records, attaching the follow-up records as additionals (§12) so one round-trip suffices. Publishing goes through a **unit file**, not a command: `/etc/systemd/dnssd/*.dnssd` (`systemd.dnssd(5)`, `net/DnssdFiles.ts`), same `[Section]` format and same `/etc` › `/run` › `/usr/lib` precedence as networkd's `.network`; an entry missing `Name`/`Type`/`Port` is skipped rather than half-published. This is what gave `resolvectl service` a data source — it was previously declared out of scope for lack of one. Instance names are free-form including dots (§4.1.1), so `parseInstanceName` splits from the end. **Subtypes** (§7.1) answer too: `_printer._sub._http._tcp.local` PTRs point at the very same instance — a subtype narrows discovery, it does not create a second service — and they stay out of the §9 type enumeration. **Service lifecycle** (§8.4, §10.1): a service is announced once the host name is claimed (never before — that would assert both at once), re-announced with cache-flush when it changes, and sent with TTL 0 when withdrawn. `.dnssd` reload is differential rather than clear-and-republish: without diffing, a service deleted from disk would vanish silently and peers would keep believing in it; republishing an unchanged one announces nothing. So this isn't decorative, `MdnsAgent` also *listens* to other hosts' announcements and keeps a passive cache of services heard (`knownServices()`) — that cache is what a TTL 0 empties, and it is what makes a goodbye observable at all. `systemd.dnssd(5)`'s `SubType=`, `Priority=` and `Weight=` are parsed and reach the SRV. Cache entries expire on their announced TTL (§10) — a peer that dies without a goodbye is forgotten rather than believed forever, and a re-announcement pushes the deadline back. Pruning happens on read and on every announcement heard rather than on a per-entry timer: the observable contract (an expired service is never reported) holds, so the expiry event fires *at or after* the deadline, not to the second. The cache reports what was *heard*; `browse()` asks a live question, so after expiry a browse still finds the service — an expired entry is not an absent service. **The IPv6 groups (`FF02::1:3`/`FF02::FB`) are now real**, the blocker once named here (no arbitrary-group send path on the v6 stack) having been removed by `EndHost.sendIPv6ToGroup`: `McastDnsBinding.group6` carries the group, every send site emits on BOTH groups (a peer may listen on only one, and v4-only would make this host invisible on a v6 link), and `bindMulticastDns` joins the group so replies can be heard. Three defects surfaced getting there, each of them outside mDNS/LLMNR and each measured rather than guessed. (1) **`sendIPv6ToGroup` read the scope from the wrong place**: it tested `isLinkLocal()`, which is `fe80::/10` and therefore FALSE for every multicast group including `ff02::5`, so a link-local-scope datagram left with a global source and the default hop limit; the scope of a group is the second nibble (RFC 4291 §2.7), now `multicastScope()`/`isLinkLocalScopeMulticast()`. (2) **The daemon is bound at boot, before any address is configured**, so joining only the interfaces that already carried IPv6 joined nothing at all and an address configured afterwards opened no group — the host asked questions it could never hear the answers to; membership is now per interface and takes effect when that interface gains IPv6, as a kernel programs a group on a link. (3) **`configureIPv6Interface` never installed the `fe80::/10` connected route** — only `enableIPv6()` did, and it pushed a duplicate on every call — so a normally-configured host could not reach ANY link-local address: `resolveIPv6Route` found nothing and the send failed silently. That is what stopped the unicast reply, whose destination is precisely the asker's link-local. Both agents also answer **AAAA** now (LLMNR gained `resolveAaaa`, and answers the type asked rather than substituting A for AAAA), since a transport that crosses a v6-only link and teaches no address would be decoration. Link-local addresses are deliberately never advertised: they are ambiguous off their link and the record carries no zone index. Still deliberately out of scope: continuous re-querying at 80–95% of TTL (§5.2, needs a long-lived active browse), and the RFC's one-second grace before acting on a goodbye. The §8.2 tiebreak compares sorted A records rather than the RFC's canonical byte-wise form (same ordering for the only records in play here, but a simplification, not the letter). The responder is host-wide while the setting is per-link, so per-link granularity of *responding* is not modelled; per-link granularity of *resolving* is.

  - `ipsla/` (`docs/PRD-IP-SLA.md`) — **IP SLA sends real probes now, and what they measure is what decides.** The previous implementation was not a simplification but an inversion: `IpSlaRepository.ipReachable()` answered "is the target reachable?" by walking `router.getRoutingTable()` — asking the machine what it *believes*, when the whole point of an active probe is to discover that the belief is wrong. A dead target behind an intact route, a blackholing next hop, an ACL dropping the echo-reply all answered `reachable`; `frequency` was stored and read only by the renderer (no `setInterval` anywhere under `inspection/config/`); `timeout`/`threshold` lived in an untyped `op as unknown as Record<string, unknown>` bag and gated nothing; reactions were stored and never evaluated; `ip sla responder` set a boolean and opened no port; and `TrackRepository` called the same `sla.reachable()` for BOTH `ipsla-reach` and `ipsla-state`, fusing the two questions IOS keeps apart. The canonical lab of the whole subsystem — `ip route 0.0.0.0 0.0.0.0 <ISP1> track 1` failing over while the ISP1 link stays up — could not work. The engine now runs on `src/events/Scheduler` with a real lifecycle (Pending → Active → Inactive, `ageout` deleting the entry, `recurring`, `restart`) and a verdict that is one of `rttMonLatestRttOperSense`'s codes rather than a boolean — the `Over threshold` / `Timeout` / `Dropped` / `Not connected` distinction being exactly what separates `track … state` from `track … reachability`. Probes: `icmp-echo` (RFC 792), `udp-echo` (RFC 862), `udp-jitter` with its four timestamps, `tcp-connect` on the real handshake, `http` through the existing RFC 9112 client, `dns` through the real wire codec, `icmp-jitter`, `path-echo`. The responder really opens a port through an IP SLA Control Protocol exchange on UDP/1967, authenticable by key-chain MD5 — a probe toward a responder that is off is **refused** (`Dropped`) without burning the timeout, and the negotiated port closes on expiry. Two things that could have been done half-way and were not: jitter is signed and kept per direction (RFC 3393) with RFC 3550 §6.4.1's smoothed estimator rendered alongside, and losses are **attributed** to a direction rather than summed — the responder reports what it received, so a gap it never saw is an SD loss, a different fact from a reply that was lost; and one-way values are only counted when BOTH ends declare themselves NTP-synchronized, so the sample counter stays at 0 without NTP exactly as on real IOS instead of publishing a meaningless number. MOS/ICPIF come from the G.107 E-model with G.113's per-codec `Ie`/`Bpl`; the test pins the G.711/G.729A **crossover under loss** (G.729A's `Bpl=19` vs `4.3` makes it win above ~1% loss), which is a real property of the model and would have been easy to invert "because it looks more logical". Reactions genuinely evaluate: five threshold types with distinct semantics, hysteresis requiring a return past the LOW threshold to clear, and polarity as a declared property per element (a low MOS is bad — comparing everything with the same `>` would have been a silent bug); `ip sla logging traps` writes `%RTT-3-IPSLATHRESHOLD`, which makes thresholds usable from EEM with no EEM code at all. `track` finally applies `delay up`/`down` (parsed and read by nobody before), counts its changes, lists `Tracked by:`, and emits `%TRACKING-5-STATE`. CISCO-RTTMON-MIB is projected as lazy accessors over live state, so an `snmpget` answers the current measurement. **Three defects found while building this and fixed here**: (1) `ip route 0.0.0.0 0.0.0.0 <nh> track <n>` silently dropped its `track` AND `permanent` — the default route goes through `setDefaultRoute()`, whose signature carried neither, so the single most common floating route in the whole object-tracking story was unconditional; (2) IP SLA and `track` state lived on the SHELL, and `createVtyShell()` builds a fresh shell per session — a `track` typed over SSH was invisible from the same machine's console, and the running-config (rendered by the shell but describing the device) could not see either; both now live on `Router`; (3) nothing was rendered in the running-config although track-conditioned static routes WERE saved, so a reloaded topology had routes hanging off objects that no longer existed. Deliberate, measured limits written into the PRD rather than left to be discovered: frame delivery is synchronous so the RTT is 0 ms in virtual time and no topology can cross a threshold by itself (`overThreshold` is reachable by logic, tested, not by the path — it becomes observable the day `Cable` carries latency, with no engine change); a dead host behind a router yields `Dropped` rather than `Timeout` because the last-hop router answers ICMP Destination Unreachable, and rendering a received negative answer as an absence of answer would throw information away; `verify-data` is applied and structurally unreachable (nothing corrupts an ICMP payload here); and the responder reports the LIST of sequence numbers it received where a real one sends a count — that is what makes the SD/DS split exact instead of a best-effort attribution, at the price of this simulator being better informed than the hardware. Still out of scope, each because a brick is missing rather than because it is hard: `path-jitter`, `ftp`/`dhcp` operations (no FTP or DHCP client on a router), `voip`/RTP, MPLS LSP, Y.1731, IPv6 targets (no ICMPv6 emitter on a router — a separate, reusable piece of work), VRF (no per-VRF forwarding plane, so the command is refused rather than stored inert), TWAMP (RFC 5357 is a protocol of its own, not a responder option), and Huawei NQA (the twin subsystem, entirely absent today — its CLI can reuse this engine).

Assumed limits, written down rather than left to be found: the RTT is 0 ms in virtual time (same synchronous-frame-delivery cause as on the IOS side), so `threshold rtd` always counts 0 crossings in a test topology — the logic is exercised, the crossing cannot come from the path; `start delay … milliseconds` rounds up to the second, the engine's scheduling having no finer granularity; and `records result <n>` is stored and bounds nothing, since only one result per test is kept today. Out of scope and unchanged from the IP SLA list: IPv6 targets, `vpn-instance` (refused rather than stored inert), NQA traps (the Huawei NQA MIB is distinct from CISCO-RTTMON and nothing consumes it yet), and Huawei switches.

  - `eigrp/EIGRPEngine.ts` implements the real DUAL *feasibility condition* (successor = lowest FD; a feasible successor needs RD < FD, gated by `variance`/`maximum-paths`) — genuinely more than plain distance-vector. But there is no Active/Passive state, no Query/Reply/Ack, and no RTP (`packets.ts` only defines `hello`/`update` opcodes); a lost successor with no feasible backup just recomputes instantly from cached Update TLVs instead of diffusing a query, and there is no SIA/stuck-in-active concept because there's no Active state to get stuck in. Timers are explicitly documented as absent in the engine's own header: liveness is "a convergence round IS the hello interval," not a wall-clock hold timer — there is no `src/events/Scheduler` usage anywhere under `eigrp/`. Convergence itself is CLI-triggered (`RouterDynamicRouting.converge()`, called from `Router.convergeDynamicRouting()`), not timer-driven; `Router._setupPortMonitoring()` also fires it on link up/down so an autonomous link failure doesn't need an operator to run a `show` first (mirroring, but not literally reusing, the same wiring OSPF has), but this only makes the *existing* recompute run on more triggers — it isn't real timer-driven convergence. Already tracked as backlog: `docs/audit/02-protocoles-L3-routage.md` (item #10, "EIGRP QUERY/REPLY + hold timers réels") and a stale, never-implemented `docs/DESIGN-EIGRP.md` that once scoped real RTP/Active/SIA and was abandoned in favor of the simpler shipped engine.
  - `vtp/VtpAgent.ts` (`docs/PRD-VTP.md` Phase 1) used to conflate two distinct real-Cisco fields under one name: `VtpConfig.updaterMac` (a switch's own fixed chassis MAC, shown as "Device ID" in `show vtp status`) was overwritten on every received Summary with the *sender's* identity — real VTP's "Updater Identity" is a separate, gossiped IP address (the lowest-numbered active VLAN SVI, or the management interface) naming whoever last bumped the revision, and never touches the receiver's own Device ID. Fixed by splitting them: `updaterMac` is now local-only and never mutated by peer sync; `VtpConfig.lastUpdaterIdentity`/`lastUpdateTimestamp` (new fields) carry the learned IP+timestamp, set from `Switch._vtpUpdaterIdentity()` (lowest-VLAN SVI IP, `'0.0.0.0'` if none) on a local revision bump and from the wire on receipt. `show vtp status`'s "Configuration last modified by"/"Local updater ID" lines now read `lastUpdaterIdentity`/`lastUpdateTimestamp` instead of re-deriving a fresh local IP every time. Also added real Subset Advertisement fragmentation (Cisco splits a large VLAN database across multiple numbered Subsets after a Summary declares a follower count): `sendSummaryAndSubset` chunks the VLAN list into 40-VLAN lots and sends one `subset` frame per lot with a `sequenceNumber`, preceded by a `summary` frame's `followers` count; the receiver buffers fragments by sequence number in `pendingSubsetParts` and only calls `vtpApplyVlans()` — which treats its argument as the *complete* target set, deleting anything local not present — once every declared fragment has arrived, discarding/resetting the buffer on a new, non-matching Summary. An incomplete fragment set (peer link drops mid-transfer) therefore leaves the local VLAN database and revision untouched rather than partially applying a truncated diff. The common single-lot case (≤40 VLANs, the overwhelming majority of labs) is unchanged: one `summary` + one `subset`, `followers`/`sequenceNumber` both default to 1.
  - `vtp/VtpAgent.ts` (`docs/PRD-VTP.md` Phase 2) propagates a v3 MST region (`docs/PRD-STP.md §4`'s `MstRegion` — name/revision/instance table) between switches in the same VTP domain, independently of the standard VLAN database. `VtpFrame` gained an optional `database?: 'vlan' | 'mst'` tag (absent/`'vlan'` is today's flow, untouched) and an `mstRegion` payload (the region's `instances: Map<number, string>` flattened to `[number, string][]` for the wire); `VtpConfig.mstDatabaseRevision` is a separate auto-incrementing counter — distinct from both the VLAN database's `revision` and the operator-set `MstRegion.revision` carried as data — bumped by `onLocalMstChange()` (wired from every `CiscoSwitchShell` mutation under `spanning-tree mst configuration`: `name`/`revision`/`instance`/`no`) exactly like `bumpRevision()` does for VLANs. `handleFrame` branches on `payload.database === 'mst'` into a dedicated `handleMstFrame` with its own summary/subset state (`lastMstSummaryDomain/Revision`, `hasSyncedMstDatabase`) completely separate from the VLAN path's — a fresh-join client catches up on an equal revision the same way the VLAN flow does, and a server relays a newly-learned region onward. `StpAgent.applyMstRegion()` (new) is the single call a synced client makes to replace its whole local region (name/revision/instance map) in one shot, mirroring `vtpApplyVlans`'s full-replace semantics rather than diffing instance-by-instance. Unlike the VLAN database, MST regions never fragment across multiple Subsets (real region configs are tiny), so `sendMstSummaryAndSubset` always sends exactly one summary+subset pair; sent on local change, on trunk link-up/mode-change, on an Advertisement Request reply, and on the periodic 300s timer — all gated on `version === 3`, so a v1/v2 domain (still VTP's overwhelming default) never emits an MST-database frame at all, confirmed by `vtp-v3-mst-database.test.ts`'s last case. Deliberately out of scope, per the PRD: Private VLAN association propagation (blocked on `docs/PRD-VLAN.md §2.1.2`, no Private VLAN concept exists anywhere yet) and any Huawei equivalent (VTP is confirmed Cisco-proprietary, `vtp/` has no Huawei wiring at all, by design).
  - `vtp/types.ts`'s `hashPassword()` (`docs/PRD-VTP.md` Phase 3) used to be `md5Hex(\`${domain}|${password}\`)` — a plausible-looking but invented construction, never checked against anything real. Replaced with the actual byte layout: Wireshark's `packet-vtp.c` dissector documents the Summary Advertisement's Management Domain as a fixed 32-byte zero-padded field followed by a 4-byte big-endian Configuration Revision Number, and the Yersinia VTP packet-crafting tool's `vtp_generate_md5()` (real source, since a forging tool has to reproduce what a real switch accepts) documents the digest itself as `MD5(MD5(password) ‖ <domain+revision struct> ‖ MD5(password))` — the password's own digest bookending the struct on both sides, then hashed again. `hashPassword(domain, password, revision)` now builds exactly that (new optional 3rd `revision` param, defaulting to 0 so old 2-arg call sites keep compiling); every `VtpAgent` call site was updated to pass the revision the frame actually advertises — the VLAN database's `config.revision` for ordinary summary/subset/request frames and primary-claims, and `payload.revision` (the sender's claimed revision, not the receiver's own) when verifying an incoming frame's `passwordHash`. Confirmed by the new `tcpdump-vtp-frame-capture.test.ts` (the VTP counterpart to `tcpdump-byte-slice-vlan-filters.test.ts`): the 32-byte domain truncation/padding boundary, the revision field's big-endianness, and Cisco's own documented real-world behavior that the same domain+password produce a different digest per revision, are all pinned by test. Also fixed `vtp-md5-password.test.ts`'s first case, which had asserted the *old* `domain|password` string-concat construction directly — genuinely broken by this change, not a pre-existing false assumption to preserve. Honestly scoped, not literally "byte-exact" against a real capture: Yersinia's real struct also includes `version`, `code`, and the VLAN database bytes, none of which are included here, because no byte-serialization for a `VtpVlanEntry` or an IPv4 "updater identity" exists anywhere else in this codebase to reuse — inventing one to complete the digest would mean stacking a second unverified encoding on top of an already-uncertain one, when the PRD's own stated scope for this phase was specifically domain/revision/password.

- **Telnet toward a router VTY is a real session, end to end.** Since `PRD-VTY-Transport.md` P5, `Router`'s TCP/23 listener runs a genuine `TelnetServerHandler` (`src/network/protocols/telnet/` — RFC 854 IAC framing, RFC 855 option negotiation, IOS-shaped opening offer, RFC 1091 terminal-type exchange, login dialog, server-driven echo that never echoes a password, `AYT`/`IP`/`BRK`, `exec-timeout` hang-up). It reuses `Router.createVtyShell()`, `vtyAdmissionVerdict('telnet', …)` and the `SshSessionRegistry` line pool, so a telnet session gets the same per-session EXEC mode, the same ACL/quiet-mode/pool refusals and the same `show users` line as an SSH one (`display users` shows `TEL` vs `SSH` from the local port). `TelnetClientSession` is the client half. All four terminals — bash (`LinuxTerminalSession.enterTelnet`), `cmd` (`WindowsTerminalSession.enterTelnet`) and the Cisco/Huawei CLIs (`CLITerminalSession.enterTelnet`, which keeps a single `telnetSubShell` since a CLI terminal has no general sub-shell stack) — intercept `telnet` before it reaches the device shell and push a `TelnetInteractiveSubShell` over one real socket, via the shared `terminal/subshells/telnetLaunch.ts`. There is deliberately **no pre-flight probe**: the connect verdict comes from that one connection, so `Trying …` / `Connection refused` are facts of the wire. **The wording is per-platform** (`terminal/subshells/telnetDialect.ts`): `launchTelnet` used to print the BSD client's transcript everywhere, so a Cisco router answered a refused connection with `telnet: connect to address 10.0.0.1: Connection refused` — the Linux words, on an IOS prompt, while the scripted paths said `% Connection refused by remote host` all along. Each `TelnetDialect` (`BSD_TELNET`/`IOS_TELNET`/`VRP_TELNET`/`WINDOWS_TELNET`) is populated from those existing scripted implementations rather than written afresh, so the interactive and scripted halves cannot say different things about the same event; `CLITerminalSession.getTelnetDialect()` is the per-vendor hook. One deliberate cosmetic divergence: IOS puts `Open` on the same line as `Trying x ...` and this transcript is line-based, so it lands on the next line. `Router` gained a `tcpConnect` mirroring `EndHost`'s, which it lacked — an outbound client on a router CLI previously had no way to reach the wire at all. What is **not** rewired: the non-interactive/scripted paths (`LinuxCommandExecutor.runTelnetClient`, `WindowsPC.cmdTelnet`, `CiscoShellBase.runOutboundTelnet`, `HuaweiVRPShell.runOutboundTelnet`) still print their banner and synthesise capture frames (`emitTelnetWire`); they are only reachable when the command does not go through a terminal (a pipe, a script), because `LinuxCommandExecutor.dispatch()` is synchronous while the server answers through `TelnetSession`'s promise chain.
- **A fault under an ESTABLISHED ssh session is read, never provoked.** `sessionLiveness.ts`'s `establishedSessionLiveness(session, sourceDevice, peerHost)` is what `LinuxTerminalSession.connectAndEnterSsh` and `sshLauncher.finalisePendingAuth` hand to the interactive sub-shell, and it combines two facts that answer different questions: `transportLiveness` reads the socket this side holds — which knows when THIS link drops — and `peerLiveness` reads the path, which is the only thing that notices a cable pulled at the FAR end of a switch, an intermediate device losing power, or the peer being switched off. Using the socket alone (the previous behaviour) left a session happily serving a machine that was no longer on the network; the client only learns any of this on its next write, which is exactly when the check runs, so nothing polls and no fresh handshake is ever opened (opening one would make the remote log an accept/close pair per command — the §V30 regression). Deliberately **not** part of liveness: whether the peer's sshd is still running. Debian's `ssh.service` is `KillMode=process`, so `systemctl stop ssh` kills the listener and leaves every established session alone — that is *why* reconfiguring sshd over ssh is survivable, and treating a stopped daemon as a dead session would be wrong rather than stricter. The same rule holds for every vendor's own way of closing the door (Cisco `transport input none`, Huawei `undo stelnet server enable`): new connections are refused, the open session is untouched.
- **A device logs the connections it ACCEPTED, not the ones it dialled.** `tcp.connection.opened` always carried a `passive` flag and both log projections filtered on it; `tcp.connection.closed` carried none, so neither could tell the two apart and both logged every close as `Connection from <peer> closed (<reason>)` — including the close of a socket the device had opened itself. The visible consequence was a server-shaped line on a CLIENT's console: a router whose outbound `telnet` had just been refused printed `%SYS-6-INFORMATIONAL: Connection from 10.0.0.1:23 closed (rst)`, as if somebody had connected *to* it, right under the refusal; on Linux the same close was tagged `sshd`, a daemon that had accepted nothing. Fixed by adding `passive` to the closed payload (`network/tcp/events.ts`, stamped from `socket.passive` which already existed) and filtering on it in `LoggingConfig`'s bus subscription and `PortActivityLogProjection.onTcpConnectionClosed`. Related and fixed in the same pass: `LinuxTerminalSession.connectAndEnterSsh` rendered the session's `CONNECTION_REFUSED` as `No route to host`, which sends an operator to check cables when the path is fine and the far end simply said no (quiet-mode, `transport input none`, a stopped daemon) — unreachability is already decided *before* any session by the liveness probe, so reaching that branch can only mean a genuine refusal.
- **A REFUSAL and a SILENCE are two diagnoses, and the whole stack collapsed them into one.** The distinction already existed one layer down and was thrown away: `TcpStack.connectOutcome` answers `'refused'` when the peer sends a RST or an ICMP unreachable and `'timeout'` when nothing comes back (a silent DROP, no route) — its own comment says so — but `EndHost.tcpConnect`/`Router.tcpConnect` resolved a bare `null` carrying no reason, so `SshSession.connect` called both `CONNECTION_REFUSED` and every client wrote `Connection refused` for a packet that was never answered. This is the costliest diagnosis to get backwards (a firewall that REJECTS gives "refused" and sends you to look at the service; one that DROPS gives "timed out" and sends you to look at a filtering rule), and it is exactly what a FortiGate's `allowaccess` does — it drops. `TcpDialFailure` (`tcp/types.ts`) + `dialTcp` (`tcp/dial.ts`) now carry the reason; `tcpConnect` is a thin wrapper over `tcpDial` on **both** `EndHost` and `Router`, which had a verbatim copy of the same dial loop — one implementation, so the two cannot drift. `SshError` gained `CONNECTION_TIMEOUT`; `TelnetDialect` gained `timedOut()` so **each platform says it in its own words** (IOS `% Connection timed out; remote host not responding`, BSD `telnet: connect to address <ip>: Connection timed out`, while VRP and Windows keep ONE wording for both causes because the real boxes do). Two things surfaced while measuring, and both corrected a claim of mine rather than the code: the promise does **not** hang forever on a dropped SYN — it settles at ~63 s, the RFC 6298 backoff with `TCP_MAX_RETRANSMITS = 5`, which no real-clock test ever reaches; and `SftpSession` still rendered `CONNECTION_REFUSED` as `No route to host`, the very defect the entry above says was fixed for `connectAndEnterSsh` — the SFTP copy had survived. Fixed in the same pass: the dial API takes **domain types, not primitives** — `dialTcp(stack, destination: IPAddress, port: PortNumber)` — using the project's existing `core/ports/PortNumber` (RFC 6335, already behind the Linux `ports/ServiceSocketServer` and the Windows service manager) rather than a new type, and parsing at the boundary is what makes `telnet <host> 99999` refused instead of dialled.
- **`ssh -L`/`-R` (the `executeCommand`/`LinuxSshClient.ts` path — the one every vendor's outbound `ssh` actually goes through, `docs/PRD-Port-Forwarding.md` Phase 8) now relay real bytes, not just `ss`/`netstat` visibility.** Two independent, non-interoperating forwarding stacks exist in this codebase — this one, and the interactive-terminal path (`LinuxTerminalSession.ts` + `SshLocalForwarder`/`SshRemoteForwarder`/`SshDynamicForwarder`), entangled with a separately-tracked "unify the two SSH stacks" effort and deliberately left untouched here. Before this fix, `SshForwardingTable.open()` only called `SocketTable.bind()`; a real connection to the forward's listen port never reached anything. Fixed: `SshForwardingTable` now takes this machine's own `TcpStack` (wired from `LinuxCommandExecutor.setSocketTable()` via the already-existing `localDevice` reference) and `open()` takes a `dialStack` — the TUNNEL's OTHER end, not the machine owning the listener: `-L`/`-D` dial out from the SSH *server*, `-R` dials out from the SSH *client*, matching real OpenSSH exactly. `LinuxSshClient.ts`'s `setupPortForwards()` supplies `machine.getTcpStack()` (server) for `-L`/`-D` and a narrow cast of `opts.sourceDevice` (client) for `-R`. `-D` itself stays unwired — this path has no SOCKS5 destination parsing to dial anything against (a separate, larger gap than "give it a channel"). Unlike Phases 5-6's NAT rewrites, no address is ever rewritten here — two ordinary, independent TCP connections either side of the relay — so there's no NAT-shaped reply-path asymmetry: both legs genuinely reach `established`. **Writing the test surfaced a second, larger, independent gap**: `TcpStack` had no loopback delivery path at all — `resolveEgress()` simply failed for `127.0.0.1`/`::1`, for any consumer, not just SSH — and since `-L`/`-R` bind to `127.0.0.1` by default (real OpenSSH's own default), the relay above would have had no reachable listener for the ordinary, no-explicit-bind-address invocation. Fixed in `resolveEgress`/`resolveEgress6`/`shipSegment` (`TcpStack.ts`): a loopback destination is now delivered directly in-process, never touching a wire — mirroring `EndHost.sendUdpDatagram`'s own established loopback shortcut for UDP. The fix is purely additive (a new early-return branch); the existing non-loopback path, and every consumer of it, is untouched, and the addresses in question already failed outright before the fix, so nothing could have depended on the old behavior — confirmed by a full `tcp-*.test.ts` pass (10 files, 64 tests) green both before and after. `ssh-forwarding-real-relay.test.ts` (3 cases — `-L` with an explicit check that the outbound leg comes from the server, `-R` with the mirror check for the client, and refusal when the real target has no listener) is git-stash discriminated at two levels: the two order-dependent cases fail identically whether all four touched files are reverted together or only `TcpStack.ts` is, isolating the loopback fix from the relay wiring.
- **`docs/PRD-Port-Forwarding.md` Phase 9 reconciled the port-forwarding documentation against what Phases 1-8 actually shipped**, after finding four contradictory sources: `GAP.md` §4.10 still said no ALG existed (untrue — `router/nat/FtpAlg.ts`, shipped under the separate `PRD-FTP-SFTP.md`, is a real FTP ALG; only SIP/NAT64 remain unimplemented, and the `show ip nat statistics` CLI line itself was deliberately left unfixed as a documentation-only pass), `GAP.md` §7.3 undersold the interactive-terminal forwarders' brokenness (its own `nc`-bridge description was itself wrong — `execute()` is never called on that path, so nothing is ever bridged, not even a stub `nc` invocation — now corrected and distinguished from the Phase-8-fixed `executeCommand` path), `docs/PRD-netsh.md`/`docs/PRD-Windows-Server.md`'s "solid" characterization of `portproxy` now notes Phase 7's real relay, and `docs/BRD-SSH-SFTP.md`/`docs/SSH-IMPLEMENTATION-ANALYSIS.md`/`docs/tutoriel-ssh.md` all called `-L`/`-R`/`-D` uniformly "out of scope"/"not modeled" despite §1.11-§1.16 already describing parser/listener support and Phase 8 now giving `-L`/`-R` a real relay on one of the two non-interoperating SSH stacks. `docs/roadmap.md` (generated 2026-03-25) got a top-of-file staleness banner plus a targeted note on its NAT/PAT section, rather than a line-by-line rewrite — it's stale well beyond port-forwarding and a full pass was out of scope here.
- **RSA host keys are what run the SSH server on IOS**, and `Router.hasSshHostKeys()` is the seam. A plain `Router` has no crypto configuration to consult and always returns true; `CiscoRouter` overrides it to read `getSecurityConfig(this).cryptoKeys`, so `crypto key zeroize rsa` genuinely takes SSH down (the router's counterpart of deleting a Linux host's `/etc/ssh/ssh_host_*_key`, `docs/PRD-Pannes.md` §F7.2 — and the classic way to lock yourself out of a box you are reaching over ssh) and `crypto key generate rsa` brings it back, both via `_refreshSshAvailability()`. The gate is applied in **both** places that can bind the listener — `mountSshDaemon()` at construction as well as `syncSshListener()` on every config change — because gating only the latter would leave a fresh router listening while `show crypto key mypubkey rsa` answers `% No RSA key generated.`, and those two must not be able to disagree. The visible consequence, and it is the correct one: a freshly-dropped Cisco router does **not** accept ssh until an operator has run `ip domain-name …` + `crypto key generate rsa` (IOS itself refuses to generate a key without the domain name, which the simulator already modelled). Several test fixtures were configuring only an IP address and relying on the old unconditional bind; they now perform the real setup. **Huawei is symmetric and shares the same seam**: `HuaweiRouter.hasSshHostKeys()` reads `getKeypairService()`, which `display rsa local-key-pair public` already read, so `rsa local-key-pair create` is what actually brings STelnet up and the newly-added `rsa local-key-pair destroy` (the command did not exist — it fell through as unrecognised) takes it down, both calling `_refreshSshAvailability()`. `stelnet server enable` on its own is not sufficient on VRP either, for the same reason it is not on IOS: there is no key to present. Its fixtures were updated the same way.

A "create a table in PDB1, confirm it's absent from PDB2" lab will silently fail. `DataGuardConfiguration.switchover()` likewise just swaps two `role` fields — there is no real redo transport/apply. Don't build pedagogical scenarios that assume real cross-PDB isolation or physical standby replication.
  - DATE columns rendered with no explicit `TO_CHAR` mask (rapport 07, item #48) previously showed either the raw internal `YYYY-MM-DD HH:MM:SS` storage string or, for `SYSDATE`/`FROM DUAL` pseudo-columns specifically, were tagged `VARCHAR2` and never date-formatted at all. Real Oracle defaults every unmasked DATE to `NLS_DATE_FORMAT` (session-scoped, default `DD-MON-RR`, no time-of-day). Fixed: `QueryResultRenderer.renderValue()` now formats any `isDate` column (or bare `instanceof Date` value) through `formatDateWithPattern()` using the session's `nlsDateFormat` (`SQLPlusSession.formatQueryResult` reads it off `session.nlsDateFormat`; `OracleDatabase.execAlterSession` writes it on `ALTER SESSION SET NLS_DATE_FORMAT`); `ScalarFunctionEvaluator`'s `TO_CHAR` falls back to the same session default when called with no format arg, and now runs `coerceDate()` (handles both a genuine `Date` object and a date-string) instead of the old `typeof === 'string'`-only check, which silently fell through to JS's own `Date.prototype.toString()` for a real `Date` value. Pseudo-column type inference (`SYSDATE`/`CURRENT_DATE` → DATE, `SYSTIMESTAMP`/`CURRENT_TIMESTAMP` → TIMESTAMP, previously always `VARCHAR2`) had to be added in two separate places — `OracleExecutor.expandSelectItems` (table-based `SELECT`) and `executeSelectFromDual` (a wholly separate `FROM DUAL` pipeline that never calls `expandSelectItems`) — since fixing only the former left `SELECT SYSDATE FROM DUAL` still showing a full timestamp. Also added real `RR` century-rollover semantics (`resolveRRYear` in `dateSupport.ts`) alongside the pre-existing `YY` handling, for both formatting and `TO_DATE` parsing. Not attempted: PL/SQL-block `TO_CHAR` (`functions/conversionFunctions.ts`, a separate implementation reached only from inside `BEGIN...END` via a `SqlFunctionContext` that doesn't carry clean session access) still ignores `NLS_DATE_FORMAT` and is a smaller, separate, still-open gap.
  - `SELECT … FOR UPDATE` row-level locking (rapport 07, item #49): `LockManager.rowLocks` (`lock/LockManager.ts`) genuinely tracks which session owns which row, and `NOWAIT`/`SKIP LOCKED` were already correctly wired in `OracleExecutor.lockForUpdateRows()` — but a *plain* `FOR UPDATE` (no wait clause) or `FOR UPDATE WAIT n` against a row another session already held just fell through to `out.push(row)` and silently handed over the row as if the lock had been granted, without ever calling `acquireRowLock`. Two sessions could each believe they held the same row's lock — the core mutual-exclusion guarantee FOR UPDATE exists for was broken exactly when no `NOWAIT` was written. Real Oracle instead blocks the statement (indefinitely for plain `FOR UPDATE`, up to `n` seconds for `WAIT n`) until the holder commits/rolls back, but `OracleExecutor`/`OracleDatabase`/`SQLPlusSession`/`SqlPlusSubShell` are a fully synchronous call chain with no per-statement suspend/resume concept — genuine blocking would need a promise-based wait queue in `LockManager` threaded through that whole chain as `async`, which `ISubShell.processLine`'s `SubShellResult | Promise<SubShellResult>` signature and `interruptForeground()` hook (`terminal/subshells/ISubShell.ts`) already anticipate structurally (per its doc comment, another subshell already returns async), but which touches the single synchronous `OracleExecutor.execute()` core shared by every statement type (DDL, DML, PL/SQL, triggers, scheduler jobs) — a cross-cutting refactor, not a bounded fix. Fixed the bounded half instead: a plain `FOR UPDATE` or `WAIT n` against an already-held row now denies immediately (`ORA-00054`/`ORA-30006` respectively) rather than silently granting a second, phantom lock — trading "hangs forever" for "fails fast," which is honest given the architectural constraint and strictly safer than the previous silent double-grant. `LockManager.lockTable()` (TM/table locks, not row locks) has the identical "record a fake wait, never actually suspend the caller" pattern — tracked separately as item #50, not touched here.
  - TM (table) lock enforcement for ordinary DML (rapport 07, item #50): `LockActor` used to acquire a DML statement's TM lock reactively, off the `oracle.dml.executed` event — which only fires *after* `OracleExecutor.execute()` has already run the INSERT/UPDATE/DELETE against storage (`emitForStatement`/`emitDml` are called post-execution). The lock therefore never protected anything; it was pure `V$LOCK`/`DBA_DML_LOCKS` bookkeeping applied after the fact, and `LockManager.acquireDmlLock`'s catch swallowed everything but `DeadlockError` on top of that. A session holding an explicit `LOCK TABLE t IN EXCLUSIVE MODE` (or any stronger mode) could not actually stop another session's plain DML on that table. Fixed: `OracleExecutor.dispatchStatement()` now calls a new `acquireDmlTableLock()` *before* dispatching to `executeInsert`/`executeUpdate`/`executeDelete`, and `LockManager.acquireDmlLock()` denies immediately (`ORA-00054`) on a real conflicting held lock instead of registering `lockTable()`'s usual fake-pending/wait-for-later entry — same "can't block, so fail fast rather than silently let it through" reasoning as item #49, and low blast radius since ordinary DML's own Row-X(3) mode never conflicts with another session's plain DML (only with an explicit stronger `LOCK TABLE`). `LockActor` no longer subscribes to `oracle.dml.executed` at all (release-side subscriptions — commit/rollback/disconnect — are unchanged and still correct). Explicit `LOCK TABLE`'s own fake-pending/`DBA_WAITERS`/`DBA_BLOCKERS`/`V$SESSION.BLOCKING_SESSION` observability (`execLockTable`, still calling `lockTable()` directly) was deliberately left untouched — those views are a deliberately-accepted simplification for that specific statement, not the MAJEUR-rated complaint this item targets. Not attempted: deadlock detection reachable via pure DML (rated MINEUR in the source audit, and structurally still unreachable regardless of acquisition timing since two Row-X(3) locks never conflict with each other in the compatibility matrix — deadlock among plain DML statements requires a modeled conflict path this simulator doesn't have).

### Couches (`src/network/layers/`)

Le modèle TCP/IP du simulateur (`docs/BRD-Modele-TCP-IP.md`, agent
`mandeng`). Avant lui il n'existait **aucune notion de couche** : chaque
protocole réimplémentait sa propre descente jusqu'au câble, et le BRD
mesure la facture — cinq acheminements IPv4 indépendants, soixante-cinq
fichiers écrivant directement sur le fil. Chaque phase est livrable
seule et **ne change aucune sémantique protocolaire** : un moteur qui
émettait un paquet correct émet le même après migration.

- `link/LinkLayer.ts` (phase 1, complète) — la classification de la
  destination, la réception, et l'émission. Les dix répertoires de
  couche lien sont déclarés migrés ; des cas structurels échouent en
  NOMMANT tout répertoire migré qui appellerait encore `sendFrame` ou
  poserait un `srcMAC:` à la main.
- `internet/InternetLayer.ts` (phase 2, incrément 1) — **la règle du TTL
  vit en un seul lieu**. `decrementForForwarding` décrémente, décide de
  l'expiration et recalcule la somme de contrôle d'en-tête ; les cinq
  corps que le BRD avait comptés la lisent (`Router.forwardPacket`,
  `Router.forwardMulticast`, `EndHost.forwardIPv4`,
  `SwitchSvi.forwardIpPacket`, l'étape du pare-feu), chacun gardant ce
  qui lui est propre — son journal, son compteur, et la façon dont il
  annonce l'expiration. **Ce lot ne change aucun comportement, et c'est
  vérifié plutôt qu'espéré** : j'avais d'abord lu `SwitchSvi` comme
  décrémentant sans garde, donc comme émettant des paquets à TTL 0 ; sa
  garde est en tête de `forwardIpPacket`, écrite `ttl <= 1` AVANT le
  décrément là où le routeur écrit `ttl - 1 <= 0` APRÈS — deux
  formulations équivalentes. Les cinq sites étaient d'accord ; la
  déduplication est donc pure, et la sonde le dit dans son en-tête.
  **Incrément 2** : la CLASSE d'une destination IPv4 (`limited-broadcast`,
  `link-local-multicast`, `multicast`, `unicast`) se décide au même
  endroit. Le routeur redécoupait le bloc à la main
  (`destOctets[0] >= 224 && <= 239`), l'hôte appelait `isMulticastIpv4`
  pour la même question, le commutateur en portait une **cinquième**
  écriture dans son filtrage IGMP snooping — bornes du bloc puis
  exclusion du lien-local par `isReservedMulticast`, c'est-à-dire un même
  prédicat répondu deux fois de suite — et `TcpdumpFilter.isMulticastIp`
  recopiait `isMulticastIpv4` mot pour mot. Seul le routeur distinguait
  le multicast **lien-local** (224.0.0.0/24, que la RFC 1112 interdit
  d'acheminer) du multicast routable ; l'hôte les confondait, ce qui ne
  se voyait pas parce qu'un hôte n'achemine pas. **La mesure a imposé la
  PORTÉE du garde-fou** : passé sur tout `devices/`, il attrapait trois
  fichiers qui ne sont pas des acheminements et qui ont RAISON d'écrire
  ces bornes — `CiscoDhcpCommands` et `CiscoRoutingProtoCommands`
  refusent un argument non unicast (`o[0] === 0 || o[0] >= 224`,
  `first > 0 && first < 224 && first !== 127`), c'est-à-dire une
  grammaire d'ARGUMENT et non une classe de destination : 0 et 127 en
  font partie, et 240.0.0.1 est unicast pour la couche. Les fondre aurait
  été la fausse réutilisation que le BRD interdit ; le garde-fou porte
  donc sur les fichiers qui lisent la destination d'un VRAI paquet.
  **Incrément 3** : un pare-feu ROUTÉ n'accepte que ce qui lui est
  adressé. `Firewall.handleFrame` n'avait AUCUN filtre de couche lien —
  une trame portant une adresse MAC de destination étrangère, injectée
  sur un FortiGate en mode `nat`, était traitée exactement comme en mode
  `transparent` : les deux modes répondaient la même chose à une question
  dont ils SONT la différence. Le filtre lit `LinkLayer.deliver` — la
  règle existante, celle de l'hôte et du routeur, pas une seconde — et le
  mode transparent le court-circuite, un VDOM transparent étant un pont de
  niveau 2 qui doit accepter ce qu'il achemine. **Le filtre a révélé deux
  défauts indépendants que son absence rendait invisibles** : une grappe
  FGCP n'avait pas d'adresse MAC VIRTUELLE — la vraie formule est
  `<préfixe>:<group-id % 256>:<vcluster + index>`, où le préfixe dépend de
  la tranche du group-id (`00:09:0f:09` pour 0-255, puis `e0:23:ff:fc/fd/fe`)
  et le décalage du cluster virtuel vaut 0x00 ou 0x20 ; elle est posée sur
  toutes les interfaces SAUF le battement de cœur, et c'est elle qui rend
  un basculement invisible au voisinage dont le cache ARP reste valide ;
  puis, une fois l'adresse partagée, le subordonné émettait des
  sollicitations de voisin IPv6 depuis cette même adresse, si bien que le
  commutateur voisin réapprenait l'adresse virtuelle sur le port du
  SECONDAIRE — un subordonné a-p n'émet pas sur ses interfaces de
  données, pendant exact de `forwardsTransit()` pour la moitié TRANSIT du
  même fait, posé au seul point d'émission (`sendFrame`).
  **Incrément 4** : une diffusion dirigée explose ou tombe (RFC 2644,
  BCP 34). `ip directed-broadcast` était accepté, rangé sur le port et
  rendu par `show running-config`, et `isDirectedBroadcastEnabled()`
  n'avait qu'UN appelant — ce rendu ; aucun plan de données ne le lisait,
  si bien que `ping -b` rendait `100% packet loss` AVEC comme SANS la
  commande. Le défaut par défaut étant le bon, l'inertie était invisible :
  le paquet tombait, mais parce que le routeur cherchait à résoudre
  192.168.20.255 en ARP, pas parce qu'une règle en avait décidé — et cet
  ARP FUYAIT sur le sous-réseau cible. La commande Cisco « affects only
  the final transmission of the directed broadcast on its ultimate
  destination subnet » : ce n'est pas une barrière générale
  d'acheminement, seul le dernier routeur, directement connecté à la
  cible, explose en diffusion physique ou jette — d'où sa place dans la
  décision livrer-ici / faire-suivre / jeter et non dans `forwardPacket`.
  `isDirectedBroadcast` vit dans la couche et réutilise
  `IPAddress.isBroadcastFor`. **Ce que la mesure a corrigé** : un cas
  attendait que la cible RÉPONDE, et il avait tort — un vrai Linux ignore
  un echo adressé à une diffusion (`icmp_echo_ignore_broadcasts` vaut 1),
  qui est la contre-mesure Smurf que la RFC 2644 complète côté routeur ;
  l'observable est la LIVRAISON, pas la réponse.
  **Incrément 5** : une erreur ICMP ne répond pas à n'importe quoi.
  `mayGenerateICMPError` (RFC 1122 §3.2.2) existait et était juste, lue
  par `Router`, `Firewall` et `EndHost` ; `SwitchSvi` ne l'appelait NULLE
  PART, et mesuré sur un Catalyst à deux SVI il émettait une erreur en
  réponse à une erreur ICMP, à un paquet adressé à 239.1.1.1 et à un
  fragment non initial — trois interdits sur trois. Quatrième écriture
  d'un même fait, et encore une fois c'est celle qui a oublié la règle
  qui est la plus permissive ; le cas du groupe fait du commutateur un
  amplificateur Smurf, un incrément après la moitié routeur de la même
  contre-mesure. Fermés avec : `core/IcmpErrors.ts` DÉLÈGUE à ses
  appelants le contrôle de la diffusion DIRIGÉE et aucun des trois ne le
  faisait (faisable seulement depuis que l'incrément 4 a posé
  `isDirectedBroadcast`), et les DEUX émetteurs quasi identiques du SVI —
  ne différant que par le type et le code, aucun ne lisant
  `buildICMPError` — n'en font plus qu'un. **La portée est mesurée** :
  `Router` est déjà couvert par l'incrément 4, et `EndHost` émet zéro
  erreur sur une diffusion dirigée, attesté par un TÉMOIN unicast monté
  dans le même laboratoire qui en émet exactement une — sans lui, un
  laboratoire mal bâti et une absence de défaut seraient indiscernables.
  **Incrément 6** : la somme de contrôle d'en-tête est VÉRIFIÉE. Même
  forme, un cran plus bas — `verifyIPv4Checksum` existe dans
  `core/types.ts`, `Router` (qui compte `ipInHdrErrors`) et `EndHost`
  l'appellent, `SwitchSvi` et `Firewall` ne l'appelaient nulle part, et un
  datagramme portant `headerChecksum = 0x1234` traversait les deux
  jusqu'à l'hôte de destination. Le champ était ÉCRIT par trente-huit
  sites et LU par deux. La fonction n'est délibérément PAS déplacée dans
  `layers/internet/` : elle est déjà l'unique implantation partagée, et la
  déménager churnerait trente-huit sites d'appel sans rien dédupliquer —
  la règle de réutilisation demande de l'APPELER. Le silence est la règle
  de la RFC et non une facilité : répondre par une erreur ICMP à un
  en-tête corrompu répondrait à une victime choisie par l'erreur, l'adresse
  source étant elle-même suspecte.
  **Incrément 7** : les QUATRE contrôles d'en-tête, une seule écriture.
  Le bloc « Phase B » du routeur porte somme, version, IHL et longueur
  totale, en quatre `if` qui répètent le même geste (compteur, journal,
  retour) ; l'hôte, le commutateur L3 et le pare-feu n'en avaient qu'UN,
  la somme. Mesuré : `version = 6` dans une trame IPv4, `ihl = 2` et
  `totalLength = 4` — chacun avec une somme RECALCULÉE pour que seul le
  champ visé soit en cause — traversaient les deux, six paquets livrés
  sur six. `ipv4HeaderProblem` rend la RAISON et non un booléen, le
  routeur comptant `ipInHdrErrors` et journalisant un message par
  contrôle ; l'ORDRE est celui du routeur et il compte, la somme d'abord,
  un en-tête dont la somme est fausse n'étant pas lisible.

- `layers/transport/` (phase 4, incréments 1-3) — **UDP a un lieu, et le
  démultiplexage a une règle**. `L4Checksum.ts`/`UdpChecksum.ts` (inc. 1)
  ont sorti la somme de contrôle de `tcp/types.ts`. `EphemeralPorts.ts`
  et `UdpPortTable.ts` (inc. 3) ferment deux duplications mesurées :
  `ControlPlaneUdpEndpoint.allocateEphemeralPort` était la copie mot pour
  mot de `SocketTable.allocateEphemeralPort` — même algorithme (256
  tirages puis balayage linéaire), même message `EADDRINUSE`, et ses
  propres constantes 49152/65535 codées en dur là où l'autre les importe
  de `WellKnownPorts` ; les deux lisent maintenant la même fonction. Une
  table de ports UDP nomme le PROPRIÉTAIRE de chaque liaison
  (`ownerOf`), ce que le paramètre `owner` de `udpBind` déclarait déjà et
  que l'implémentation JETAIT.
  - **Un routeur cesse d'AVALER le trafic de transit.**
    `CiscoRouter.processIPv4` et `HuaweiRouter.processIPv4`
    interceptaient l'UDP de leurs agents **avant** `super.processIPv4`,
    donc avant la décision « pour nous ou transit » que la base prend
    pourtant correctement. Mesuré sur `L — R1 — R` : un datagramme de
    bout en bout sur 161 (SNMP), 123 (NTP), 1812 (RADIUS), 3784 (BFD) ou
    1985 (HSRP) n'arrivait **jamais** — le routeur le donnait à son propre
    agent, si bien qu'un poste ne pouvait interroger aucun de ces
    serveurs à travers un routeur. `Router.receiveControlPlaneUdp` est le
    point d'extension unique, consulté depuis `handleLocalDelivery`, donc
    APRÈS la décision. Rien n'est perdu : HSRP et GLBP arrivent sur
    224.0.0.2 / 224.0.0.102, que la base envoie déjà en remise locale au
    titre du multicast lien-local, et les réponses NTP/SNMP/RADIUS sont
    adressées au routeur lui-même. **Le TÉMOIN a été indispensable** : sa
    première version échouait aussi, parce que le laboratoire oubliait
    `no shutdown` — un labo mal bâti et un défaut auraient été
    indiscernables.
  - **Un port UDP que personne n'écoute se DIT.** RFC 1122 §4.1.3.1 :
    « If a datagram arrives addressed to a UDP port for which there is no
    pending LISTEN call, UDP SHOULD send an ICMP Port Unreachable
    message » ; RFC 1812 §6.1 : « A router that implements UDP MUST be
    compliant […] with the requirements of [INTRO:2] », où `[INTRO:2]`
    est RFC 1122 (vérifié dans la bibliographie du RFC, pas de mémoire).
    Mesuré : un hôte Linux répondait `Destination unreachable … code 3`,
    le routeur et la SVI d'un Catalyst ne répondaient **rien**. Les trois
    répondent désormais, chacun par son propre émetteur mais tous
    derrière le même `mayGenerateICMPError`, donc jamais sur une
    diffusion, un multicast, un fragment ni une erreur ICMP.
  - **Une liaison sur un port déjà possédé est REFUSÉE.** `udpBind(520)`
    rendait `true` sur un routeur où RIP sert déjà 520 : acceptée et
    **inerte**, la chaîne codée en dur passant avant. Les ports du plan de
    contrôle sont DÉCLARÉS une fois (`controlPlaneUdpClaims`) et cette
    déclaration a deux lecteurs qui ne peuvent plus se contredire — le
    répartiteur et le refus de liaison. Fermé avec : `DHCP_SERVER_PORT`
    et `DHCP_CLIENT_PORT` étaient écrits **quatre fois** (Linux, Windows,
    pare-feu, plus deux littéraux nus dans `Router`) ; une déclaration
    dans `WellKnownPorts`, quatre lecteurs. **Le piège que la
    non-régression a attrapé** : conditionner la revendication du port 500
    à l'existence du moteur IPsec paraît plus honnête, mais la carte est
    construite UNE FOIS et mise en cache tandis que `ipsecEngine` naît
    plus tard, à la configuration `crypto` — le port n'était donc jamais
    revendiqué et IKE ne recevait plus rien (7 cas NAT-T, plus 8 par
    ricochet). La revendication est inconditionnelle et c'est le
    RÉCEPTEUR qui lit `this.ipsecEngine?.` à la remise ; règle générale,
    une déclaration mise en cache ne peut pas dépendre d'un moteur créé
    paresseusement. **Non-regression** : `network-v2` entier rend 18 rouges
    dans 5 fichiers, et les cinq sont ANTERIEURS — rejoues contre l'etat
    de la branche avant le chantier, ils donnent exactement les memes 18,
    et ils sont nommes au `TODO.md`. Restent ouverts et inscrits
    au `TODO.md` : `show ip sockets` (la matière est prête, la capture de
    référence n'existe pas — `ntc-templates` porte 139 gabarits
    `cisco_ios` et aucun pour les sockets), et les interceptions IGMP/PIM/
    GRE, qui précèdent encore la même décision mais dont le déplacement
    n'est pas mécanique (un rapport IGMP est adressé au GROUPE).

- **Un bus est PAR MACHINE, et une sonde qui l'oublie ne mesure rien.**
  `Equipment.getBus()` rend un `EventBus` propre a l'equipement (sauf
  `setEventBus`), ce qui est voulu : un evenement de A ne doit jamais
  etre livre sur le bus de B. Trois fichiers de test s'abonnaient au bus
  DEFAUT global et n'observaient donc rien —
  `ospfv3-real-packets` (10 cas : « expected 0 to be greater than 0 »,
  aucun paquet vu alors que l'adjacence se formait), `new-roles-observability`
  (5 cas) — pendant que la convention deja etablie par
  `kerberos-replication-observability` s'abonne, elle, par
  `publisher.getBus()`. Les trois lisent desormais le bus de l'equipement
  qui PUBLIE, et pour DFSR c'est le serveur qui SYNCHRONISE, pas sa cible.
  **La lecon vaut au-dela de ces fichiers** : un `expect(x).toEqual([])`
  sur un bus non branche passe a vide, donc un test d'ISOLATION doit
  toujours porter un temoin qui prouve que quelque chose a bien ete emis.
  `nat-engine-own-bus` en etait l'exemple : son cas vert n'emettait rien
  du tout (il appelait un `emitSignalRefresh?.()` qui n'existe pas) et son
  cas rouge lisait un champ `busOverride` que `NATEngine` n'a jamais porte
  — le moteur range son bus dans un `BusHolder`, et `Router.ts` le lui
  passe correctement. Les deux cas sont refaits sur du TRAFIC REEL : un
  ping traverse le NAT (`0% packet loss` comme temoin), l'evenement parait
  sur le routeur qui traduit, et `show ip nat translations` ne le montre
  que la.

### Event/timing infra (`src/events/`)

`EventBus`, `Scheduler`, `Signal`, `TimerSet`, `waitForEvent` — shared reactive primitives used by protocol actors (OSPF, IPSec, DHCP, BGP, etc.) that model asynchronous, timer-driven behavior.

### Adapters (`src/adapters/`)

Bridges between subsystems, e.g. `OracleFilesystemSync`, `OracleSystemdSync` — keep the Oracle simulation's view of the filesystem/service manager in sync with the host OS simulation.

### State management (`src/store/`)

Single Zustand store (`networkStore.ts`) holds the full topology: devices (`NetworkDeviceUI[]`), connections (`Connection[]`), and UI state. The store bridges `Equipment` instances to React rendering. `topologySerializer.ts` handles save/load of topologies.
- `NetworkCanvas`/`PropertiesPanel` subscribe to the whole store (no per-field selector, see item #52's note above on why that's deliberately not narrowed), so any zustand `set()` anywhere re-renders them and picks up a fresh `getDevices()` snapshot of live `Equipment` state. That's fine for CLI-triggered changes — the CLI action itself is a store-adjacent event — but until fixed (rapport 09, item #56) it meant an autonomous change with no `set()` anywhere in its path never reached the canvas at all: a port going admin-down or carrier-down from a dead-interval timeout, a DHCP lease clearing an interface's IP on expiry, an autonomous SPF recompute reaching the RIB via `RoutingTableSyncActor` — none of these ever call into zustand (`src/network/` never imports the store, confirmed by grep), so the connection/interface data on canvas stayed visually frozen until some unrelated store action happened to fire afterward. Fixed by bridging a small, explicit topic allowlist off the default `EventBus` (`getDefaultEventBus()`, the "OBSERVER bus (Logger/UI/tests)" per its own header comment — already the intended hook-in point, not a repurposing) into a `revision` bump: `port.link.up`/`port.link.down`/`port.config.ip-changed` — exactly the topics behind the two fields `NetworkDeviceUI.interfaces` actually renders (`isUp`, `ipAddress`); DHCP lease grant/renew/expire and static/manual IP changes all funnel through `port.config.ip-changed` already (`Port.configureIP`/`clearIP`), so no separate DHCP-specific subscription was needed. Deliberately NOT `bus.subscribeAll()`: the same bus also carries a `port.frame.*`/`cable.frame.*`/`ospf.packet.*` event per Ethernet frame and a `device.position-changed` per drag-pixel, and reintroducing that volume would undo item #52's re-render fix. The subscription is (re-)established from `getDevices()` itself (cheap reference check against the last-subscribed bus) rather than once at module load, specifically because `setupGlobalState.ts`'s global `beforeEach` nulls the default EventBus before every test (`__setDefaultEventBus(null)`) — a naive one-time subscription would silently go dead against the discarded bus and only ever work in the first test of a file; `canvas-autonomous-events.test.ts`'s "rebridges after the default EventBus is swapped" case covers exactly this. Note this fix is scoped to what's actually rendered today: OSPF neighbor/SPF events, STP role changes, and HSRP/VRRP/GLBP active/standby are real and event-driven but have no corresponding field on `NetworkDeviceUI` to refresh, so they're deliberately not in the allowlist — add them if a future UI surface ever renders that state.

C'est donc une propriete de la PLATEFORME : `EndHost.linkLocalAutoconfigurationEnabled()` rend `false`, `WindowsPC` la surcharge en LISANT cette cle dans son propre registre (defaut vrai), et `DHCPClient` interroge ce port au lieu de regarder un drapeau de ligne de commande. **L'ordre est corrige en meme temps, et il compte** : le repli passe desormais TOUJOURS par `noOffersFallback` — qui essaie le bail enregistre non expire, RFC 2131 §4.4.5, le client garde son adresse jusqu'a expiration — et l'auto-attribution ne vient qu'apres, s'il ne reste rien. **Une adresse de lien-local n'est plus retenue comme `lastKnownLease`** : c'est ce qui produisait le troisieme oddity du transcript, un `DHCPREQUEST for 169.254...` en INIT-REBOOT, c'est-a-dire un client redemandant a un serveur DHCP une adresse qu'aucun serveur n'a donnee. Cinq tests encodaient le defaut comme contrat et sont corriges plutot que le code : trois construisaient un `LinuxPC` SANS aucun serveur et attendaient un bail (ils ont maintenant un vrai routeur qui sert), un attendait l'APIPA apres une coupure alors que le bail etait encore valide (il libere d'abord), un se servait d'`ip addr flush` pour « oublier » un bail que la base de baux gardait (il utilise `dhclient -r`). Limite mesuree et inscrite au `TODO.md` : `dhclient -t N` est accepte et lu par personne — son unique lecteur etait justement la condition qui desactivait l'APIPA — et la livraison synchrone des trames ne laisse rien a mesurer a un delai. `probe-dhclient-sans-serveur.test.ts` (6 cas) est discrimine par `git stash` : 4 tombent avant correctif ; les 2 autres sont nommes dans l'en-tete — le TEMOIN avec serveur, et le cas des mots d'ISC, la branche bavarde ayant toujours ete juste, ce qui est tout le propos.
  - **Ouvrir une topologie remettait le generateur d'adresses a zero, et l'equipement ajoute ensuite recevait celle du routeur.** Signale comme « un bug avec le ping » : depuis un PC a 192.168.10.15 que la liste de controle AUTORISE, quinze reponses arrivent, vingt-huit se perdent, cent vingt-huit se perdent, dix-neuf reviennent — 65 % de perte qu'aucune regle ne decide. L'export du laboratoire portait la reponse : le PC ajoute apres coup avait pour `eth0` `02:00:00:00:00:01`, l'adresse de la `GigabitEthernet0/0` du routeur, c'est-a-dire la PASSERELLE de son LAN ; le commutateur n'a qu'UNE entree par adresse et elle bat entre le port du routeur et celui du PC selon qui a emis en dernier, si bien que tout ce que l'on envoie a sa passerelle part chez le voisin pendant les fenetres ou le voisin a parle. La cause tient a l'ORDRE de deux appels : `NetworkDesigner` appelait `clearAll()` **apres** `importTopology()`, et `clearAll()` appelle `resetCounters()` — il effacait donc le compteur que l'import venait de pousser au-dela de chaque adresse restauree par `MACAddress.reserve`, dont le commentaire decrit exactement le defaut qu'il ne pouvait plus empecher. Le meme appel effacait le compteur de NOMS (d'ou deux « PC1 » et deux « PC2 » dans le fichier de l'utilisateur, et le premier nom l'emporte partout ou l'on cherche un equipement par son nom) et VIDAIT `EquipmentRegistry`, que l'import venait de remplir — mesure : aucun des equipements ouverts n'y figurait, donc toute la topologie etait invisible a ce qui parcourt le registre (collecte de domaine OSPF, `resolveAcrossTransparentDevices`, decouverte DHCP, repli NSS du resolveur, traceroute, capture). Le correctif nomme les deux operations au lieu d'en detourner une : `clearAll` vide le canevas et remet les generateurs a zero ; `replaceTopology` — nouvelle action du magasin, utilisee par Ouvrir et par Importer — demonte l'ANCIEN canevas (cables, extinction, `deregister` equipement par equipement plutot qu'un `clear` global qui emporterait les nouveaux) et installe le nouveau SANS toucher aux generateurs, l'import s'en etant deja charge au bon moment. Deux tours d'ordre INTERNES a l'import sont refermes du meme coup, parce qu'un compteur ne protege que ce qui a ete reserve AVANT qu'on y puise : les adresses et les noms sont desormais reserves en une premiere passe sur tout le fichier, avant la creation du moindre equipement — sans quoi un port que le fichier ne decrit pas garde une adresse generee qu'une adresse restauree plus loin peut doubler — et `createDevice` recoit le nom restaure au lieu d'en tirer un qu'il jette aussitot, ce qui laissait un trou dans la numerotation. `reserveDeviceName` est le pendant exact de `MACAddress.reserve` pour les noms. `probe-mac-apres-ouverture-topologie.test.ts` (8 cas) est discrimine : 5 tombent avant correctif, dont le ping du laboratoire de l'utilisateur (`2 packets transmitted, 0 received, 100% packet loss` avant, `0% packet loss` apres) ; les 3 autres sont nommes dans l'en-tete — le TEMOIN sur canevas neuf, dont c'est l'objet de passer des deux cotes, le cas ou le fichier decrit tous les ports (le tour d'ordre interne n'est atteignable que par un fichier incomplet), et la reserve d'une adresse hors du bloc du generateur.
  - **`systemctl disable` is a REMOVED symlink, and a capture of what exists cannot see a removal.** `captureLinuxFiles` records every file that differs from a pristine VFS, so `systemctl enable`'s `multi-user.target.wants/<unit>` link is captured — but `disable`, which works by deleting it, left no trace at all, and the reopened machine re-created the link at boot and started the service again. `systemctl stop` (not file-backed at all) was lost the same way. A `docs/PRD-Pannes.md`-style lab built on a stopped daemon came back healthy, silently. Fixed with `captureLinuxServices`/`restoreLinuxServices` (`linuxServices: {name, enabled, active}[]`). This one is deliberately **not** a diff, unlike the registry: a machine has ~15 units, so the whole table is readable in the file and needs no baseline to interpret, and the restore applies only what actually differs on the reopened machine. Order matters and is asserted: enablement before activation (`mask` also blocks a start), and the whole block after `restoreLinuxFiles`, because a unit file the lab wrote has to exist before the manager can be asked to enable it. `static` is reported and never set — a unit with no `[Install]` section has no link to make or break.
  - **`sc qc` and `reg query` are two readings of one fact**, and until fixed they could disagree. The projection used to be driven from *outside* the SCM — a `WindowsPC` subscriber on `windows.service.account-changed` plus a one-shot seeding loop at bus attach — so only an account change ever refreshed the key: `sc config <svc> start= disabled` moved the service to DISABLED and left the hive's `Start` at 2 (AUTO_START), on the same machine at the same instant. On a real box that key IS the configuration (it is what the SCM re-reads at boot), so the fix is that `WindowsServiceManager` now writes it itself through the `ServiceRegistrySink` it is handed at construction (`attachRegistrySink`, which also projects every seeded service). Writing from inside is what makes it airtight: a mutation cannot forget to announce itself because there is nothing to announce — `setStartType`, `setAccount`, `createService`, `addService` (role/feature installs) and `deleteService` all go through it, and `deleteService` genuinely removes the key (`PSRegistryProvider.removeServiceKey`), since leaving it behind would have the SCM re-read a service nobody can start. `WindowsPC.syncServiceRegistryKey`, its `_serviceRegistrySyncOff` subscription and the seeding loop are gone. `windows-service-config-is-the-registry.test.ts` pins the round-trip for `sc config start=`/`obj=`, `Set-Service -StartupType`, `sc create`/`sc delete`, and that a refused (non-admin) `sc config` leaves the hive untouched. The serializer's baseline uses the same one call rather than its own loop.

## Déclarer une commande — le socle, pas le trie

**Toute commande NOUVELLE se déclare sur le socle** (`src/cli/`), en
`CommandSpec`, dans une famille sous `src/cli/commands/<famille>/`.
`CommandTrie` est l'ancien moteur : il porte encore l'essentiel du
vocabulaire et la migration est incrémentale, mais on ne lui ajoute plus
rien.

Une famille est une fonction qui rend des `CommandSpec[]` :

```ts
export function maFamille(): CommandSpec[] {
  return [{
    id: 'ip-address-dhcp',
    path: ['ip', 'address', 'dhcp'],
    description: 'IP Address negotiated via DHCP',
    modes: ['config-if', 'config-subif'], minPrivilege: 15,
    run: (session, args) => { … },
  }];
}
```

Ce que le socle apporte et que le trie n'a pas : un seul arbre construit
une fois (le vocabulaire appartient à la PLATEFORME, la session ne porte
que le mode, le privilège et la vue) ; l'abréviation et l'ambiguïté par
le même mécanisme ; un argument **typé et PARSÉ**, donc `ip address
zorglub` refusé au lieu d'accepté ; un gestionnaire qui peut être
asynchrone. Une déclaration en double est refusée au lieu d'écraser.

La famille se branche dans `socleSpecs()` du shell concerné
(`CiscoShellBase`, `CiscoIOSShell`, `CiscoSwitchShell`). Le `session.device`
est le SHELL : les méthodes dont la famille a besoin se déclarent en
interface étroite (`DhcpClientHost`, `TunnelHost`) et le shell les
implémente en déléguant à l'équipement.

**Migrer une PORTE de sous-mode** — une commande qui change de mode
(`interface`, `line`, `vlan`, `router ospf`) : elle se déclare pour TOUS
les modes d'où elle se tape, parce qu'IOS laisse passer d'une interface
à l'autre sans `exit`. Quatre pièges, chacun mesuré :
**(1)** la même commande écrite une fois par mode finit par diverger —
`interface` l'était quatre fois, avec sept écarts, tous du côté du
sous-mode ; **(2)** une place à `alternatives` perd le `leadingOnly` du
trie, donc `CompletionEngine` fait primer une FORME déclarée qui
correspond à la frappe sur les valeurs vivantes qui la prolongent ;
**(3)** un type sans son numéro REMPLISSAIT une place libre, donc `?`
annonçait `<cr>` pour une frappe refusée — chaque type est un mot-clé
avec sa place EXIGÉE (`typesInterfaceEnMotsCles`) ; **(4)** le socle
admet une commande de `config` depuis un sous-mode par HÉRITAGE, ce qui
rouvrait le confinement des vues d'analyseur — `confinerSousVue` le pose
pour les deux moteurs.

`ArgumentSpec.rangeIsAdvisory` — même mot que le trie, même sens : une
plage qui DÉCRIT sans trancher. À poser quand la borne dépend de l'état,
ou quand le gestionnaire refuse déjà dans les mots d'IOS ; sinon la règle
« une plage annoncée est appliquée » remplace le message par un caret.

`argumentFor` n'est JAMAIS consulté pour un chemin `no X` quand `X`
existe : déclarer la place deux fois y range une entrée que personne ne
lit.

**Les shells VRP n'ont pas encore de pont vers le socle** — c'est inscrit
dans `TODO.md`. Tant qu'il n'existe pas, une commande VRP se déclare sur
son trie et l'entrée du registre est mise à jour.

## Conventions worth knowing

- **Search the repository BEFORE writing anything — reuse, never re-implement.** This is the first rule, and it applies to every layer: a protocol, an engine, a codec, a renderer, a value object, a parser, a lookup. Before a single line, grep for what already answers the question; if something does, DELEGATE to it, even when writing a fresh one would be shorter. Two implementations of one question are two answers that eventually disagree, and this repository's history is largely the cost of that: two Windows registries, two SSH stacks, two `service timestamps` parsers, two `flash:` renderers, two NQA engines, two zone lookups. Three traps make the rule easy to break in good faith. **A partial reuse is still a duplication**: reusing a codec and hand-writing the lookup on top of it (`FirewallDnsServer.fromZones` beside `ZoneStore`) reads as reuse and is not. **A different caller is not a reason to fork**: when the existing implementation is bound to a class you cannot extend (`queryDnsOverUdp` on `EndHost`), extract the narrow port and let both callers share it rather than copying the body. **The duplicate is usually the more permissive one**, because the fresh copy only implements the cases its author had in mind — which is why de-duplicating keeps closing real defects rather than merely shortening files. When a genuine reuse is impossible, write down in the commit message and in the PRD which existing thing you looked at and why it could not serve.
- **A domain value is a TYPE, never a primitive.** An IP address is an `IPAddress`, a transport port is a `PortNumber` (`core/ports/PortNumber.ts`, RFC 6335), a MAC is a `MACAddress`, a mask is a `SubnetMask` — in every function signature, not merely in storage. A `string` host and a `number` port push validation to nobody and let a malformed address or an impossible port (`0`, `99999`, `NaN`) travel until something far away misbehaves; the value object parses once, fails fast, and makes the invalid state unrepresentable thereafter. **Parse at the boundary**: the place that reads a CLI argument, a config line or a wire field is the place that converts, so everything downstream receives a value already known good — that is what makes `telnet <host> 99999` a refusal instead of a dial. Existing APIs that still take primitives (`tcpConnect(string, number)` and its many call sites) are legacy: keep them compiling, implement them by parsing and delegating to the typed form, and write anything NEW against the types. Before writing a new value object, **search the whole repository for one that already exists** — `core/ports/` already holds the port system used by Linux services and the Windows service manager, and a second one would be exactly the duplication this project keeps undoing.
- **A duplicate is a defect, and closing it is part of the task — not a follow-up.** Whenever you meet the same fact written twice — two parsers for one grammar, two stores for one setting, two renderers for one view, two tables of the same constants — remove one of them in the same change. Two writings of one fact do not stay equal: they diverge, and the day they do, the machine answers two different things to the same question and nothing says which is right. This repository has paid that bill repeatedly (two Windows registries, two SSH stacks, two `service timestamps` parsers, three ACL grammars), and every entry above that begins "il n'y en a plus qu'une" is one of those bills. So: do not add a second writing, and when you find one, **delete it rather than keep it in sync** — a comment asking the reader to update both is not a fix. If a duplicate genuinely cannot be closed in that change (it is another subsystem, or the two behaviours differ and choosing costs a measurement), say so in the commit message and open a `TODO.md` entry naming both sites; never leave it silent.
- **Code is written in English — always.** Identifiers, types, functions, constants, locals, test names: English, without exception, in every file. Some older code in this repository carries French identifiers; that is legacy, not a pattern to follow or extend. Do not rename it wholesale either — leave it where it is and write English in anything you add or touch.
- **Anything sent between two machines MUST cross the simulated network as real frames — this is mandatory, not a preference.** A command, a file, a login, a query, a reply: if two devices exchange it, it goes through `Port`/`Cable`/`TcpStack` and is countable on the wire. Reaching for the peer's object and calling a method on it (`remote.executeCommand(...)`, `device.fs`, a registry lookup that returns the far-side instance) is the one shortcut this project does not accept, however correct the answer looks — a simulator whose SSH command never leaves the client teaches a network that is not there. Two consequences follow, and both have caught real defects here. First, **the shortcut hides privilege and policy**: `ssh alice@host whoami` answered `root` for as long as the command ran in memory, because the local call had no session and therefore no user. Second, **the test must count frames, and count the RIGHT ones**: a total above zero proves nothing when a real login precedes an unreal command, so measure the DIFFERENCE between the same exchange with and without the payload — that difference is the payload's own traffic, and it was exactly zero. When something genuinely cannot cross the wire yet, say so in the file and in the PRD rather than papering over it with a local call.
- **Do not write comments. This is absolute, and it is the rule most often broken.** No inline `//` explanations, no new `/** */` blocks, no file headers, no section banners, no `// ─── … ───` separators — in any language, in production code and in tests alike. Zero new comment lines per diff is the target, and a diff that adds even one is wrong unless the user asked for it. Say it with the name instead: a function whose name states what it decides needs no sentence above it, and a comment that drifts from the code is worse than no comment. **The reasoning, the measurement, the defect found and the limit accepted go in the COMMIT MESSAGE and in the PRD — never in the source file.** That is where this project keeps its record, and it is why a commit message here runs long while the code it carries runs silent. Existing comments stay; do not add to them. When behaviour that an existing comment describes changes, delete that comment rather than update it — the tests are the record. The abundant commentary in older files is legacy, not a house style to imitate: writing more of it because the neighbours have it is the single most common way this rule gets violated.
- Production builds set `esbuild.keepNames: true` and `build.minify: 'esbuild'` because the simulator dispatches on `instance.constructor.name` (e.g. `=== 'WindowsPC'`) to choose vendor-specific behavior — default minification would break this (see comment in `vite.config.ts`).
- Reactive protocol engines (OSPF, IPSec, DHCP, BGP, routing) follow a consistent shape: `<Protocol>Engine.ts` + `types.ts` + `events.ts` + `observables.ts` + `actors/` built on `src/events/` primitives — follow this pattern when adding a new protocol.
- `@typescript-eslint/no-unused-vars` runs as a **warning** (not disabled — this line
  previously claimed otherwise, which was false), with `^_` ignore patterns for args and
  vars. Treat its warnings as real: in a security engine, a declared-and-never-read field
  is the exact signature of a criterion that is parsed, displayed, and never enforced —
  which is how seven ACL findings were introduced (see `AUDIT-ACL-CISCO.md`).
- **Failure posture — security criteria fail CLOSED.** In any matching engine (ACL, VACL,
  route policy, firewall rule), *a criterion the engine cannot decide must fail the match*.
  Never succeed, never "skip the criterion". An unknown keyword, a missing L4 payload, an
  unbacked clause, an unparsable flag: all make the entry NOT match. Skipping a criterion
  silently makes an entry more permissive than what the operator wrote — a hole in the
  list that nothing in the CLI reveals. `ACLEngine.aclEntryMatches` and `Ipv6AclEngine`
  both state and apply this rule; anything that evaluates rules must too.
- **Never store a criterion you do not evaluate.** If the CLI accepts a keyword, either the
  engine enforces it or the parser rejects it with `% Invalid input detected at '^' marker.`
  Parsing a criterion, rendering it back in `show`/`running-config`, and ignoring it at
  evaluation time is the worst of the three options: it has every appearance of existing
  except the effect.
