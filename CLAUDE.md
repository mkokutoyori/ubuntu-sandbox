# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A browser-based network simulator (Ubuntu Sandbox) built with React + TypeScript. Users drag-and-drop network devices (routers, switches, PCs, servers) onto a canvas, cable them together, and interact via in-browser terminal emulators that simulate Cisco IOS, Huawei VRP, Linux bash, Windows cmd/PowerShell, and Oracle SQL*Plus. The simulation runs entirely client-side — protocols (OSPF, BGP, EIGRP, STP, DHCP, IPSec, etc.), shells, and the Oracle database engine are all reimplemented from scratch in TypeScript.

## Architecture

**Path alias:** `@/` maps to `src/`.

### Network simulation layer (`src/network/`)

Equipment-driven architecture — no central simulator mediator. Devices process and forward frames themselves, peer-to-peer over cabled ports.

- `equipment/Equipment.ts` — abstract base class for all devices; maintains a static `EquipmentRegistry` for topology traversal. Subclasses implement `handleFrame()`.
- `equipment/HostCapabilities.ts` / `equipment/RouterServiceCapabilities.ts` — segregated optional-capability interfaces + accessor functions (`isCredentialAuthenticator(dev)`, `getManagementService(dev)`, `getHsrpAgent(dev)`, …) for reaching a concrete device's methods from code typed against a narrower shared interface (`CiscoDevice`, `ICLIDevice`, raw `Equipment`). Prefer extending these over a fresh inline `dev as unknown as { getXxx?: () => Yyy }` at the call site (rapport 08 audit: reduce unencapsulated casts).
- `hardware/Port.ts`, `hardware/Cable.ts`, `hardware/PortSecurity.ts` — physical layer; Cables connect Ports for direct device-to-device frame delivery.
  - No FCS field exists on `EthernetFrame` (rapport 04, item #45), and adding a bare one would be decorative — there's no byte-level frame encoding to corrupt against. Instead, `Cable` now has a `corruptionRate` knob mirroring the pre-existing `packetLossRate` one (`setCorruptionRate`/`getCorruptionRate`, `CableStats.framesCorrupted`): a "corrupted" frame never reaches the receiver's `handleFrame()` (same observable effect as a real NIC silently discarding a bad-FCS frame) and increments the previously-dead `Port.errorsIn` counter, distinct from generic simulated loss. Also fixed: `Cable.transmit`/`Port.sendFrame`/`receiveFrame` intentionally deliver the *same* frame object end to end (asserted by identity in `hardware.test.ts`, kept that way — cloning every frame would be the hottest path in the simulator for no observed bug), but several **fan-out** call sites were handing that same object to *multiple* destinations instead of a fresh one per destination: `Hub.handleFrame`, `Switch.floodFrame`'s `stripTag`/`stripOuterTag` (returned the input frame unchanged for the common untagged case), `Switch.emitMirror` (SPAN destination shared the real egress frame), and `Router.forwardMulticast` (one `IPv4Packet` object reused as the `payload` of every OIF's frame). Nothing currently mutates a frame/packet in place post-handoff, so this was latent rather than an active bug — but a landmine for the next feature that does. Fixed by giving each fan-out destination its own shallow copy; BGP/IS-IS-style deep immutability (`Object.freeze`, already used elsewhere for config objects) was not applied to the hot data-plane path.
- `core/types.ts` — frame/packet structures (`EthernetFrame`, `IPv4Packet`, `ARPPacket`, `ICMPPacket`, `UDPPacket`, `RIPPacket`), address types (`MACAddress`, `IPAddress`, `SubnetMask`), protocol constants, ID/checksum helpers.
- `core/` also holds shared infra: `Logger.ts` (pub/sub network event log), `RoutingTable.ts`, `PacketQueue.ts`, `SocketTable.ts`, `TcpConnection.ts`, `FilterChain.ts`, `NeighborResolver.ts`, `WellKnownPorts.ts`, `Ipv4Fragmentation.ts` (RFC 791 §3.2 `fragmentIPv4`/`IPv4Reassembler` — used by `Router.forwardPacket` and `EndHost.forwardIPv4` when a datagram crosses onto a smaller-MTU link with DF clear; DF=1 still gets ICMP Fragmentation Needed instead).
- UDP checksum (RFC 768) — `computeUdpChecksum`/`verifyUdpChecksum` live in `tcp/types.ts` (shared L4-checksum module with TCP's `computeTcpChecksum`, despite the filename). `EndHost.sendUdpDatagram` stamps a real checksum; `EndHost.deliverUDP` and `Router`'s self-destined UDP dispatch verify and silently drop a mismatch. Internal protocol agents (RIP, DHCP, IKE, SNMP, …) still build `UDPPacket`s with `checksum: 0` — that's RFC 768's IPv4 "not computed" opt-out and is accepted unconditionally, same as those agents' payloads not being real serialized bytes in the first place.
- `devices/` — concrete device classes (`LinuxPC`, `WindowsPC`, `LinuxServer`, `CiscoRouter`, `HuaweiRouter`, `CiscoSwitch`, `HuaweiSwitch`, `GenericSwitch`, `Hub`, `Router`, `Switch`, `EndHost`). Instantiated via `DeviceFactory.createDevice(type)` (see `core/types.ts` for the `DeviceType` union — note some types like `firewall-*` are currently stubbed as `LinuxPC`).
  - `firewall-cisco`/`firewall-fortinet`/`firewall-paloalto` (rapport 04, item #46) are literal `new LinuxPC(...)` calls (`DeviceFactory.ts`) — no ASA/FortiOS/PAN-OS CLI, no security-level/zone forwarding model, nothing reads the `deviceType` string at runtime beyond hostname prefix and palette icon. This is UI-reachable, not dead code (draggable from the palette today), but already honestly disclosed there: `DevicePalette.tsx` renders an amber "Limited simulation" badge via `isFullyImplemented()` for exactly these types. What a firewall device inherits from `LinuxPC` — `LinuxIptablesManager.ts`'s netfilter engine (real 4-table chain traversal, genuine conntrack NEW/ESTABLISHED/RELATED, working NAT) — is actually more realistic stateful-filtering machinery than `Router.ts`'s own `ACLEngine` (`established` is a bare TCP-flag check, no reflexive ACL, no zone-based firewall concept exists anywhere in the codebase to reuse). The missing piece is purely the vendor CLI/security-model wrapper, and there's zero existing scaffolding for any of the three (no ASA/FortiOS/PAN-OS shell, parser, or test fixture anywhere). Deliberately not attempted: per the audit's own prioritization (`docs/audit/04-equipements-data-plane.md` §5.7 — this item doesn't even make the audit's own "top 10 recommended actions"), and given each vendor's CLI grammar + security model is genuinely distinct (ASA security-levels/object-NAT, FortiOS VDOMs/`config firewall policy`, PAN-OS zones/rulebase) and comparable in scope to the multi-session Huawei-router-CLI or SSH-unification efforts — not a bounded single-session slice. If attempted later, Cisco ASA (extending `Router` like `CiscoRouter`/`HuaweiRouter` do, reusing `ACLEngine`/`NATEngine`) is the best-reuse starting point; a real connection table, twice-NAT, and the other two vendors would remain out of scope even then.
  - `devices/router/` — router subsystems: ACL, NAT, IPv6 data plane, dynamic routing (OSPF/RIP integration), AAA, BFD, DNS, EEM, NetFlow, NHRP, redundancy (HSRP/VRRP/GLBP), policy, management, CLI.
  - `devices/router/policy/{RoutePolicy,IpPrefixList}.ts` (rapport 02, item #44) — `IpPrefixList.evaluate()` was already a real, correct RFC-shaped prefix matcher, just never called from redistribution. `RoutePolicy`/`RoutePolicyNode` had no evaluation logic at all — pure config storage for `display`. Fixed the bounded slice: `RoutePolicy.evaluate()` now matches `if-match ip-prefix` (via `IpPrefixListStore`), `tag`, and `route-type` — the only match kinds with real data on a redistributed route today — and fails a node closed (doesn't match) if it also references `acl`/`community`/`as-path`/`interface`/`ext-community`, since none of those have a backing value to check yet; no match on any node is an implicit deny, like real VRP. Wired into both directions: Huawei RIP's `import-route ... route-policy <name>` (`RIPEngine.advertisableMetric()` via a new `RIPCallbacks.evaluateRoutePolicy` seam) and Huawei OSPF's `filter-policy { <acl> | ip-prefix <name> } { import | export }` (`RouterOSPFIntegration.isFilteredByDistributeList()`, gating both `installRoutes()` for `import` and `originateRedistributedRoutes()` for `export` — the `export`/`out` direction and the `ip-prefix` form of `filter-policy` were previously silently dropped by the CLI parser entirely). Not attempted: `apply`-clause mutation (cost/tag/next-hop rewriting on a permitted route), BGP/IS-IS redistribution (both are separately-tracked dead config — `BGPEngine.redistribute` and `HuaweiRoutingExtras.importedRoutes` are never read by anything), and Cisco's `route-map`/`PolicyRepository` equivalent (stores raw strings, no structured match at all — a larger lift than Huawei's already-structured-but-unused stores).
  - `Router.ts`'s RIB (`private routingTable: RouteEntry[]`) has no separate FIB and no next-hop recursion: `lookupRoute()` (the data-plane forwarding seam) reads the very same live array every protocol integration mutates directly, and it's called on *every* forwarding decision, which in turn calls `dynamicRouting.refresh()` — control-plane recomputation triggered by data-plane packet processing, backwards from a real router's independent timer-driven control plane. There's also no recursive next-hop resolution: every route's next-hop must be on a directly-connected subnet, so a classic recursive static route (`ip route <net> <mask> <off-link-ip>`) or loopback-to-loopback iBGP is accepted by the CLI but never actually resolves/forwards. Real ECMP (ties on prefix/AD/metric round-robin across all tied RIB entries — see `lookupRoute`'s `candidates` array and `RouterOSPFIntegration.installRoutes`'s per-nextHop loop over `OSPFRouteEntry.nextHops[]`) was fixed; full RIB/FIB separation and route recursion were not — both are genuine architectural gaps (rapport 02 audit item #40), not bounded fixes.
  - `devices/host/` — end-host actors/lifecycle/identity/hardware (shared by Linux/Windows hosts).
  - `devices/linux/` — Linux subsystem services: ARP, DNS, cron, firewall/iptables, IP/net commands, process management, logging, scripting.
  - `devices/linux/iam/policy/AccountLockoutPolicy.ts` models every `/etc/security/faillock.conf` key including `unlock_time` (default 600s, matching real Debian/Ubuntu), but until fixed, `unlock_time` was stored/rendered and never actually consulted: once `LinuxUserManager.checkPassword()`'s failure tally reached the `deny` threshold (default 3 — exactly `LinuxInteractionPlanner.MAX_SUDO_ATTEMPTS`, so a single `sudo` invocation with 3 mistyped passwords was enough to trip it), the account stayed locked out **for the rest of the session**, rejecting even the correct password forever after, with no self-service recovery (`faillock --reset` itself needs root, which was now unreachable). Fixed: `LinuxUserAccount.recordFailedLogin()` now stamps `lastFailedLoginAt`; `AccountLockoutPolicy.shouldLockOut()` takes that timestamp and auto-clears the lock once `unlock_time` (or `root_unlock_time` for uid 0) has elapsed, same as real `pam_faillock`; `LinuxUserManager.isAccountLockedOut()` resets the tally to zero once it observes the window has passed. `su`/`passwd` share the same `checkPassword()` gate and are fixed the same way.
  - `devices/linux/iam/fs/AccountDatabaseParser.ts` is the reverse of `LinuxUserAccount.toPasswdLine()`/`toShadowLine()`/`LinuxGroup.toGroupLine()`/`toGshadowLine()`, and it is what makes the account database genuinely file-backed instead of write-only. Before it, the in-memory maps were the sole source of truth and `/etc/passwd` was a rendering of them: `vim /etc/passwd`, `sed -i`, `rm /etc/shadow` or `cp /etc/passwd- /etc/passwd` changed the text and nothing else, so the machine kept behaving as though the edit had never happened — and the next `useradd` silently erased it by re-rendering the whole file from memory. Now `LinuxUserManager` treats the four files as the store and its maps as a cache: `reloadIfChanged()` (called by every read path — `getUser`, `getUserByUid`, `getAllUsers`, `getGroup`, `getGroupByGid`, `getUserGroups`, `checkPassword`) compares the on-disk text against what the manager last wrote or read and re-parses when they differ, so an external edit takes effect on the very next lookup, at the cost of one string compare when nothing changed. `syncToFilesystem()` restamps after writing so the manager never mistakes its own projection for an operator's edit. Four behaviours are deliberate and each is pinned by test: a **duplicated** name resolves to the FIRST line (libc stops at the first match — getting this backwards would let anyone append a line to hijack an existing name); a **malformed** line is skipped without taking the rest of the file down (one typo must not lock everybody out); an account present in `/etc/passwd` with **no `/etc/shadow` line** still exists and simply has no password (that is an inconsistency `pwck` names, not a deleted user); and the **password round-trips** because `passwd` stores the secret as `$6$simulated$<clear>` — a secret that is not in that shape (an opaque hash pasted in from another machine, `*`, `!`) yields no recoverable cleartext, so the account stops authenticating by password, which is the real consequence of hand-editing a hash rather than a parser limitation. Fields no file carries (`lastLoginAt`, the faillock tally, `createdAt`) are carried over from the account of the same name rather than reset, because on a real system they live outside `/etc` too (`/var/log/lastlog`, faillock's tally directory). This is what makes `docs/PRD-Pannes.md` §F7.3/§F7.4 real rather than staged: nothing special-cases "the file is missing" — parsing nothing yields nothing, exactly as NSS does with no source, so `rm /etc/passwd` gives numeric `id`/`ls -l` output and `whoami: cannot find name for user ID 1000`, while `rm /etc/shadow` leaves every identity resolvable and only kills password verification (SSH public-key auth, which never reads shadow, keeps working). Note `nss-systemd(8)`'s synthetic `root`/`nobody` still answer with no `/etc/passwd` at all — that is real behaviour, deliberately preserved, and losing it would be a bug. Two consequences of "the files are the store" that the parser alone does not give you are handled in `LinuxUserManager` itself. **UID/GID allocation scans the live database** rather than a stored cursor: `allocateUid`/`allocateGid` implement shadow-utils' own `find_new_uid()` — highest id already used inside `[MIN, MAX]` plus one, falling back to the lowest free id only once the range is exhausted — so an id an operator added or freed by editing `/etc/passwd` is visible to the very next `useradd`, and the range being full is a real error (`useradd: can't get unique UID …`) instead of an out-of-range id. A forward-only cursor could not see either edit and would eventually hand out an id already in the file; note also that this makes "delete the highest account, then `useradd`" reuse that id (correct, and what real `useradd` does) while a hole in the middle of the range stays unfilled. **`useradd -r` searches the opposite way** — downward from `SYS_UID_MAX`, taking the highest free system id (999, 998, 997…) — because the two ranges are adjacent (…999 | 1000…) and growing them towards each other would have them collide as soon as either filled up; growing them apart preserves the gap, which is why a real Debian box numbers daemons downwards and users upwards. **`/etc/nsswitch.conf` governs this manager too**, not just `getent`: `filesSourceEnabled()` reads the `passwd:`/`group:`/`shadow:`/`gshadow:` lines and a database whose `files` source is switched off reads as empty however intact the file is, so `passwd: systemd` alone makes `id`/`su`/every permission check stop resolving accounts while `/etc/passwd` still lists them — the confusing failure that line exists to cause. `compat` counts as files (the historical spelling), an absent `nsswitch.conf` falls back to glibc's compiled-in default rather than disabling name resolution, and the file's text is part of the reload stamp so editing it takes effect on the next lookup. The chain does not stop at `files` either, and it does not blindly run every source: `walkNssChain()` builds each table by running `nss/chainWalk.ts`'s `startNssWalk()` once per name — the very same walk object `NameServiceSwitch` drives for `getent`/`ping`/the resolver, extracted so the two callers cannot drift (a machine where `getent passwd alice` and `id alice` disagree is worse than one where both are wrong, because nothing in the diagnosis adds up; `nss-chain-is-one-implementation.test.ts` pins both the rule and the agreement). The walk looks each source's outcome up in that source's own action table (`[NOTFOUND=return]`, `[SUCCESS=continue]`, `[UNAVAIL=return]`, `[SUCCESS=merge]`) via `effectiveAction()`, defaults being SUCCESS=return / NOTFOUND=continue / UNAVAIL=continue / TRYAGAIN=continue. **The distinction that actually bites is UNAVAIL vs NOTFOUND**, which is why the chain callback returns `null` rather than an empty map for a source that cannot answer at all: a MISSING `/etc/passwd` makes the files source UNAVAILABLE, while a present file that merely lacks the name is NOTFOUND — so `passwd: files [NOTFOUND=return] systemd` still lets systemd synthesise root once the file is deleted (the `NOTFOUND=return` never fires, because files never got as far as "not found"), whereas `[UNAVAIL=return]` does stop it. Collapsing the two would lock that machine out for good. `[SUCCESS=continue]` lets a later source override an earlier answer (glibc's last-wins) — extracting the walk exposed that the original `NameServiceSwitch` copy returned on any non-`merge` action, which made `continue` behave exactly like `return`; the shared rule distinguishes all three (`return` settles, `merge` combines, `continue` replaces). `[SUCCESS=merge]` unions group member lists, the one database glibc implements it for. What the later sources contribute — for `systemd`, the `root`/`nobody` records `nss-systemd(8)` synthesises precisely so a corrupt or missing `/etc/passwd` does not leave a machine with no root (`SYNTH_PASSWD`/`SYNTH_GROUP` are exported from `SystemdNssSource` so there is one definition, not two that can drift). A name found earlier is never overwritten, matching nss-systemd's own rule that it synthesises those two only when they are not defined by other means, so the `/etc/passwd` entry always wins. The synthetic records carry no secret (`password: '*'`, locked), so `id root` answers on a machine with no `/etc/passwd` while `checkPassword('root', …)` still fails — resolving a name and authenticating it are different questions. Relatedly, root's *own* seeded secret is now written as `$6$simulated$admin` rather than a bare `x`: it used to be the one account the file could not describe (password in memory only), so the first reload silently lost it — if the files are the store, root has to be in them too. One visible consequence, asserted by test rather than papered over: with `/etc/passwd` deleted, `ls -l` shows `root` for a root-owned file (synthesised) and a bare `1000` for a regular user's — both halves are real, and only the regular account actually loses its name.
  - `devices/linux/service/CriticalFiles.ts` (docs/PRD-Pannes.md §6.2, §13) is the single declarative place saying which files a service or a command cannot work without, so that deleting one **actually breaks the feature** rather than merely being reported somewhere. Before it, every config reader in the codebase did `vfs.readFile(path) ?? ''`, which makes "file deleted" indistinguishable from "file empty" — `rm /etc/ssh/sshd_config` had literally no effect. Both halves of that distinction are real behaviour and both are now modelled: a MISSING sshd config is a start-up failure (`/etc/ssh/sshd_config: No such file or directory`), an EMPTY one is legal and starts on built-in defaults, so the check is existence and never emptiness. Wired through the pre-existing `LinuxServiceManager.registerConfigCheck('ssh', …)` seam (the analogue of systemd's `ExecReload=/usr/sbin/sshd -t`), so `systemctl start`/`restart`/`reload` all refuse and the client really gets `Connection refused`. `CriticalFileSet` (`anyOf`/`onAllMissing`) covers host keys, where sshd needs *some* key and does not care which algorithm; requirement order matters and is the daemon's own (config first — it is what names the keys). `LinuxCommand` gained two matching declarative fields, `binaryPath` and `criticalFiles`, so a command's file dependencies live on the command rather than at its call site. For the ~269 commands still living in `LinuxCommandExecutor`'s switch with no `LinuxCommand` object to hang them off, the same data lives in `STANDARD_BIN_PATHS` (moved here from `LinuxCommandExecutor`) and `COMMAND_CRITICAL_FILES`. **The guard-rail is as load-bearing as the feature**, because `checkCommandDependencies` runs on the simulator's hottest path (every command dispatch): only a binary the image actually SHIPS — one `STANDARD_BIN_PATHS` names, and which `seedSetuidBinaries()` therefore laid down at boot — can ever be judged missing, so a shell builtin or a command this build does not provide is untouched and absence can only mean the user deleted it. The two failures are deliberately distinct because they are distinct on a real system: a missing executable is the shell failing to exec (`bash: /bin/ls: No such file or directory`, exit 127), a missing data file is the program itself refusing (`sudo: /etc/sudoers is required`, exit 1). `canonicalBinPath()` exists because the VFS ships the real merged-`/usr` layout (`/bin` → `usr/bin`, `/sbin` → `usr/sbin`) and `resolveInode` follows a symlink in the LAST path component but not an intermediate one — so `exists('/bin/ls')` answers false for a file genuinely present at `/usr/bin/ls`; normalising keeps this module agreeing with the filesystem instead of second-guessing it, and has the side benefit that `rm /bin/ls` and `rm /usr/bin/ls` are treated as what they are, the same file. Note one honest consequence, asserted by test rather than papered over: `sudo` cannot repair its own missing `/etc/sudoers` (the obvious repair is the one thing that no longer works), which is exactly why real admins edit it with `visudo` and never with `rm`.
  - `devices/windows/` — Windows/PowerShell subsystem services: registry, event log, services, pipelines, port-proxy, cmdlets.
  - **A Windows machine has one registry, one event log, one set of network tables**, and `createWindowsPSProviders(pc)` (`src/powershell/providers/WindowsPSProviders.ts`) is where that is decided. `reg`/`netsh` (cmd) and the `*-Item*`/`*-NetIPAddress` cmdlets (PowerShell) are two *interfaces* over one store, not two implementations — `WinRegistryProvider` (`devices/windows/WinRegCommand.ts`) is a narrow port and `WindowsPC.cmdReg` hands it the very `PSRegistryProvider` instance the cmdlets use, so `reg add` then `Get-ItemProperty` sees the value (the path spellings differ, `HKLM\…` vs the `HKLM:\…` drive, exactly as on a real box). The factory's `shared` bag used to default every store to a FRESH detached object, and both production call sites (`WindowsPC.getPowerShellInterpreter`, `PowerShellSubShell`) spelled the same six device fields out by hand to avoid that default — which worked until a third caller forgot, and never worked for tests, which got a PowerShell wired to a private copy of the machine. The defaults are now the device's own fields (`pc.registry`/`pc.eventLog`/`pc.extraIPs`/…), both call sites pass no bag at all, and `shared` survives only for a caller that means to substitute a store. `windows-one-registry-per-machine.test.ts` pins both directions of the cmd↔PowerShell round-trip and the bagless factory. Removed in the same pass: the factory's `shared.scheduledTasks` option and its private `SEEDED_TASKS` seed list — a leftover from before `WindowsScheduledTaskAdapter` was relocated onto the device, duplicating `WindowsPC.scheduledTasks` entry for entry, accepted by the signature and silently ignored by the body.
  - `devices/os/` — cross-platform OS abstractions (`OSProcess`, `OSService`, `OSServiceOrchestrator`, `OSFeatureGate`).
  - `devices/inspection/` — `DeviceStateView` / `EquipmentStateView` for introspecting live device state (used by debug tooling and tests).
  - `devices/shells/` — CLI shell implementations (`CiscoIOSShell`, `HuaweiVRPShell`, `CiscoSwitchShell`, `HuaweiSwitchShell`, `CLIStateMachine`, `CommandTrie`, `PromptBuilder`) implementing `IRouterShell`/`ISwitchShell`.
- **Protocol engines** — each protocol has its own top-level directory with engine, types, events/observables, and (for reactive ones) `actors/`: `ospf/`, `bgp/`, `eigrp/`, `rip/`, `routing/`, `dhcp/`, `ipsec/`, `acl/`, `arp/`, `bfd/`, `cdp/`, `dot1x/`, `dtp/`, `glbp/`, `gre/`, `hsrp/`, `igmp/`, `igmp-snooping/`, `lacp/`, `llmnr/`, `lldp/`, `mdns/`, `netflow/`, `ntp/`, `pim/`, `radius/`, `snmp/`, `stp/`, `syslog/`, `tacacs/`, `tcp/`, `udld/`, `vrrp/`, `vtp/`, `vxlan/`. SSH/SCP/SFTP lives under `protocols/ssh/`.
  - `llmnr/LlmnrAgent.ts` (RFC 4795, UDP/5355 on 224.0.0.252) and `mdns/MdnsAgent.ts` (RFC 6762, UDP/5353 on 224.0.0.251) are real responders/queriers sharing one transport, `dns/transport/MulticastDnsTransport.ts`. A host answers only for the name it owns — its single-label hostname for LLMNR, `<hostname>.local` for mDNS — and stays **silent** otherwise (a NXDOMAIN on a group would speak for the whole link). LLMNR replies unicast to the asker; mDNS replies on the group, except to a one-shot query from an ephemeral source port, which gets a unicast reply with a 10s-capped TTL (§6.7), and announces itself unsolicited at start with the cache-flush bit (§8.3). Wired into `ResolvedService` by systemd's own rule — `.local` goes to mDNS and never to a unicast server (RFC 6762 §3), a single-label name falls back to LLMNR when DNS has nothing — so `resolvectl query`, `getent hosts` and `ping <name>` all reach them; `resolvectl query` names the protocol used (`-- Information acquired via protocol LLMNR/IPv4`), and a link-local answer is never reported as authenticated since nobody signs it. **The global `LLMNR=`/`MulticastDNS=` setting is the default for links, not an independent switch**: a protocol is on as soon as one link allows it, and the global decides only while no link is configured — without that rule `resolvectl llmnr eth0 no` on the only link closed nothing, and `resolvectl mdns eth0 yes` did nothing on a machine with no DNS server. **Name conflict is handled, and the two RFCs diverge there.** LLMNR *signals*: at start the host asks the link for its own name three times (§4.1); an answer means someone else holds it, so it sets the `C` bit in its replies and lets the asker decide — it never renames. mDNS *arbitrates*: it probes three times 250ms apart (§8.1) with an `ANY` question carrying its intended records in the Authority section, and on conflict moves to `alpha-2.local` and re-probes (§9); two hosts probing at once can't rely on each other to answer, so they compare proposed records and the greater one wins (§8.2). While probing, a host does **not** answer for the name — that would assert the ownership it is still verifying. **Header trap, and a real bug this fixed:** LLMNR redefines bit 10 as `C` (Conflict) where DNS has `AA`, and bit 8 as `T` (Tentative) where DNS has `RD`. The responder set `aa: true` on every reply "because an LLMNR responder is authoritative" — so it announced a conflict every time; `llmnrFlagOverrides`/`readLlmnrBits` in `llmnr/types.ts` exist so the aliasing is written down rather than guessed. **Known-answer suppression** (§7.1) is implemented: a querier attaches what it already knows, the responder drops those records and stays fully silent if nothing is left. The threshold is the RFC's — the querier's copy only counts if its TTL exceeds half the TTL *we would have served*, which for a one-shot query is the §6.7-capped 10s, not 120. **DNS-SD** (RFC 6763) lives in `dnssd/`: `DnsSdRegistry` synthesises PTR/SRV/TXT (plus the `_services._dns-sd._udp.local` type enumeration of §9) and `MdnsAgent` answers from it alongside its own address records, attaching the follow-up records as additionals (§12) so one round-trip suffices. Publishing goes through a **unit file**, not a command: `/etc/systemd/dnssd/*.dnssd` (`systemd.dnssd(5)`, `net/DnssdFiles.ts`), same `[Section]` format and same `/etc` › `/run` › `/usr/lib` precedence as networkd's `.network`; an entry missing `Name`/`Type`/`Port` is skipped rather than half-published. This is what gave `resolvectl service` a data source — it was previously declared out of scope for lack of one. Instance names are free-form including dots (§4.1.1), so `parseInstanceName` splits from the end. **Subtypes** (§7.1) answer too: `_printer._sub._http._tcp.local` PTRs point at the very same instance — a subtype narrows discovery, it does not create a second service — and they stay out of the §9 type enumeration. **Service lifecycle** (§8.4, §10.1): a service is announced once the host name is claimed (never before — that would assert both at once), re-announced with cache-flush when it changes, and sent with TTL 0 when withdrawn. `.dnssd` reload is differential rather than clear-and-republish: without diffing, a service deleted from disk would vanish silently and peers would keep believing in it; republishing an unchanged one announces nothing. So this isn't decorative, `MdnsAgent` also *listens* to other hosts' announcements and keeps a passive cache of services heard (`knownServices()`) — that cache is what a TTL 0 empties, and it is what makes a goodbye observable at all. `systemd.dnssd(5)`'s `SubType=`, `Priority=` and `Weight=` are parsed and reach the SRV. Cache entries expire on their announced TTL (§10) — a peer that dies without a goodbye is forgotten rather than believed forever, and a re-announcement pushes the deadline back. Pruning happens on read and on every announcement heard rather than on a per-entry timer: the observable contract (an expired service is never reported) holds, so the expiry event fires *at or after* the deadline, not to the second. The cache reports what was *heard*; `browse()` asks a live question, so after expiry a browse still finds the service — an expired entry is not an absent service. Deliberately out of scope: the IPv6 groups (`FF02::1:3`/`FF02::FB`) — the v6 stack has no arbitrary-group send path — continuous re-querying at 80–95% of TTL (§5.2, needs a long-lived active browse), and the RFC's one-second grace before acting on a goodbye. The §8.2 tiebreak compares sorted A records rather than the RFC's canonical byte-wise form (same ordering for the only records in play here, but a simplification, not the letter). The responder is host-wide while the setting is per-link, so per-link granularity of *responding* is not modelled; per-link granularity of *resolving* is.

  - `vtp/types.ts`'s `hashPassword()` (`docs/PRD-VTP.md` Phase 3) used to be `md5Hex(\`${domain}|${password}\`)` — a plausible-looking but invented construction, never checked against anything real. Replaced with the actual byte layout: Wireshark's `packet-vtp.c` dissector documents the Summary Advertisement's Management Domain as a fixed 32-byte zero-padded field followed by a 4-byte big-endian Configuration Revision Number, and the Yersinia VTP packet-crafting tool's `vtp_generate_md5()` (real source, since a forging tool has to reproduce what a real switch accepts) documents the digest itself as `MD5(MD5(password) ‖ <domain+revision struct> ‖ MD5(password))` — the password's own digest bookending the struct on both sides, then hashed again. `hashPassword(domain, password, revision)` now builds exactly that (new optional 3rd `revision` param, defaulting to 0 so old 2-arg call sites keep compiling); every `VtpAgent` call site was updated to pass the revision the frame actually advertises — the VLAN database's `config.revision` for ordinary summary/subset/request frames and primary-claims, and `payload.revision` (the sender's claimed revision, not the receiver's own) when verifying an incoming frame's `passwordHash`. Confirmed by the new `tcpdump-vtp-frame-capture.test.ts` (the VTP counterpart to `tcpdump-byte-slice-vlan-filters.test.ts`): the 32-byte domain truncation/padding boundary, the revision field's big-endianness, and Cisco's own documented real-world behavior that the same domain+password produce a different digest per revision, are all pinned by test. Honestly scoped, not literally "byte-exact" against a real capture: Yersinia's real struct also includes `version`, `code`, and the VLAN database bytes, none of which are included here, because no byte-serialization for a `VtpVlanEntry` or an IPv4 "updater identity" exists anywhere else in this codebase to reuse — inventing one to complete the digest would mean stacking a second unverified encoding on top of an already-uncertain one, when the PRD's own stated scope for this phase was specifically domain/revision/password.

- **Telnet toward a router VTY is a real session, end to end.** Since `PRD-VTY-Transport.md` P5, `Router`'s TCP/23 listener runs a genuine `TelnetServerHandler` (`src/network/protocols/telnet/` — RFC 854 IAC framing, RFC 855 option negotiation, IOS-shaped opening offer, RFC 1091 terminal-type exchange, login dialog, server-driven echo that never echoes a password, `AYT`/`IP`/`BRK`, `exec-timeout` hang-up). All four terminals — bash (`LinuxTerminalSession.enterTelnet`), `cmd` (`WindowsTerminalSession.enterTelnet`) and the Cisco/Huawei CLIs (`CLITerminalSession.enterTelnet`, which keeps a single `telnetSubShell` since a CLI terminal has no general sub-shell stack) — intercept `telnet` before it reaches the device shell and push a `TelnetInteractiveSubShell` over one real socket, via the shared `terminal/subshells/telnetLaunch.ts`. There is deliberately **no pre-flight probe**: the connect verdict comes from that one connection, so `Trying …` / `Connection refused` are facts of the wire. **The wording is per-platform** (`terminal/subshells/telnetDialect.ts`): `launchTelnet` used to print the BSD client's transcript everywhere, so a Cisco router answered a refused connection with `telnet: connect to address 10.0.0.1: Connection refused` — the Linux words, on an IOS prompt, while the scripted paths said `% Connection refused by remote host` all along. Each `TelnetDialect` (`BSD_TELNET`/`IOS_TELNET`/`VRP_TELNET`/`WINDOWS_TELNET`) is populated from those existing scripted implementations rather than written afresh, so the interactive and scripted halves cannot say different things about the same event; `CLITerminalSession.getTelnetDialect()` is the per-vendor hook. One deliberate cosmetic divergence: IOS puts `Open` on the same line as `Trying x ...` and this transcript is line-based, so it lands on the next line. `Router` gained a `tcpConnect` mirroring `EndHost`'s, which it lacked — an outbound client on a router CLI previously had no way to reach the wire at all. What is **not** rewired: the non-interactive/scripted paths (`LinuxCommandExecutor.runTelnetClient`, `WindowsPC.cmdTelnet`, `CiscoShellBase.runOutboundTelnet`, `HuaweiVRPShell.runOutboundTelnet`) still print their banner and synthesise capture frames (`emitTelnetWire`); they are only reachable when the command does not go through a terminal (a pipe, a script), because `LinuxCommandExecutor.dispatch()` is synchronous while the server answers through `TelnetSession`'s promise chain.
- **A fault under an ESTABLISHED ssh session is read, never provoked.** `sessionLiveness.ts`'s `establishedSessionLiveness(session, sourceDevice, peerHost)` is what `LinuxTerminalSession.connectAndEnterSsh` and `sshLauncher.finalisePendingAuth` hand to the interactive sub-shell, and it combines two facts that answer different questions: `transportLiveness` reads the socket this side holds — which knows when THIS link drops — and `peerLiveness` reads the path, which is the only thing that notices a cable pulled at the FAR end of a switch, an intermediate device losing power, or the peer being switched off. Using the socket alone (the previous behaviour) left a session happily serving a machine that was no longer on the network; the client only learns any of this on its next write, which is exactly when the check runs, so nothing polls and no fresh handshake is ever opened (opening one would make the remote log an accept/close pair per command — the §V30 regression). Deliberately **not** part of liveness: whether the peer's sshd is still running. Debian's `ssh.service` is `KillMode=process`, so `systemctl stop ssh` kills the listener and leaves every established session alone — that is *why* reconfiguring sshd over ssh is survivable, and treating a stopped daemon as a dead session would be wrong rather than stricter. The same rule holds for every vendor's own way of closing the door (Cisco `transport input none`, Huawei `undo stelnet server enable`): new connections are refused, the open session is untouched.
- **A device logs the connections it ACCEPTED, not the ones it dialled.** `tcp.connection.opened` always carried a `passive` flag and both log projections filtered on it; `tcp.connection.closed` carried none, so neither could tell the two apart and both logged every close as `Connection from <peer> closed (<reason>)` — including the close of a socket the device had opened itself. The visible consequence was a server-shaped line on a CLIENT's console: a router whose outbound `telnet` had just been refused printed `%SYS-6-INFORMATIONAL: Connection from 10.0.0.1:23 closed (rst)`, as if somebody had connected *to* it, right under the refusal; on Linux the same close was tagged `sshd`, a daemon that had accepted nothing. Fixed by adding `passive` to the closed payload (`network/tcp/events.ts`, stamped from `socket.passive` which already existed) and filtering on it in `LoggingConfig`'s bus subscription and `PortActivityLogProjection.onTcpConnectionClosed`. Related and fixed in the same pass: `LinuxTerminalSession.connectAndEnterSsh` rendered the session's `CONNECTION_REFUSED` as `No route to host`, which sends an operator to check cables when the path is fine and the far end simply said no (quiet-mode, `transport input none`, a stopped daemon) — unreachability is already decided *before* any session by the liveness probe, so reaching that branch can only mean a genuine refusal.
- **RSA host keys are what run the SSH server on IOS**, and `Router.hasSshHostKeys()` is the seam. A plain `Router` has no crypto configuration to consult and always returns true; `CiscoRouter` overrides it to read `getSecurityConfig(this).cryptoKeys`, so `crypto key zeroize rsa` genuinely takes SSH down (the router's counterpart of deleting a Linux host's `/etc/ssh/ssh_host_*_key`, `docs/PRD-Pannes.md` §F7.2 — and the classic way to lock yourself out of a box you are reaching over ssh) and `crypto key generate rsa` brings it back, both via `_refreshSshAvailability()`. The gate is applied in **both** places that can bind the listener — `mountSshDaemon()` at construction as well as `syncSshListener()` on every config change — because gating only the latter would leave a fresh router listening while `show crypto key mypubkey rsa` answers `% No RSA key generated.`, and those two must not be able to disagree. The visible consequence, and it is the correct one: a freshly-dropped Cisco router does **not** accept ssh until an operator has run `ip domain-name …` + `crypto key generate rsa` (IOS itself refuses to generate a key without the domain name, which the simulator already modelled). Several test fixtures were configuring only an IP address and relying on the old unconditional bind; they now perform the real setup. **Huawei is symmetric and shares the same seam**: `HuaweiRouter.hasSshHostKeys()` reads `getKeypairService()`, which `display rsa local-key-pair public` already read, so `rsa local-key-pair create` is what actually brings STelnet up and the newly-added `rsa local-key-pair destroy` (the command did not exist — it fell through as unrecognised) takes it down, both calling `_refreshSshAvailability()`. `stelnet server enable` on its own is not sufficient on VRP either, for the same reason it is not on IOS: there is no key to present. Its fixtures were updated the same way.


### Database simulation (`src/database/`)

- `engine/` — vendor-agnostic SQL engine scaffolding: `lexer/`, `parser/` (AST), `executor/`, `catalog/`, `storage/`, `types/`.
- `oracle/` — Oracle DBMS engine built on the engine layer: `OracleLexer`/`OracleParser`/`OracleExecutor`/`OracleCatalog`/`OracleStorage`/`OracleDatabase`/`OracleInstance`, plus subsystems for `asm/`, `awr/`, `dataguard/`, `flashback/`, `lock/`, `multitenant/`, `plan/`, `metadata/`, `packages/`, `commands/`, `actors/`, `demo/`.
  - `multitenant/` and `dataguard/` are honest state/bookkeeping facades, not physically-isolated engines: `PluggableDatabase` tracks CON_ID/name/open-mode but `OracleStorage` has no CON_ID notion at all — every PDB shares one schema/table namespace, so `ALTER SESSION SET CONTAINER` only swaps the session label (see the comment at `OracleDatabase.ts` around the `ALTER SESSION SET CONTAINER` handler). A "create a table in PDB1, confirm it's absent from PDB2" lab will silently fail. `DataGuardConfiguration.switchover()` likewise just swaps two `role` fields — there is no real redo transport/apply. Don't build pedagogical scenarios that assume real cross-PDB isolation or physical standby replication.
  - DATE columns rendered with no explicit `TO_CHAR` mask (rapport 07, item #48) previously showed either the raw internal `YYYY-MM-DD HH:MM:SS` storage string or, for `SYSDATE`/`FROM DUAL` pseudo-columns specifically, were tagged `VARCHAR2` and never date-formatted at all. Real Oracle defaults every unmasked DATE to `NLS_DATE_FORMAT` (session-scoped, default `DD-MON-RR`, no time-of-day). Fixed: `QueryResultRenderer.renderValue()` now formats any `isDate` column (or bare `instanceof Date` value) through `formatDateWithPattern()` using the session's `nlsDateFormat` (`SQLPlusSession.formatQueryResult` reads it off `session.nlsDateFormat`; `OracleDatabase.execAlterSession` writes it on `ALTER SESSION SET NLS_DATE_FORMAT`); `ScalarFunctionEvaluator`'s `TO_CHAR` falls back to the same session default when called with no format arg, and now runs `coerceDate()` (handles both a genuine `Date` object and a date-string) instead of the old `typeof === 'string'`-only check, which silently fell through to JS's own `Date.prototype.toString()` for a real `Date` value. Pseudo-column type inference (`SYSDATE`/`CURRENT_DATE` → DATE, `SYSTIMESTAMP`/`CURRENT_TIMESTAMP` → TIMESTAMP, previously always `VARCHAR2`) had to be added in two separate places — `OracleExecutor.expandSelectItems` (table-based `SELECT`) and `executeSelectFromDual` (a wholly separate `FROM DUAL` pipeline that never calls `expandSelectItems`) — since fixing only the former left `SELECT SYSDATE FROM DUAL` still showing a full timestamp. Also added real `RR` century-rollover semantics (`resolveRRYear` in `dateSupport.ts`) alongside the pre-existing `YY` handling, for both formatting and `TO_DATE` parsing. Not attempted: PL/SQL-block `TO_CHAR` (`functions/conversionFunctions.ts`, a separate implementation reached only from inside `BEGIN...END` via a `SqlFunctionContext` that doesn't carry clean session access) still ignores `NLS_DATE_FORMAT` and is a smaller, separate, still-open gap.
  - `SELECT … FOR UPDATE` row-level locking (rapport 07, item #49): `LockManager.rowLocks` (`lock/LockManager.ts`) genuinely tracks which session owns which row, and `NOWAIT`/`SKIP LOCKED` were already correctly wired in `OracleExecutor.lockForUpdateRows()` — but a *plain* `FOR UPDATE` (no wait clause) or `FOR UPDATE WAIT n` against a row another session already held just fell through to `out.push(row)` and silently handed over the row as if the lock had been granted, without ever calling `acquireRowLock`. Two sessions could each believe they held the same row's lock — the core mutual-exclusion guarantee FOR UPDATE exists for was broken exactly when no `NOWAIT` was written. Real Oracle instead blocks the statement (indefinitely for plain `FOR UPDATE`, up to `n` seconds for `WAIT n`) until the holder commits/rolls back, but `OracleExecutor`/`OracleDatabase`/`SQLPlusSession`/`SqlPlusSubShell` are a fully synchronous call chain with no per-statement suspend/resume concept — genuine blocking would need a promise-based wait queue in `LockManager` threaded through that whole chain as `async`, which `ISubShell.processLine`'s `SubShellResult | Promise<SubShellResult>` signature and `interruptForeground()` hook (`terminal/subshells/ISubShell.ts`) already anticipate structurally (per its doc comment, another subshell already returns async), but which touches the single synchronous `OracleExecutor.execute()` core shared by every statement type (DDL, DML, PL/SQL, triggers, scheduler jobs) — a cross-cutting refactor, not a bounded fix. Fixed the bounded half instead: a plain `FOR UPDATE` or `WAIT n` against an already-held row now denies immediately (`ORA-00054`/`ORA-30006` respectively) rather than silently granting a second, phantom lock — trading "hangs forever" for "fails fast," which is honest given the architectural constraint and strictly safer than the previous silent double-grant. `LockManager.lockTable()` (TM/table locks, not row locks) has the identical "record a fake wait, never actually suspend the caller" pattern — tracked separately as item #50, not touched here.
  - TM (table) lock enforcement for ordinary DML (rapport 07, item #50): `LockActor` used to acquire a DML statement's TM lock reactively, off the `oracle.dml.executed` event — which only fires *after* `OracleExecutor.execute()` has already run the INSERT/UPDATE/DELETE against storage (`emitForStatement`/`emitDml` are called post-execution). The lock therefore never protected anything; it was pure `V$LOCK`/`DBA_DML_LOCKS` bookkeeping applied after the fact, and `LockManager.acquireDmlLock`'s catch swallowed everything but `DeadlockError` on top of that. A session holding an explicit `LOCK TABLE t IN EXCLUSIVE MODE` (or any stronger mode) could not actually stop another session's plain DML on that table. Fixed: `OracleExecutor.dispatchStatement()` now calls a new `acquireDmlTableLock()` *before* dispatching to `executeInsert`/`executeUpdate`/`executeDelete`, and `LockManager.acquireDmlLock()` denies immediately (`ORA-00054`) on a real conflicting held lock instead of registering `lockTable()`'s usual fake-pending/wait-for-later entry — same "can't block, so fail fast rather than silently let it through" reasoning as item #49, and low blast radius since ordinary DML's own Row-X(3) mode never conflicts with another session's plain DML (only with an explicit stronger `LOCK TABLE`). `LockActor` no longer subscribes to `oracle.dml.executed` at all (release-side subscriptions — commit/rollback/disconnect — are unchanged and still correct). Explicit `LOCK TABLE`'s own fake-pending/`DBA_WAITERS`/`DBA_BLOCKERS`/`V$SESSION.BLOCKING_SESSION` observability (`execLockTable`, still calling `lockTable()` directly) was deliberately left untouched — those views are a deliberately-accepted simplification for that specific statement, not the MAJEUR-rated complaint this item targets. Not attempted: deadlock detection reachable via pure DML (rated MINEUR in the source audit, and structurally still unreachable regardless of acquisition timing since two Row-X(3) locks never conflict with each other in the compatibility matrix — deadlock among plain DML statements requires a modeled conflict path this simulator doesn't have).

`EventBus`, `Scheduler`, `Signal`, `TimerSet`, `waitForEvent` — shared reactive primitives used by protocol actors (OSPF, IPSec, DHCP, BGP, etc.) that model asynchronous, timer-driven behavior.

### State management (`src/store/`)

Single Zustand store (`networkStore.ts`) holds the full topology: devices (`NetworkDeviceUI[]`), connections (`Connection[]`), and UI state. The store bridges `Equipment` instances to React rendering. `topologySerializer.ts` handles save/load of topologies.
- `NetworkCanvas`/`PropertiesPanel` subscribe to the whole store (no per-field selector, see item #52's note above on why that's deliberately not narrowed), so any zustand `set()` anywhere re-renders them and picks up a fresh `getDevices()` snapshot of live `Equipment` state. That's fine for CLI-triggered changes — the CLI action itself is a store-adjacent event — but until fixed (rapport 09, item #56) it meant an autonomous change with no `set()` anywhere in its path never reached the canvas at all: a port going admin-down or carrier-down from a dead-interval timeout, a DHCP lease clearing an interface's IP on expiry, an autonomous SPF recompute reaching the RIB via `RoutingTableSyncActor` — none of these ever call into zustand (`src/network/` never imports the store, confirmed by grep), so the connection/interface data on canvas stayed visually frozen until some unrelated store action happened to fire afterward. Fixed by bridging a small, explicit topic allowlist off the default `EventBus` (`getDefaultEventBus()`, the "OBSERVER bus (Logger/UI/tests)" per its own header comment — already the intended hook-in point, not a repurposing) into a `revision` bump: `port.link.up`/`port.link.down`/`port.config.ip-changed` — exactly the topics behind the two fields `NetworkDeviceUI.interfaces` actually renders (`isUp`, `ipAddress`); DHCP lease grant/renew/expire and static/manual IP changes all funnel through `port.config.ip-changed` already (`Port.configureIP`/`clearIP`), so no separate DHCP-specific subscription was needed. Deliberately NOT `bus.subscribeAll()`: the same bus also carries a `port.frame.*`/`cable.frame.*`/`ospf.packet.*` event per Ethernet frame and a `device.position-changed` per drag-pixel, and reintroducing that volume would undo item #52's re-render fix. The subscription is (re-)established from `getDevices()` itself (cheap reference check against the last-subscribed bus) rather than once at module load, specifically because `setupGlobalState.ts`'s global `beforeEach` nulls the default EventBus before every test (`__setDefaultEventBus(null)`) — a naive one-time subscription would silently go dead against the discarded bus and only ever work in the first test of a file; `canvas-autonomous-events.test.ts`'s "rebridges after the default EventBus is swapped" case covers exactly this. Note this fix is scoped to what's actually rendered today: OSPF neighbor/SPF events, STP role changes, and HSRP/VRRP/GLBP active/standby are real and event-driven but have no corresponding field on `NetworkDeviceUI` to refresh, so they're deliberately not in the allowlist — add them if a future UI surface ever renders that state.
- `topologySerializer.ts` captures a real, wide slice of configurable device state (see the file's own header comment: interfaces, static routes/ARP, every modified Linux file, VLAN/switchport config, and full running/startup vendor config text replayed through the real CLI on import) — but until fixed (rapport 09, item #55), none of what it *doesn't* capture was ever disclosed to the user, and Save/Export/Open/Import were silent about it either way. What's genuinely lost on a round-trip: terminal sessions and scrollback (actively torn down on import — `clearAll()` triggers `registry.cleared`, which `TerminalManager.disposeAll()` subscribes to), live TCP/SSH transport state (a fresh `Equipment` instance is created on import; the old one's sockets go with it), and dynamic protocol/runtime state (OSPF LSDB, BGP RIB, DHCP lease bindings) — only the *config* that produces these is captured, so a reloaded topology must reconverge from scratch rather than resuming mid-state. Fixed the disclosure half: `TOPOLOGY_SAVE_CAVEATS` (exported from `topologySerializer.ts`) is now shown as plain text in `SaveTopologyDialog` and as the body of a new confirm step gating `Export` (previously Export had no dialog at all — it just downloaded a file). Also fixed an adjacent silent-loss gap in the same family: `Open`/`Import` used to discard the current canvas with zero warning; both now route through a `ConfirmDialog` ("Replace current topology?"/"Replace current topology's contents") when the canvas isn't empty, reusing `OpenTopologyDialog`'s existing nested-`ConfirmDialog` pattern from item #54 via a new `confirmReplace` prop. Deliberately not attempted: actually capturing the excluded state (terminal sessions, live sockets, LSDB/RIB/lease tables) is a materially larger lift with no existing schema fields or capture functions to extend, and is out of scope here. One gap this item once flagged as out of scope is now closed, and by a different change: Linux user accounts used to *look* preserved on a topology round-trip (their `/etc/passwd`/`/etc/shadow`/`/etc/group` text is captured by `captureLinuxFiles()` and written back verbatim by `restoreLinuxFiles()`) while not being functionally restored, because nothing re-read that text into `LinuxUserManager.users`/`groups` — a fresh imported device had only the default accounts even though `cat /etc/passwd` showed otherwise. `iam/fs/AccountDatabaseParser.ts` (see the IAM section above) supplies that reverse parse, so restoring the four files now rebuilds the accounts *and* their passwords for real (`account-database-is-file-backed.test.ts`, "a topology import that restores the files restores the ACCOUNTS"). The other exclusions above (terminal sessions, live sockets, LSDB/RIB/lease tables) are unchanged. Two more Windows-only surfaces have since been closed the same way — both live only on the `WindowsPC` object, with no file describing them and no config text replaying them, so a lab built on either came back factory-fresh with no warning. **The registry** is captured as a DIFF against a pristine hive (`captureRegistry`/`restoreRegistry`), walked through the same public surface `reg query /s` uses, with two non-obvious requirements: the baseline is built with the device's own product identity (a server diffed against a client hive would report its build number, `EditionID` and `InstallationType` as operator changes in every topology file) AND it runs `projectServiceIntoRegistry` over a factory `WindowsServiceManager`, because `HKLM:\SYSTEM\CurrentControlSet\Services\<name>` is not seeded at all — the device projects it from the service table at boot, so a bare hive reports that whole subtree as new. **Deletions are carried explicitly** (`removedValues`/`removedKeys`), and that is the reason it is a diff rather than a dump of what exists: half of what a lab does to a registry is REMOVE a seeded value or key, and a capture that only listed what was present would bring every one of them back on the next load — the machine would silently undo the exercise. `RegistryValue.type` is deliberately not captured: it is write-only metadata that nothing in the codebase ever reads back (`reg query` infers REG_DWORD vs REG_SZ from `typeof`), and `setItemProperty` — the very path `reg add` takes — collapses it to String/DWord anyway, so replaying through it reproduces exactly what the operator's own command produced. **Services** are captured the same way (`captureWindowsServices`/`restoreWindowsServices`): each field only when it differs from a factory `WindowsServiceManager`'s service of the same name, plus the whole record for one `sc create` added. Restore order matters twice and both are asserted by test: state is applied BEFORE start type, because the SCM refuses to start a disabled service and "disabled while it was running" is a real machine state; and services are restored BEFORE the registry, so the captured hive — projection included — has the last word. `projectServiceIntoRegistry` (`WindowsServiceManager.ts`, a narrow `ServiceRegistrySink` port so that file need not depend on the registry) exists precisely so the device's live projection and the serializer's baseline cannot drift.
  - **A generic switch used to make Save fail for the whole topology.** `CiscoSwitchShell.buildRunningConfig` — the function `exportTopology` goes through for every `Router`/`Switch` — read `sw.getDtpAgent()` and `sw.getLacpAgent()` unconditionally, but `GenericSwitch` runs neither protocol and has neither agent (only `CiscoSwitch` does), so exporting any topology holding one threw `sw.getDtpAgent is not a function` and nothing was written at all. Fixed the way that function already resolves CDP/LLDP/STP/VTP — optionally, `if (agent)` — which was clearly the intent and simply missed for those two: no agent, no lines, which is exactly right for an unmanaged port (no negotiated mode, no channel group). Note what this fix alone recovered: **sticky port-security MACs already round-tripped**, because they live in the running-config (`renderPortSecurityLines`) that import replays through the real CLI, just as on real IOS — the "sticky MACs aren't serialized" symptom was this crash, not a missing capture. The wider problem behind it — `GenericSwitch` is given the full `CiscoSwitchShell` while running none of the Cisco protocols — is covered next.
  - **A generic switch's CLI crashed on twelve commands, and opened the wrong terminal entirely.** `CiscoSwitchShell` reads six protocol agents only `CiscoSwitch` builds (DTP, VTP, STP, LACP, UDLD, IGMP snooping) across ~53 call sites; on a `GenericSwitch` each threw `getXxxAgent is not a function` — `vlan 10` included, a switch's whole purpose — and one throw left the CLI stuck in a mode it could not leave, so everything after it answered `% Invalid input`. Fixed by splitting on what the device can honestly answer. **Derivable from local configuration ⇒ it really works**: the VLAN database lives on the device and VTP only PROPAGATES it, so `vlan`/`no vlan`/`name` now notify VTP optionally (`optionalVtp()?.onLocalVlanChange()`) and create the VLAN either way; likewise a switch that does not speak DTP negotiates nothing, so its operational mode IS its configured mode and `show interfaces switchport`/`show interfaces trunk` answer truthfully (with `Negotiation of Trunking: Off`, since there is no DTP to negotiate with). **Needs a protocol the device does not run ⇒ refused**, in IOS's own words for a command the platform lacks (`% Invalid input detected at '^' marker.`) — not a table describing a protocol nobody speaks, which would be a fake. Mechanically, `require*` accessors throw a dedicated `UnsupportedOnThisSwitchError` caught in exactly one place (`execute`), which is what lets forty handlers stay untouched; being a named type rather than a blanket `catch`, it cannot swallow a real bug. **Separately and more insidiously, the terminal itself was the wrong platform's**: `getOSType()` is read everywhere as "which shell dialect is this" (`Router` delegates it straight to `this.shell.getOSType()`, and both `sessionFactory` and `primaryShellKindFor` dispatch on it), and `GenericSwitch` answered `'generic'`, which fell through to the POSIX default — so a switch whose only shell is `CiscoSwitchShell` got a **bash** `LinuxTerminalSession` in the UI, where `exit` from `config-vlan` logged the operator out mid-configuration instead of going up one level. It now answers `'cisco-ios'`; nothing else read `'generic'`. Still true and deliberately unchanged: `GenericSwitch` runs no protocol agents at all, so the refusals above are permanent, not a stub awaiting an implementation.
  - **`systemctl disable` is a REMOVED symlink, and a capture of what exists cannot see a removal.** `captureLinuxFiles` records every file that differs from a pristine VFS, so `systemctl enable`'s `multi-user.target.wants/<unit>` link is captured — but `disable`, which works by deleting it, left no trace at all, and the reopened machine re-created the link at boot and started the service again. `systemctl stop` (not file-backed at all) was lost the same way. A `docs/PRD-Pannes.md`-style lab built on a stopped daemon came back healthy, silently. Fixed with `captureLinuxServices`/`restoreLinuxServices` (`linuxServices: {name, enabled, active}[]`). This one is deliberately **not** a diff, unlike the registry: a machine has ~15 units, so the whole table is readable in the file and needs no baseline to interpret, and the restore applies only what actually differs on the reopened machine. Order matters and is asserted: enablement before activation (`mask` also blocks a start), and the whole block after `restoreLinuxFiles`, because a unit file the lab wrote has to exist before the manager can be asked to enable it. `static` is reported and never set — a unit with no `[Install]` section has no link to make or break.
  - **`sc qc` and `reg query` are two readings of one fact**, and until fixed they could disagree. The projection used to be driven from *outside* the SCM — a `WindowsPC` subscriber on `windows.service.account-changed` plus a one-shot seeding loop at bus attach — so only an account change ever refreshed the key: `sc config <svc> start= disabled` moved the service to DISABLED and left the hive's `Start` at 2 (AUTO_START), on the same machine at the same instant. On a real box that key IS the configuration (it is what the SCM re-reads at boot), so the fix is that `WindowsServiceManager` now writes it itself through the `ServiceRegistrySink` it is handed at construction (`attachRegistrySink`, which also projects every seeded service). Writing from inside is what makes it airtight: a mutation cannot forget to announce itself because there is nothing to announce — `setStartType`, `setAccount`, `createService`, `addService` (role/feature installs) and `deleteService` all go through it, and `deleteService` genuinely removes the key (`PSRegistryProvider.removeServiceKey`), since leaving it behind would have the SCM re-read a service nobody can start. `WindowsPC.syncServiceRegistryKey`, its `_serviceRegistrySyncOff` subscription and the seeding loop are gone. `windows-service-config-is-the-registry.test.ts` pins the round-trip for `sc config start=`/`obj=`, `Set-Service -StartupType`, `sc create`/`sc delete`, and that a refused (non-admin) `sc config` leaves the hive untouched. The serializer's baseline uses the same one call rather than its own loop.

### UI (`src/components/`)

- `network/` — canvas, device palette, device icons, connection lines, properties panel, terminal modal, packet animation, logs panel. Entry point: `NetworkDesigner.tsx`.
  - Two bounded re-render fixes (rapport 09, item #52): `NetworkCanvas`'s `handleMouseMove` used to call `setMousePos` on *every* mouse movement, even idle (not connecting a cable) — that state only feeds the elastic connection-drawing line, so it re-rendered the whole canvas subtree for no visible effect; now gated on `isConnecting`. `ConnectionLine`/`PacketAnimation` were not memoized, so `NetworkCanvas` re-rendering 60x/sec off `useActivePackets`' rAF loop (component state, outside the zustand store) re-rendered every connection line too even though its own `connection`/`devices` props hadn't changed — `networkStore.ts`'s existing snapshot cache (`stableDeviceUI`/`devicesArraySnapshot`, see `getDevices()`) already keeps those props referentially stable when nothing visible changed, so `memo()` on both components (plus converting `ConnectionLine`'s own unscoped `useNetworkStore()` call to per-field selectors) was a correct, low-risk fix. Deliberately **not** attempted: narrowing `NetworkCanvas`/`PropertiesPanel`'s own top-level `useNetworkStore()` calls the same way — both destructure `getDevices`, whose result is driven by `revision`/`deviceInstances`, neither of which the component reads directly (confirmed via `devices-snapshot-stability.test.ts`: `moveDevice` bumps `revision` alone, without touching `deviceInstances`). Selecting only the fields actually rendered would silently stop the canvas from updating on a plain device drag — a worse regression (silent staleness) than the wasted re-renders it would fix. This is entangled with item #56 (autonomous network events not reaching the canvas at all): the current over-broad subscription is accidentally the only thing keeping some of those cases live today, so narrowing it is only safe once #56's dedicated bus-driven revision hook exists to replace that accidental coverage.
  - Two-part fix (rapport 09, item #54). Part 1, blocking native dialogs: `window.prompt`/`alert`/`confirm` in `NetworkDesigner.tsx` (Save name entry, Open topology picker + delete, Clear-All/Reset confirmation, assorted error notices) freeze the whole tab and can't be driven or asserted from tests. The one non-obvious constraint (surfaced by an investigation *before* writing any code): a device's entire CLI-configured state — IPs, routes, hostname, VLANs — lives only on the live `Equipment` instance, so `undo` of `removeDevice` must keep the *same* instance alive (deregistered, not destroyed) and re-register it, never recreate a blank one via `createDevice()`; `EquipmentRegistry.register()` is safe to call again for this. Per-pixel drag ticks still go through the pre-existing `moveDevice` (no history); a new `commitMove(id, from, to)` records exactly one step per whole drag gesture or arrow-key nudge, wired from `NetworkDevice.tsx`'s mouseup handler and keyboard nudge. `clearAll()` (and by extension Import/Open, which call it first) resets both stacks — same "loading a new document drops undo history" rule real editors use. Deliberately out of scope: `updateDevice` (property-panel edits like hostname/interface config) is not undoable, a restored device comes back powered off with no terminal session restored, and undo/redo themselves don't push new history entries (an undo can't be "redone-away" by a stray extra undo).
- `terminal/TerminalView.tsx` — terminal renderer.
  - Two bounded fixes (rapport 09, item #53): (1) the scroll-to-bottom `useEffect` ran unconditionally on every render (no "am I at the bottom?" check), so a stream (`tail -f`, continuous ping, `debug ip ospf`) yanked the view back down on every new line — the user could never scroll up to read earlier output. Fixed by tracking a `stuckToBottom` flag (an `onScroll` handler recomputes it from `scrollHeight - scrollTop - clientHeight`) and only forcing `scrollTop` while it's true — the same live-tail pattern already correct in `NetworkLogsPanel.tsx`. (2) Scrollback is configurable up to 50,000 lines (`TerminalModal.tsx`) with one `<pre>` per line and no virtualization — every past line stayed a live DOM/layout node forever. `LineRenderer` was already memoized, so reconciliation was bounded, but layout/paint wasn't. Fixed with the audit's own suggested minimal correctif: each line is wrapped in a `content-visibility: auto` + `contain-intrinsic-size` div, letting the browser skip layout/paint for scrollback that isn't near the viewport without changing the render tree or any scroll/selection/search interaction. Trade-off (matches MDN's own guidance for long lists): a wrapped multi-row line gets a brief height correction once it scrolls into view, since the single-row `contain-intrinsic-size` estimate can't predict wrapping. Manual windowing (rendering only a slice of `session.lines`) would avoid that trade-off but is a bigger change touching scroll-position math, search-within-scrollback, and selection across virtualized rows — not attempted here.

- Until fixed (rapport 09, item #57), every spec that needed a lab topology built it by calling `store.getState().addDevice`/`addConnection` directly in `page.evaluate` and only drove the terminal/CLI layer through real DOM interaction — nothing exercised the actual pointer-driven cabling gesture or the Save/Open dialogs (items #54/#55) through the browser, despite ~123 spec files existing. `canvas-cable-save-flow.spec.ts` closes that gap: places two devices via the palette's accessible add-button, cables them through the real Connect flow, and round-trips the result through Save then Open. Two non-obvious things worth knowing if extending it: (1) cabling is click/keyboard-driven, not a drag gesture — `NetworkDevice.tsx`'s `handleMouseDown` calls `selectDevice`/opens `InterfaceSelectorPopover` on plain clicks (`startConnecting`/`finishConnecting`), so ordinary Playwright `.click()` works with no special drag choreography (device *placement*, by contrast, genuinely is HTML5 DnD when driven via the palette's `draggable` button — see `dnd-first-attempt.spec.ts`'s manual `DragEvent` dispatch for that case, since Playwright's built-in `dragTo()` doesn't reliably fire native DnD events here); (2) `InterfaceSelectorPopover`'s own Cancel/X button renders *before* the interface-row buttons in DOM order and is never `disabled`, so a naive `button:not([disabled])` locator clicks Cancel instead of an interface — a real failure hit while writing this spec, not a hypothetical; select interface rows via `button:not([disabled]):not([aria-label="Cancel interface selection"])` instead. Save/Open's dialogs are plain Radix `Dialog`s (`role="dialog"`, portalled to `document.body`); the "replace current topology?" confirm they can trigger is an `AlertDialog` (`role="alertdialog"`) — the distinct role is what disambiguates the two stacked dialogs without needing a `data-testid`.
- Vitest environment is `node` (configured in `vite.config.ts`); globals enabled. Coverage is currently scoped to `src/network/protocols/ssh/**` with thresholds (lines/functions/statements 85%, branches 75%).
- `setupFiles: ['./src/__tests__/setupGlobalState.ts']` (rapport 08, item #51) runs a global `beforeEach` resetting `EquipmentRegistry`/device-name counters (`resetDeviceCounters()`, which also calls `Equipment.clearRegistry()`), MAC/ID counters (`resetCounters()`), `Logger`, and the default `EventBus`/`Scheduler` singletons (`__setDefaultEventBus(null)`/`__setDefaultScheduler(null)`, forcing a fresh instance on next `getDefaultEventBus()`/`getDefaultScheduler()`) before every test in every file. This was the audit's own highest-value, lowest-cost recommendation: 834 of ~1344 test files already call some subset of these resets by hand in a local `beforeEach`, and a forgotten or incomplete one let one `it()` block pollute the next *within the same file* (Vitest's default per-file `isolate: true` already prevents pollution *across* files). The new global hook is a backstop, not a replacement — existing manual resets are untouched and stay harmless no-ops where this hook already did the work. Deliberately scoped to only the globals shared by virtually every test regardless of subsystem; subsystem-specific singletons (`resetAllOracleInstances()`, `resetPkiCaRegistry()`, `resetForestRegistry()`, `resetExchangeOrganizations()`, …) remain each test file's own responsibility, both because they're needed by a much smaller fraction of files and because pulling e.g. `terminal/commands/database.ts` into a universally-loaded setup file would add import cost to every single test file regardless of whether it touches Oracle. Verified with two full clean-state A/B comparisons (with vs. without this file) across `unit/database/` (3115 tests), the rest of `unit/` excluding `network-v2` (3927 tests), and multiple individually-reproduced `unit/network-v2/` cases spanning unrelated failure categories (SSH session/connection-count timing, Windows Event Log "gap confirmé" tests) — identical results either way, confirming this change fixes the flakiness class without altering behavior of any currently-passing test.

## Conventions worth knowing

- Production builds set `esbuild.keepNames: true` and `build.minify: 'esbuild'` because the simulator dispatches on `instance.constructor.name` (e.g. `=== 'WindowsPC'`) to choose vendor-specific behavior — default minification would break this (see comment in `vite.config.ts`).
- Reactive protocol engines (OSPF, IPSec, DHCP, BGP, routing) follow a consistent shape: `<Protocol>Engine.ts` + `types.ts` + `events.ts` + `observables.ts` + `actors/` built on `src/events/` primitives — follow this pattern when adding a new protocol.
- `@typescript-eslint/no-unused-vars` is disabled project-wide in `eslint.config.js`.
