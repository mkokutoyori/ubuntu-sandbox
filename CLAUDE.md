# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A browser-based network simulator (Ubuntu Sandbox) built with React + TypeScript. Users drag-and-drop network devices (routers, switches, PCs, servers) onto a canvas, cable them together, and interact via in-browser terminal emulators that simulate Cisco IOS, Huawei VRP, Linux bash, Windows cmd/PowerShell, and Oracle SQL*Plus. The simulation runs entirely client-side — protocols (OSPF, BGP, EIGRP, STP, DHCP, IPSec, etc.), shells, and the Oracle database engine are all reimplemented from scratch in TypeScript.

## Architecture

**Path alias:** `@/` maps to `src/`.

### Network simulation layer (`src/network/`)

Equipment-driven architecture — no central simulator mediator. Devices process and forward frames themselves, peer-to-peer over cabled ports.

- `equipment/Equipment.ts` — abstract base class for all devices; maintains a static `EquipmentRegistry` for topology traversal. Subclasses implement `handleFrame()`.
- `equipment/HostCapabilities.ts` / `equipment/RouterServiceCapabilities.ts` — segregated optional-capability interfaces + accessor functions (`isCredentialAuthenticator(dev)`, `getManagementService(dev)`, `getHsrpAgent(dev)`, …) for reaching a concrete device's methods from code typed against a narrower shared interface (`CiscoDevice`, `ICLIDevice`, raw `Equipment`). Prefer extending these over a fresh inline `dev as unknown as { getXxx?: () => Yyy }` at the call site (rapport 08 audit: reduce unencapsulated casts).
- `hardware/Port.ts`, `hardware/Cable.ts`, `hardware/PortSecurity.ts` — physical layer; Cables connect Ports for direct device-to-device frame delivery.
  - No FCS field exists on `EthernetFrame` (rapport 04, item #45), and adding a bare one would be decorative — there's no byte-level frame encoding to corrupt against. Instead, `Cable` now has a `corruptionRate` knob mirroring the pre-existing `packetLossRate` one (`setCorruptionRate`/`getCorruptionRate`, `CableStats.framesCorrupted`): a "corrupted" frame never reaches the receiver's `handleFrame()` (same observable effect as a real NIC silently discarding a bad-FCS frame) and increments the previously-dead `Port.errorsIn` counter, distinct from generic simulated loss. Also fixed: `Cable.transmit`/`Port.sendFrame`/`receiveFrame` intentionally deliver the *same* frame object end to end (asserted by identity in `hardware.test.ts`, kept that way — cloning every frame would be the hottest path in the simulator for no observed bug), but several **fan-out** call sites were handing that same object to *multiple* destinations instead of a fresh one per destination: `Hub.handleFrame`, `Switch.floodFrame`'s `stripTag`/`stripOuterTag` (returned the input frame unchanged for the common untagged case), `Switch.emitMirror` (SPAN destination shared the real egress frame), and `Router.forwardMulticast` (one `IPv4Packet` object reused as the `payload` of every OIF's frame). Nothing currently mutates a frame/packet in place post-handoff, so this was latent rather than an active bug — but a landmine for the next feature that does. Fixed by giving each fan-out destination its own shallow copy; BGP/IS-IS-style deep immutability (`Object.freeze`, already used elsewhere for config objects) was not applied to the hot data-plane path.
- `core/types.ts` — frame/packet structures (`EthernetFrame`, `IPv4Packet`, `ARPPacket`, `ICMPPacket`, `UDPPacket`, `RIPPacket`), address types (`MACAddress`, `IPAddress`, `SubnetMask`), protocol constants, ID/checksum helpers.
- `core/` also holds shared infra: `Logger.ts` (pub/sub network event log), `RoutingTable.ts`, `PacketQueue.ts`, `SocketTable.ts`, `TcpConnection.ts`, `FilterChain.ts`, `NeighborResolver.ts`, `WellKnownPorts.ts`, `Ipv4Fragmentation.ts` (RFC 791 §3.2 `fragmentIPv4`/`IPv4Reassembler` — used by `Router.forwardPacket` and `EndHost.forwardIPv4` when a datagram crosses onto a smaller-MTU link with DF clear; DF=1 still gets ICMP Fragmentation Needed instead).
- UDP checksum (RFC 768) — `computeUdpChecksum`/`verifyUdpChecksum` live in `tcp/types.ts` (shared L4-checksum module with TCP's `computeTcpChecksum`, despite the filename). `EndHost.sendUdpDatagram` stamps a real checksum; `EndHost.deliverUDP` and `Router`'s self-destined UDP dispatch verify and silently drop a mismatch. Internal protocol agents (RIP, DHCP, IKE, SNMP, …) still build `UDPPacket`s with `checksum: 0` — that's RFC 768's IPv4 "not computed" opt-out and is accepted unconditionally, same as those agents' payloads not being real serialized bytes in the first place.
- `devices/` — concrete device classes (`LinuxPC`, `WindowsPC`, `LinuxServer`, `CiscoRouter`, `HuaweiRouter`, `CiscoSwitch`, `HuaweiSwitch`, `GenericSwitch`, `Hub`, `Router`, `Switch`, `EndHost`). Instantiated via `DeviceFactory.createDevice(type)` (see `core/types.ts` for the `DeviceType` union — note some types like `firewall-*` are currently stubbed as `LinuxPC`).
  - `firewall-cisco`/`firewall-fortinet`/`firewall-paloalto` (rapport 04, item #46) are literal `new LinuxPC(...)` calls (`DeviceFactory.ts`) — no ASA/FortiOS/PAN-OS CLI, no security-level/zone forwarding model, nothing reads the `deviceType` string at runtime beyond hostname prefix and palette icon. This is UI-reachable, not dead code (draggable from the palette today), but already honestly disclosed there: `DevicePalette.tsx` renders an amber "Limited simulation" badge via `isFullyImplemented()` for exactly these types. What a firewall device inherits from `LinuxPC` — `LinuxIptablesManager.ts`'s netfilter engine (real 4-table chain traversal, genuine conntrack NEW/ESTABLISHED/RELATED, working NAT) — is actually more realistic stateful-filtering machinery than `Router.ts`'s own `ACLEngine` (`established` is a bare TCP-flag check, no reflexive ACL, no zone-based firewall concept exists anywhere in the codebase to reuse). The missing piece is purely the vendor CLI/security-model wrapper, and there's zero existing scaffolding for any of the three (no ASA/FortiOS/PAN-OS shell, parser, or test fixture anywhere). Deliberately not attempted: per the audit's own prioritization (`docs/audit/04-equipements-data-plane.md` §5.7 — this item doesn't even make the audit's own "top 10 recommended actions"), and given each vendor's CLI grammar + security model is genuinely distinct (ASA security-levels/object-NAT, FortiOS VDOMs/`config firewall policy`, PAN-OS zones/rulebase) and comparable in scope to the multi-session Huawei-router-CLI or SSH-unification efforts — not a bounded single-session slice. If attempted later, Cisco ASA (extending `Router` like `CiscoRouter`/`HuaweiRouter` do, reusing `ACLEngine`/`NATEngine`) is the best-reuse starting point; a real connection table, twice-NAT, and the other two vendors would remain out of scope even then.
  - `devices/router/` — router subsystems: ACL, NAT, IPv6 data plane, dynamic routing (OSPF/RIP integration), AAA, BFD, DNS, EEM, NetFlow, NHRP, redundancy (HSRP/VRRP/GLBP), policy, management, CLI.
  - `devices/router/policy/{RoutePolicy,IpPrefixList}.ts` (rapport 02, item #44) — `IpPrefixList.evaluate()` was already a real, correct RFC-shaped prefix matcher, just never called from redistribution. `RoutePolicy`/`RoutePolicyNode` had no evaluation logic at all — pure config storage for `display`. Fixed the bounded slice: `RoutePolicy.evaluate()` now matches `if-match ip-prefix` (via `IpPrefixListStore`), `tag`, and `route-type` — the only match kinds with real data on a redistributed route today — and fails a node closed (doesn't match) if it also references `acl`/`community`/`as-path`/`interface`/`ext-community`, since none of those have a backing value to check yet; no match on any node is an implicit deny, like real VRP. Wired into both directions: Huawei RIP's `import-route ... route-policy <name>` (`RIPEngine.advertisableMetric()` via a new `RIPCallbacks.evaluateRoutePolicy` seam) and Huawei OSPF's `filter-policy { <acl> | ip-prefix <name> } { import | export }` (`RouterOSPFIntegration.isFilteredByDistributeList()`, gating both `installRoutes()` for `import` and `originateRedistributedRoutes()` for `export` — the `export`/`out` direction and the `ip-prefix` form of `filter-policy` were previously silently dropped by the CLI parser entirely). Not attempted: `apply`-clause mutation (cost/tag/next-hop rewriting on a permitted route), BGP/IS-IS redistribution (both are separately-tracked dead config — `BGPEngine.redistribute` and `HuaweiRoutingExtras.importedRoutes` are never read by anything), and Cisco's `route-map`/`PolicyRepository` equivalent (stores raw strings, no structured match at all — a larger lift than Huawei's already-structured-but-unused stores).
  - `Router.ts`'s RIB (`private routingTable: RouteEntry[]`) has no separate FIB and no next-hop recursion: `lookupRoute()` (the data-plane forwarding seam) reads the very same live array every protocol integration mutates directly, and it's called on *every* forwarding decision, which in turn calls `dynamicRouting.refresh()` — control-plane recomputation triggered by data-plane packet processing, backwards from a real router's independent timer-driven control plane. There's also no recursive next-hop resolution: every route's next-hop must be on a directly-connected subnet, so a classic recursive static route (`ip route <net> <mask> <off-link-ip>`) or loopback-to-loopback iBGP is accepted by the CLI but never actually resolves/forwards. Real ECMP (ties on prefix/AD/metric round-robin across all tied RIB entries — see `lookupRoute`'s `candidates` array and `RouterOSPFIntegration.installRoutes`'s per-nextHop loop over `OSPFRouteEntry.nextHops[]`) was fixed; full RIB/FIB separation and route recursion were not — both are genuine architectural gaps (rapport 02 audit item #40), not bounded fixes.
  - `devices/host/` — end-host actors/lifecycle/identity/hardware (shared by Linux/Windows hosts).
  - `devices/linux/` — Linux subsystem services: ARP, DNS, cron, firewall/iptables, IP/net commands, process management, logging, scripting.
  - `devices/linux/iam/policy/AccountLockoutPolicy.ts` models every `/etc/security/faillock.conf` key including `unlock_time` (default 600s, matching real Debian/Ubuntu), but until fixed, `unlock_time` was stored/rendered and never actually consulted: once `LinuxUserManager.checkPassword()`'s failure tally reached the `deny` threshold (default 3 — exactly `LinuxInteractionPlanner.MAX_SUDO_ATTEMPTS`, so a single `sudo` invocation with 3 mistyped passwords was enough to trip it), the account stayed locked out **for the rest of the session**, rejecting even the correct password forever after, with no self-service recovery (`faillock --reset` itself needs root, which was now unreachable). Fixed: `LinuxUserAccount.recordFailedLogin()` now stamps `lastFailedLoginAt`; `AccountLockoutPolicy.shouldLockOut()` takes that timestamp and auto-clears the lock once `unlock_time` (or `root_unlock_time` for uid 0) has elapsed, same as real `pam_faillock`; `LinuxUserManager.isAccountLockedOut()` resets the tally to zero once it observes the window has passed. `su`/`passwd` share the same `checkPassword()` gate and are fixed the same way.
  - `devices/windows/` — Windows/PowerShell subsystem services: registry, event log, services, pipelines, port-proxy, cmdlets.
  - `devices/os/` — cross-platform OS abstractions (`OSProcess`, `OSService`, `OSServiceOrchestrator`, `OSFeatureGate`).
  - `devices/inspection/` — `DeviceStateView` / `EquipmentStateView` for introspecting live device state (used by debug tooling and tests).
  - `devices/shells/` — CLI shell implementations (`CiscoIOSShell`, `HuaweiVRPShell`, `CiscoSwitchShell`, `HuaweiSwitchShell`, `CLIStateMachine`, `CommandTrie`, `PromptBuilder`) implementing `IRouterShell`/`ISwitchShell`.
- **Protocol engines** — each protocol has its own top-level directory with engine, types, events/observables, and (for reactive ones) `actors/`: `ospf/`, `bgp/`, `eigrp/`, `rip/`, `routing/`, `dhcp/`, `ipsec/`, `acl/`, `arp/`, `bfd/`, `cdp/`, `dot1x/`, `dtp/`, `glbp/`, `gre/`, `hsrp/`, `igmp/`, `igmp-snooping/`, `lacp/`, `llmnr/`, `lldp/`, `mdns/`, `netflow/`, `ntp/`, `pim/`, `radius/`, `snmp/`, `stp/`, `syslog/`, `tacacs/`, `tcp/`, `udld/`, `vrrp/`, `vtp/`, `vxlan/`. SSH/SCP/SFTP lives under `protocols/ssh/`.
  - `llmnr/LlmnrAgent.ts` (RFC 4795, UDP/5355 on 224.0.0.252) and `mdns/MdnsAgent.ts` (RFC 6762, UDP/5353 on 224.0.0.251) are real responders/queriers sharing one transport, `dns/transport/MulticastDnsTransport.ts`. A host answers only for the name it owns — its single-label hostname for LLMNR, `<hostname>.local` for mDNS — and stays **silent** otherwise (a NXDOMAIN on a group would speak for the whole link). LLMNR replies unicast to the asker; mDNS replies on the group, except to a one-shot query from an ephemeral source port, which gets a unicast reply with a 10s-capped TTL (§6.7), and announces itself unsolicited at start with the cache-flush bit (§8.3). Wired into `ResolvedService` by systemd's own rule — `.local` goes to mDNS and never to a unicast server (RFC 6762 §3), a single-label name falls back to LLMNR when DNS has nothing — so `resolvectl query`, `getent hosts` and `ping <name>` all reach them; `resolvectl query` names the protocol used (`-- Information acquired via protocol LLMNR/IPv4`), and a link-local answer is never reported as authenticated since nobody signs it. **The global `LLMNR=`/`MulticastDNS=` setting is the default for links, not an independent switch**: a protocol is on as soon as one link allows it, and the global decides only while no link is configured — without that rule `resolvectl llmnr eth0 no` on the only link closed nothing, and `resolvectl mdns eth0 yes` did nothing on a machine with no DNS server. **Name conflict is handled, and the two RFCs diverge there.** LLMNR *signals*: at start the host asks the link for its own name three times (§4.1); an answer means someone else holds it, so it sets the `C` bit in its replies and lets the asker decide — it never renames. mDNS *arbitrates*: it probes three times 250ms apart (§8.1) with an `ANY` question carrying its intended records in the Authority section, and on conflict moves to `alpha-2.local` and re-probes (§9); two hosts probing at once can't rely on each other to answer, so they compare proposed records and the greater one wins (§8.2). While probing, a host does **not** answer for the name — that would assert the ownership it is still verifying. **Header trap, and a real bug this fixed:** LLMNR redefines bit 10 as `C` (Conflict) where DNS has `AA`, and bit 8 as `T` (Tentative) where DNS has `RD`. The responder set `aa: true` on every reply "because an LLMNR responder is authoritative" — so it announced a conflict every time; `llmnrFlagOverrides`/`readLlmnrBits` in `llmnr/types.ts` exist so the aliasing is written down rather than guessed. **Known-answer suppression** (§7.1) is implemented: a querier attaches what it already knows, the responder drops those records and stays fully silent if nothing is left. The threshold is the RFC's — the querier's copy only counts if its TTL exceeds half the TTL *we would have served*, which for a one-shot query is the §6.7-capped 10s, not 120. **DNS-SD** (RFC 6763) lives in `dnssd/`: `DnsSdRegistry` synthesises PTR/SRV/TXT (plus the `_services._dns-sd._udp.local` type enumeration of §9) and `MdnsAgent` answers from it alongside its own address records, attaching the follow-up records as additionals (§12) so one round-trip suffices. Publishing goes through a **unit file**, not a command: `/etc/systemd/dnssd/*.dnssd` (`systemd.dnssd(5)`, `net/DnssdFiles.ts`), same `[Section]` format and same `/etc` › `/run` › `/usr/lib` precedence as networkd's `.network`; an entry missing `Name`/`Type`/`Port` is skipped rather than half-published. This is what gave `resolvectl service` a data source — it was previously declared out of scope for lack of one. Instance names are free-form including dots (§4.1.1), so `parseInstanceName` splits from the end. **Subtypes** (§7.1) answer too: `_printer._sub._http._tcp.local` PTRs point at the very same instance — a subtype narrows discovery, it does not create a second service — and they stay out of the §9 type enumeration. **Service lifecycle** (§8.4, §10.1): a service is announced once the host name is claimed (never before — that would assert both at once), re-announced with cache-flush when it changes, and sent with TTL 0 when withdrawn. `.dnssd` reload is differential rather than clear-and-republish: without diffing, a service deleted from disk would vanish silently and peers would keep believing in it; republishing an unchanged one announces nothing. So this isn't decorative, `MdnsAgent` also *listens* to other hosts' announcements and keeps a passive cache of services heard (`knownServices()`) — that cache is what a TTL 0 empties, and it is what makes a goodbye observable at all. `systemd.dnssd(5)`'s `SubType=`, `Priority=` and `Weight=` are parsed and reach the SRV. Deliberately out of scope: the IPv6 groups (`FF02::1:3`/`FF02::FB`) — the v6 stack has no arbitrary-group send path — and TTL expiry of the passive cache, whose entries are only removed by an explicit goodbye. The §8.2 tiebreak compares sorted A records rather than the RFC's canonical byte-wise form (same ordering for the only records in play here, but a simplification, not the letter). The responder is host-wide while the setting is per-link, so per-link granularity of *responding* is not modelled; per-link granularity of *resolving* is.
  - **Multicast on an end host was the prerequisite, and it did not exist.** `EndHost.resolveRoute` had no route for 224.0.0.0/4 or 255.255.255.255, so `sendUdpDatagram` returned `false` without emitting anything — even to a group the host had just joined — and `handleIPv4` dropped every multicast packet for not being "for us", although the L2 filter had let it up precisely because the NIC is subscribed. Both halves are fixed: `sendUdpToGroup` derives the destination MAC from the group (RFC 1112 §6.4, reusing `ipv4MulticastToMac` already there for IGMP), sends on every operationally-up link carrying an address, with TTL 1 for a link-local group; and a multicast datagram is delivered to its UDP listener with no port-unreachable in return (answering that to a group would blame someone who never asked).
  - `ospf/OSPFEngine.ts`'s Hello/dead-interval/LSA-aging/LSA-refresh timers and the SPF throttle (RFC 2328 §16.5 exponential back-off) are real, independent `src/events/Scheduler` timers, and neighbor FSMs only advance via genuine `processHello`/`processDD` packet handling — frames are real. But `RouterOSPFIntegration.autoConverge()`/`driveWireConvergence()` (called after nearly every OSPF CLI command, including `show ip route` itself, and on link-up) does a static-registry BFS across the whole reachable domain and synchronously pumps Hellos/DD retransmissions and force-accelerates DR election for every router in one call — a convenience layer, not a bug, but it means convergence always completes before the triggering command returns rather than progressing visibly through ExStart/Exchange/Loading like real IOS. Don't build labs that expect to observe those transient neighbor states under normal CLI use. `RoutingTableSyncActor.onRoutes()` (wired in `enableOSPF()`) is what makes the one case that *isn't* CLI-driven — a dead-interval timeout or other autonomous SPF trigger with no command run afterward — still reach the RIB. Previously related and larger, now fixed (rapport 00 synthesis, item #23): `collectOSPFDomain`/`collectOSPFv3Domain`/`collectV3CandidateRouters`/`findNextHopTo` each duplicated the same "look at a switch's other ports for one more hop" fragment (5 copies total, 3 of them inlined inside `findNextHopTo` alone) — hardcoded to exactly one extra hop, so a router two switches away (R1—SW1—SW2—R2) was never found in any of them. Fixed by extracting the fragment into a single, correct, arbitrary-depth primitive — `resolveAcrossTransparentDevices` (`src/network/equipment/TopologyWalk.ts`) — and migrating all four call sites onto it. Verified via git-stash that the two protocols were affected very differently: OSPFv2's physical adjacency is real-packet-driven (`pumpHellos` sends a genuine Hello that really floods through the switch chain via ordinary switch forwarding, independent of this BFS, and the reply self-heals the missing `allPeers` entry), so a SW1—SW2 OSPFv2 lab already converged before this fix — the bug's confirmed, reproducible impact was on `findNextHopTo` (virtual-link and stub-area default-route next-hop resolution, not primary SPF route computation) and on OSPFv3, whose adjacency (`v3FormAdjacency`) is formed entirely out-of-band with no real packet exchange and thus no fallback — an OSPFv3 SW1—SW2 lab genuinely never formed an adjacency before this fix (`ospf-multi-switch-domain.test.ts`). Deliberately not attempted, and distinct from this item: the *other* half of the audit's phrasing ("un service unique" behind all direct `EquipmentRegistry`/`Equipment.getById` access) — rapport 04's own inventory lists 17 such call sites project-wide (UI store lifecycle, React hooks, DHCP discovery, DNS NSS fallback, IPSec peer lookup, packet-capture routing, traceroute, …), most already marked legitimate-as-is by that same audit, and unifying them behind one service would be a much larger, separate effort overlapping with item #32's already-open casts/encapsulation work — not a bounded extension of this fix.
  - `bfd/BfdAgent.ts` is a real RFC 5880 session (genuine 3-way handshake, independent Tx/detect timers, real UDP/3784 packets) — but it's only coupled to OSPF: `ip ospf bfd`/`bfd all-interfaces` (Cisco) and `ospf bfd enable`/`bfd all-interfaces enable` (Huawei) auto-provision a session per Full neighbor and kill the OSPF neighbor the moment that session leaves `up` (`RouterOSPFIntegration.provisionBfdSessions`/`onBfdSessionDown`, wired from `CiscoRouter`/`HuaweiRouter`'s `bfd.session.changed` subscription). BGP's `neighbor <ip> fall-over bfd` isn't even parsed (falls into the generic attribute catch-all), and EIGRP has no BFD coupling and no equivalent single-neighbor-teardown entry point to hook one to — both remain accepted-syntax-only.
  - `igmp/IgmpAgent.ts` and `pim/PimAgent.ts` are both real packet-driven control planes (genuine membership reports/queries, Hello, and (*,G) Join/Prune with a real upstream-neighbor filter). L2 multicast (`Switch.ts`/`IgmpSnoopingAgent`) was already real. L3 forwarding (`Router.ts`) was not: the whole 224-239 range was treated as always-local-never-forward (only 224.0.0.0/24 actually is, RFC 1112/4541), IGMP membership never reached PimAgent's OIL, and nothing ever replicated data packets across it. Fixed: `processIPv4` now only forces local delivery for 224.0.0.0/24 and routes 224.0.1.0-239.255.255.255 through `forwardMulticast()`, which replicates out `PimAgent.getMroute(group)`'s OIL with an RPF check (against the mroute's `incomingInterface`, falling back to a unicast RIB lookup on the source) and a TTL decrement; `CiscoRouter`/`HuaweiRouter` now subscribe to `igmp.group.joined`/`igmp.group.left` and call `pimAgent.joinGroup`/`leaveGroup` so a directly-connected receiver's membership actually lands in the OIL. Deliberately not attempted (out of scope for this pass): RP-tree/SPT-switchover, register-tunnels, the Assert mechanism, and SSM — only (*,G) sparse-mode-shaped join state (already all `PimAgent` modeled) is used; a group with no RP configured and no PIM neighbor still gets pure last-hop-router OIL replication, which is a reasonable minimal slice but not full PIM-SM.
  - `gre/GreAgent.ts` does real GRE encapsulation/decapsulation (genuine header + outer IPv4 packet over proto 47, verified end-to-end over a real cable), but it is only wired up for Linux's `ip tunnel` command (`Ip.ts`) — Cisco/Huawei's `tunnel source`/`tunnel destination` CLI (`CiscoOspfCommands.ts`) only populates display/OSPF-matching metadata and never calls `greAgent.addTunnel()`, and `Router.forwardPacket()` has no GRE awareness at all, so a route pointing at `Tunnel0` on a Cisco/Huawei router never actually gets encapsulated or transits anywhere. `RouterOSPFIntegration.formAdjacency()` (called for `Tunnel*` ports matched by IP against `tunnel destination`) papers over this by seeding both sides' OSPF neighbor tables directly — "no frame transport on virtual ports yet" per the comment at the call site — instead of exchanging real Hello/DD over the tunnel. This is deliberate, tracked backlog (`docs/roadmap.md` §14.5, "Priorité : Basse"), not an oversight: don't build labs that assume OSPF-over-GRE (or any Cisco/Huawei GRE data-plane forwarding) actually transits the topology.
  - `eigrp/EIGRPEngine.ts` implements the real DUAL *feasibility condition* (successor = lowest FD; a feasible successor needs RD < FD, gated by `variance`/`maximum-paths`) — genuinely more than plain distance-vector. But there is no Active/Passive state, no Query/Reply/Ack, and no RTP (`packets.ts` only defines `hello`/`update` opcodes); a lost successor with no feasible backup just recomputes instantly from cached Update TLVs instead of diffusing a query, and there is no SIA/stuck-in-active concept because there's no Active state to get stuck in. Timers are explicitly documented as absent in the engine's own header: liveness is "a convergence round IS the hello interval," not a wall-clock hold timer — there is no `src/events/Scheduler` usage anywhere under `eigrp/`. Convergence itself is CLI-triggered (`RouterDynamicRouting.converge()`, called from `Router.convergeDynamicRouting()`), not timer-driven; `Router._setupPortMonitoring()` also fires it on link up/down so an autonomous link failure doesn't need an operator to run a `show` first (mirroring, but not literally reusing, the same wiring OSPF has), but this only makes the *existing* recompute run on more triggers — it isn't real timer-driven convergence. Already tracked as backlog: `docs/audit/02-protocoles-L3-routage.md` (item #10, "EIGRP QUERY/REPLY + hold timers réels") and a stale, never-implemented `docs/DESIGN-EIGRP.md` that once scoped real RTP/Active/SIA and was abandoned in favor of the simpler shipped engine.
  - `vtp/VtpAgent.ts` (`docs/PRD-VTP.md` Phase 1) used to conflate two distinct real-Cisco fields under one name: `VtpConfig.updaterMac` (a switch's own fixed chassis MAC, shown as "Device ID" in `show vtp status`) was overwritten on every received Summary with the *sender's* identity — real VTP's "Updater Identity" is a separate, gossiped IP address (the lowest-numbered active VLAN SVI, or the management interface) naming whoever last bumped the revision, and never touches the receiver's own Device ID. Fixed by splitting them: `updaterMac` is now local-only and never mutated by peer sync; `VtpConfig.lastUpdaterIdentity`/`lastUpdateTimestamp` (new fields) carry the learned IP+timestamp, set from `Switch._vtpUpdaterIdentity()` (lowest-VLAN SVI IP, `'0.0.0.0'` if none) on a local revision bump and from the wire on receipt. `show vtp status`'s "Configuration last modified by"/"Local updater ID" lines now read `lastUpdaterIdentity`/`lastUpdateTimestamp` instead of re-deriving a fresh local IP every time. Also added real Subset Advertisement fragmentation (Cisco splits a large VLAN database across multiple numbered Subsets after a Summary declares a follower count): `sendSummaryAndSubset` chunks the VLAN list into 40-VLAN lots and sends one `subset` frame per lot with a `sequenceNumber`, preceded by a `summary` frame's `followers` count; the receiver buffers fragments by sequence number in `pendingSubsetParts` and only calls `vtpApplyVlans()` — which treats its argument as the *complete* target set, deleting anything local not present — once every declared fragment has arrived, discarding/resetting the buffer on a new, non-matching Summary. An incomplete fragment set (peer link drops mid-transfer) therefore leaves the local VLAN database and revision untouched rather than partially applying a truncated diff. The common single-lot case (≤40 VLANs, the overwhelming majority of labs) is unchanged: one `summary` + one `subset`, `followers`/`sequenceNumber` both default to 1.
  - `vtp/VtpAgent.ts` (`docs/PRD-VTP.md` Phase 2) propagates a v3 MST region (`docs/PRD-STP.md §4`'s `MstRegion` — name/revision/instance table) between switches in the same VTP domain, independently of the standard VLAN database. `VtpFrame` gained an optional `database?: 'vlan' | 'mst'` tag (absent/`'vlan'` is today's flow, untouched) and an `mstRegion` payload (the region's `instances: Map<number, string>` flattened to `[number, string][]` for the wire); `VtpConfig.mstDatabaseRevision` is a separate auto-incrementing counter — distinct from both the VLAN database's `revision` and the operator-set `MstRegion.revision` carried as data — bumped by `onLocalMstChange()` (wired from every `CiscoSwitchShell` mutation under `spanning-tree mst configuration`: `name`/`revision`/`instance`/`no`) exactly like `bumpRevision()` does for VLANs. `handleFrame` branches on `payload.database === 'mst'` into a dedicated `handleMstFrame` with its own summary/subset state (`lastMstSummaryDomain/Revision`, `hasSyncedMstDatabase`) completely separate from the VLAN path's — a fresh-join client catches up on an equal revision the same way the VLAN flow does, and a server relays a newly-learned region onward. `StpAgent.applyMstRegion()` (new) is the single call a synced client makes to replace its whole local region (name/revision/instance map) in one shot, mirroring `vtpApplyVlans`'s full-replace semantics rather than diffing instance-by-instance. Unlike the VLAN database, MST regions never fragment across multiple Subsets (real region configs are tiny), so `sendMstSummaryAndSubset` always sends exactly one summary+subset pair; sent on local change, on trunk link-up/mode-change, on an Advertisement Request reply, and on the periodic 300s timer — all gated on `version === 3`, so a v1/v2 domain (still VTP's overwhelming default) never emits an MST-database frame at all, confirmed by `vtp-v3-mst-database.test.ts`'s last case. Deliberately out of scope, per the PRD: Private VLAN association propagation (blocked on `docs/PRD-VLAN.md §2.1.2`, no Private VLAN concept exists anywhere yet) and any Huawei equivalent (VTP is confirmed Cisco-proprietary, `vtp/` has no Huawei wiring at all, by design).
  - `vtp/types.ts`'s `hashPassword()` (`docs/PRD-VTP.md` Phase 3) used to be `md5Hex(\`${domain}|${password}\`)` — a plausible-looking but invented construction, never checked against anything real. Replaced with the actual byte layout: Wireshark's `packet-vtp.c` dissector documents the Summary Advertisement's Management Domain as a fixed 32-byte zero-padded field followed by a 4-byte big-endian Configuration Revision Number, and the Yersinia VTP packet-crafting tool's `vtp_generate_md5()` (real source, since a forging tool has to reproduce what a real switch accepts) documents the digest itself as `MD5(MD5(password) ‖ <domain+revision struct> ‖ MD5(password))` — the password's own digest bookending the struct on both sides, then hashed again. `hashPassword(domain, password, revision)` now builds exactly that (new optional 3rd `revision` param, defaulting to 0 so old 2-arg call sites keep compiling); every `VtpAgent` call site was updated to pass the revision the frame actually advertises — the VLAN database's `config.revision` for ordinary summary/subset/request frames and primary-claims, and `payload.revision` (the sender's claimed revision, not the receiver's own) when verifying an incoming frame's `passwordHash`. Confirmed by the new `tcpdump-vtp-frame-capture.test.ts` (the VTP counterpart to `tcpdump-byte-slice-vlan-filters.test.ts`): the 32-byte domain truncation/padding boundary, the revision field's big-endianness, and Cisco's own documented real-world behavior that the same domain+password produce a different digest per revision, are all pinned by test. Also fixed `vtp-md5-password.test.ts`'s first case, which had asserted the *old* `domain|password` string-concat construction directly — genuinely broken by this change, not a pre-existing false assumption to preserve. Honestly scoped, not literally "byte-exact" against a real capture: Yersinia's real struct also includes `version`, `code`, and the VLAN database bytes, none of which are included here, because no byte-serialization for a `VtpVlanEntry` or an IPv4 "updater identity" exists anywhere else in this codebase to reuse — inventing one to complete the digest would mean stacking a second unverified encoding on top of an already-uncertain one, when the PRD's own stated scope for this phase was specifically domain/revision/password.

So this reuse can only distinguish "a qualifying backup already exists" from "none exists yet," not "this specific file changed since its last backup" — once one covering backup exists, a later `BACKUP` with optimization ON will keep reporting everything as already covered even if the simulator had a way to mutate a datafile in between (it doesn't yet, so this is a latent simplification, not an active wrong answer in today's tests).

### Database simulation (`src/database/`)

- `engine/` — vendor-agnostic SQL engine scaffolding: `lexer/`, `parser/` (AST), `executor/`, `catalog/`, `storage/`, `types/`.
- `oracle/` — Oracle DBMS engine built on the engine layer: `OracleLexer`/`OracleParser`/`OracleExecutor`/`OracleCatalog`/`OracleStorage`/`OracleDatabase`/`OracleInstance`, plus subsystems for `asm/`, `awr/`, `dataguard/`, `flashback/`, `lock/`, `multitenant/`, `plan/`, `metadata/`, `packages/`, `commands/`, `actors/`, `demo/`.
  - `multitenant/` and `dataguard/` are honest state/bookkeeping facades, not physically-isolated engines: `PluggableDatabase` tracks CON_ID/name/open-mode but `OracleStorage` has no CON_ID notion at all — every PDB shares one schema/table namespace, so `ALTER SESSION SET CONTAINER` only swaps the session label (see the comment at `OracleDatabase.ts` around the `ALTER SESSION SET CONTAINER` handler). A "create a table in PDB1, confirm it's absent from PDB2" lab will silently fail. `DataGuardConfiguration.switchover()` likewise just swaps two `role` fields — there is no real redo transport/apply. Don't build pedagogical scenarios that assume real cross-PDB isolation or physical standby replication.
  - DATE columns rendered with no explicit `TO_CHAR` mask (rapport 07, item #48) previously showed either the raw internal `YYYY-MM-DD HH:MM:SS` storage string or, for `SYSDATE`/`FROM DUAL` pseudo-columns specifically, were tagged `VARCHAR2` and never date-formatted at all. Real Oracle defaults every unmasked DATE to `NLS_DATE_FORMAT` (session-scoped, default `DD-MON-RR`, no time-of-day). Fixed: `QueryResultRenderer.renderValue()` now formats any `isDate` column (or bare `instanceof Date` value) through `formatDateWithPattern()` using the session's `nlsDateFormat` (`SQLPlusSession.formatQueryResult` reads it off `session.nlsDateFormat`; `OracleDatabase.execAlterSession` writes it on `ALTER SESSION SET NLS_DATE_FORMAT`); `ScalarFunctionEvaluator`'s `TO_CHAR` falls back to the same session default when called with no format arg, and now runs `coerceDate()` (handles both a genuine `Date` object and a date-string) instead of the old `typeof === 'string'`-only check, which silently fell through to JS's own `Date.prototype.toString()` for a real `Date` value. Pseudo-column type inference (`SYSDATE`/`CURRENT_DATE` → DATE, `SYSTIMESTAMP`/`CURRENT_TIMESTAMP` → TIMESTAMP, previously always `VARCHAR2`) had to be added in two separate places — `OracleExecutor.expandSelectItems` (table-based `SELECT`) and `executeSelectFromDual` (a wholly separate `FROM DUAL` pipeline that never calls `expandSelectItems`) — since fixing only the former left `SELECT SYSDATE FROM DUAL` still showing a full timestamp. Also added real `RR` century-rollover semantics (`resolveRRYear` in `dateSupport.ts`) alongside the pre-existing `YY` handling, for both formatting and `TO_DATE` parsing. Not attempted: PL/SQL-block `TO_CHAR` (`functions/conversionFunctions.ts`, a separate implementation reached only from inside `BEGIN...END` via a `SqlFunctionContext` that doesn't carry clean session access) still ignores `NLS_DATE_FORMAT` and is a smaller, separate, still-open gap.
  - `SELECT … FOR UPDATE` row-level locking (rapport 07, item #49): `LockManager.rowLocks` (`lock/LockManager.ts`) genuinely tracks which session owns which row, and `NOWAIT`/`SKIP LOCKED` were already correctly wired in `OracleExecutor.lockForUpdateRows()` — but a *plain* `FOR UPDATE` (no wait clause) or `FOR UPDATE WAIT n` against a row another session already held just fell through to `out.push(row)` and silently handed over the row as if the lock had been granted, without ever calling `acquireRowLock`. Two sessions could each believe they held the same row's lock — the core mutual-exclusion guarantee FOR UPDATE exists for was broken exactly when no `NOWAIT` was written. Real Oracle instead blocks the statement (indefinitely for plain `FOR UPDATE`, up to `n` seconds for `WAIT n`) until the holder commits/rolls back, but `OracleExecutor`/`OracleDatabase`/`SQLPlusSession`/`SqlPlusSubShell` are a fully synchronous call chain with no per-statement suspend/resume concept — genuine blocking would need a promise-based wait queue in `LockManager` threaded through that whole chain as `async`, which `ISubShell.processLine`'s `SubShellResult | Promise<SubShellResult>` signature and `interruptForeground()` hook (`terminal/subshells/ISubShell.ts`) already anticipate structurally (per its doc comment, another subshell already returns async), but which touches the single synchronous `OracleExecutor.execute()` core shared by every statement type (DDL, DML, PL/SQL, triggers, scheduler jobs) — a cross-cutting refactor, not a bounded fix. Fixed the bounded half instead: a plain `FOR UPDATE` or `WAIT n` against an already-held row now denies immediately (`ORA-00054`/`ORA-30006` respectively) rather than silently granting a second, phantom lock — trading "hangs forever" for "fails fast," which is honest given the architectural constraint and strictly safer than the previous silent double-grant. `LockManager.lockTable()` (TM/table locks, not row locks) has the identical "record a fake wait, never actually suspend the caller" pattern — tracked separately as item #50, not touched here.
  - TM (table) lock enforcement for ordinary DML (rapport 07, item #50): `LockActor` used to acquire a DML statement's TM lock reactively, off the `oracle.dml.executed` event — which only fires *after* `OracleExecutor.execute()` has already run the INSERT/UPDATE/DELETE against storage (`emitForStatement`/`emitDml` are called post-execution). The lock therefore never protected anything; it was pure `V$LOCK`/`DBA_DML_LOCKS` bookkeeping applied after the fact, and `LockManager.acquireDmlLock`'s catch swallowed everything but `DeadlockError` on top of that. A session holding an explicit `LOCK TABLE t IN EXCLUSIVE MODE` (or any stronger mode) could not actually stop another session's plain DML on that table. Fixed: `OracleExecutor.dispatchStatement()` now calls a new `acquireDmlTableLock()` *before* dispatching to `executeInsert`/`executeUpdate`/`executeDelete`, and `LockManager.acquireDmlLock()` denies immediately (`ORA-00054`) on a real conflicting held lock instead of registering `lockTable()`'s usual fake-pending/wait-for-later entry — same "can't block, so fail fast rather than silently let it through" reasoning as item #49, and low blast radius since ordinary DML's own Row-X(3) mode never conflicts with another session's plain DML (only with an explicit stronger `LOCK TABLE`). `LockActor` no longer subscribes to `oracle.dml.executed` at all (release-side subscriptions — commit/rollback/disconnect — are unchanged and still correct). Explicit `LOCK TABLE`'s own fake-pending/`DBA_WAITERS`/`DBA_BLOCKERS`/`V$SESSION.BLOCKING_SESSION` observability (`execLockTable`, still calling `lockTable()` directly) was deliberately left untouched — those views are a deliberately-accepted simplification for that specific statement, not the MAJEUR-rated complaint this item targets. Not attempted: deadlock detection reachable via pure DML (rated MINEUR in the source audit, and structurally still unreachable regardless of acquisition timing since two Row-X(3) locks never conflict with each other in the compatibility matrix — deadlock among plain DML statements requires a modeled conflict path this simulator doesn't have).

### State management (`src/store/`)

Single Zustand store (`networkStore.ts`) holds the full topology: devices (`NetworkDeviceUI[]`), connections (`Connection[]`), and UI state. The store bridges `Equipment` instances to React rendering. `topologySerializer.ts` handles save/load of topologies.
- `NetworkCanvas`/`PropertiesPanel` subscribe to the whole store (no per-field selector, see item #52's note above on why that's deliberately not narrowed), so any zustand `set()` anywhere re-renders them and picks up a fresh `getDevices()` snapshot of live `Equipment` state. That's fine for CLI-triggered changes — the CLI action itself is a store-adjacent event — but until fixed (rapport 09, item #56) it meant an autonomous change with no `set()` anywhere in its path never reached the canvas at all: a port going admin-down or carrier-down from a dead-interval timeout, a DHCP lease clearing an interface's IP on expiry, an autonomous SPF recompute reaching the RIB via `RoutingTableSyncActor` — none of these ever call into zustand (`src/network/` never imports the store, confirmed by grep), so the connection/interface data on canvas stayed visually frozen until some unrelated store action happened to fire afterward. Fixed by bridging a small, explicit topic allowlist off the default `EventBus` (`getDefaultEventBus()`, the "OBSERVER bus (Logger/UI/tests)" per its own header comment — already the intended hook-in point, not a repurposing) into a `revision` bump: `port.link.up`/`port.link.down`/`port.config.ip-changed` — exactly the topics behind the two fields `NetworkDeviceUI.interfaces` actually renders (`isUp`, `ipAddress`); DHCP lease grant/renew/expire and static/manual IP changes all funnel through `port.config.ip-changed` already (`Port.configureIP`/`clearIP`), so no separate DHCP-specific subscription was needed. Deliberately NOT `bus.subscribeAll()`: the same bus also carries a `port.frame.*`/`cable.frame.*`/`ospf.packet.*` event per Ethernet frame and a `device.position-changed` per drag-pixel, and reintroducing that volume would undo item #52's re-render fix. The subscription is (re-)established from `getDevices()` itself (cheap reference check against the last-subscribed bus) rather than once at module load, specifically because `setupGlobalState.ts`'s global `beforeEach` nulls the default EventBus before every test (`__setDefaultEventBus(null)`) — a naive one-time subscription would silently go dead against the discarded bus and only ever work in the first test of a file; `canvas-autonomous-events.test.ts`'s "rebridges after the default EventBus is swapped" case covers exactly this. Note this fix is scoped to what's actually rendered today: OSPF neighbor/SPF events, STP role changes, and HSRP/VRRP/GLBP active/standby are real and event-driven but have no corresponding field on `NetworkDeviceUI` to refresh, so they're deliberately not in the allowlist — add them if a future UI surface ever renders that state.
- `topologySerializer.ts` captures a real, wide slice of configurable device state (see the file's own header comment: interfaces, static routes/ARP, every modified Linux file, VLAN/switchport config, and full running/startup vendor config text replayed through the real CLI on import) — but until fixed (rapport 09, item #55), none of what it *doesn't* capture was ever disclosed to the user, and Save/Export/Open/Import were silent about it either way. What's genuinely lost on a round-trip: terminal sessions and scrollback (actively torn down on import — `clearAll()` triggers `registry.cleared`, which `TerminalManager.disposeAll()` subscribes to), live TCP/SSH transport state (a fresh `Equipment` instance is created on import; the old one's sockets go with it), and dynamic protocol/runtime state (OSPF LSDB, BGP RIB, DHCP lease bindings) — only the *config* that produces these is captured, so a reloaded topology must reconverge from scratch rather than resuming mid-state. Fixed the disclosure half: `TOPOLOGY_SAVE_CAVEATS` (exported from `topologySerializer.ts`) is now shown as plain text in `SaveTopologyDialog` and as the body of a new confirm step gating `Export` (previously Export had no dialog at all — it just downloaded a file). Also fixed an adjacent silent-loss gap in the same family: `Open`/`Import` used to discard the current canvas with zero warning; both now route through a `ConfirmDialog` ("Replace current topology?"/"Replace current topology's contents") when the canvas isn't empty, reusing `OpenTopologyDialog`'s existing nested-`ConfirmDialog` pattern from item #54 via a new `confirmReplace` prop. Deliberately not attempted: actually capturing the excluded state (terminal sessions, live sockets, LSDB/RIB/lease tables) is a materially larger lift with no existing schema fields or capture functions to extend, and is out of scope here. Also deliberately not attempted, and worth flagging as its own gap: Linux user accounts created via `useradd`/`passwd` *look* preserved (their `/etc/passwd`/`/etc/shadow`/`/etc/group` text is plain-written to the VFS via `IamFilesystem.writeAccountDatabase()`, so `captureLinuxFiles()` genuinely captures the changed text and `restoreLinuxFiles()` writes it back verbatim) but are not functionally restored — there is no reverse-parse anywhere in the codebase to rehydrate `LinuxUserManager.users`/`groups` (the in-memory model `su`/login/permission checks actually consult) from that restored file content; the only `parsePasswd`/`parseShadow` functions that exist (`iam/PwGrCheck.ts`) back the read-only `pwck`/`grpck` commands, not account loading. A fresh imported device therefore still only has the default `root` account even though `cat /etc/passwd` shows otherwise. Not fixed here: `LinuxUserAccount` carries ~15 fields (uid/gid, shadow aging fields, lockout bookkeeping like `lastFailedLoginAt` that isn't in `/etc/shadow` at all) — correctly reconstructing it is a bigger, separate lift than the bounded disclosure fix this item covers.

Deliberately out of scope: `updateDevice` (property-panel edits like hostname/interface config) is not undoable, a restored device comes back powered off with no terminal session restored, and undo/redo themselves don't push new history entries (an undo can't be "redone-away" by a stray extra undo).
- `terminal/TerminalView.tsx` — terminal renderer.
  - Two bounded fixes (rapport 09, item #53): (1) the scroll-to-bottom `useEffect` ran unconditionally on every render (no "am I at the bottom?" check), so a stream (`tail -f`, continuous ping, `debug ip ospf`) yanked the view back down on every new line — the user could never scroll up to read earlier output. Fixed by tracking a `stuckToBottom` flag (an `onScroll` handler recomputes it from `scrollHeight - scrollTop - clientHeight`) and only forcing `scrollTop` while it's true — the same live-tail pattern already correct in `NetworkLogsPanel.tsx`. (2) Scrollback is configurable up to 50,000 lines (`TerminalModal.tsx`) with one `<pre>` per line and no virtualization — every past line stayed a live DOM/layout node forever. `LineRenderer` was already memoized, so reconciliation was bounded, but layout/paint wasn't. Fixed with the audit's own suggested minimal correctif: each line is wrapped in a `content-visibility: auto` + `contain-intrinsic-size` div, letting the browser skip layout/paint for scrollback that isn't near the viewport without changing the render tree or any scroll/selection/search interaction. Trade-off (matches MDN's own guidance for long lists): a wrapped multi-row line gets a brief height correction once it scrolls into view, since the single-row `contain-intrinsic-size` estimate can't predict wrapping. Manual windowing (rendering only a slice of `session.lines`) would avoid that trade-off but is a bigger change touching scroll-position math, search-within-scrollback, and selection across virtualized rows — not attempted here.
- `editors/` — Vim and Nano editor emulation.
- `ui/` — shadcn/ui components (Tailwind + Radix).
- `pages/` — route-level pages (`Index.tsx`, `NotFound.tsx`); routing via `react-router-dom`.

### Tests (`src/__tests__/`, `e2e/`)

- `unit/network-v2/` — the bulk of protocol and device unit tests (250+ files): per-protocol tests (`ospf.test.ts`, `bgp-engine.test.ts`, `cisco-stp.test.ts`, `dhcp_complete.test.ts`, …), bash/awk/grep interpreter tests, cross-vendor SSH suites, etc.
- `unit/database/`, `unit/powershell/`, `unit/bash/`, `unit/shell/`, `unit/terminal/`, `unit/terminal-core/`, `unit/events/`, `unit/react/`, `unit/gui/` — subsystem-specific unit tests.
- `debug/` — large "transcript dump" suites (`*.debug.test.ts`, often 60-400+ steps) that drive a simulated lab through long command sequences and dump the output for gap analysis (e.g. `cisco/`, `huawei/`, `oracle/`, `cmdlets/`, `protocols/`, `rman/`, `router/`). These are diagnostic tools, not assertions-based tests — read the `_*-suite.ts` helpers in each subfolder to understand how labs are built.
- `e2e/` — Playwright specs (`*.spec.ts`) driving the real browser UI (drag-and-drop, SSH between devices, network logs). Config in `playwright.config.ts`; runs against `npm run dev` on port 8080.
- Until fixed (rapport 09, item #57), every spec that needed a lab topology built it by calling `store.getState().addDevice`/`addConnection` directly in `page.evaluate` and only drove the terminal/CLI layer through real DOM interaction — nothing exercised the actual pointer-driven cabling gesture or the Save/Open dialogs (items #54/#55) through the browser, despite ~123 spec files existing. `canvas-cable-save-flow.spec.ts` closes that gap: places two devices via the palette's accessible add-button, cables them through the real Connect flow, and round-trips the result through Save then Open. Two non-obvious things worth knowing if extending it: (1) cabling is click/keyboard-driven, not a drag gesture — `NetworkDevice.tsx`'s `handleMouseDown` calls `selectDevice`/opens `InterfaceSelectorPopover` on plain clicks (`startConnecting`/`finishConnecting`), so ordinary Playwright `.click()` works with no special drag choreography (device *placement*, by contrast, genuinely is HTML5 DnD when driven via the palette's `draggable` button — see `dnd-first-attempt.spec.ts`'s manual `DragEvent` dispatch for that case, since Playwright's built-in `dragTo()` doesn't reliably fire native DnD events here); (2) `InterfaceSelectorPopover`'s own Cancel/X button renders *before* the interface-row buttons in DOM order and is never `disabled`, so a naive `button:not([disabled])` locator clicks Cancel instead of an interface — a real failure hit while writing this spec, not a hypothetical; select interface rows via `button:not([disabled]):not([aria-label="Cancel interface selection"])` instead. Save/Open's dialogs are plain Radix `Dialog`s (`role="dialog"`, portalled to `document.body`); the "replace current topology?" confirm they can trigger is an `AlertDialog` (`role="alertdialog"`) — the distinct role is what disambiguates the two stacked dialogs without needing a `data-testid`.
- Vitest environment is `node` (configured in `vite.config.ts`); globals enabled. Coverage is currently scoped to `src/network/protocols/ssh/**` with thresholds (lines/functions/statements 85%, branches 75%).
- `setupFiles: ['./src/__tests__/setupGlobalState.ts']` (rapport 08, item #51) runs a global `beforeEach` resetting `EquipmentRegistry`/device-name counters (`resetDeviceCounters()`, which also calls `Equipment.clearRegistry()`), MAC/ID counters (`resetCounters()`), `Logger`, and the default `EventBus`/`Scheduler` singletons (`__setDefaultEventBus(null)`/`__setDefaultScheduler(null)`, forcing a fresh instance on next `getDefaultEventBus()`/`getDefaultScheduler()`) before every test in every file. This was the audit's own highest-value, lowest-cost recommendation: 834 of ~1344 test files already call some subset of these resets by hand in a local `beforeEach`, and a forgotten or incomplete one let one `it()` block pollute the next *within the same file* (Vitest's default per-file `isolate: true` already prevents pollution *across* files). The new global hook is a backstop, not a replacement — existing manual resets are untouched and stay harmless no-ops where this hook already did the work. Deliberately scoped to only the globals shared by virtually every test regardless of subsystem; subsystem-specific singletons (`resetAllOracleInstances()`, `resetPkiCaRegistry()`, `resetForestRegistry()`, `resetExchangeOrganizations()`, …) remain each test file's own responsibility, both because they're needed by a much smaller fraction of files and because pulling e.g. `terminal/commands/database.ts` into a universally-loaded setup file would add import cost to every single test file regardless of whether it touches Oracle. Verified with two full clean-state A/B comparisons (with vs. without this file) across `unit/database/` (3115 tests), the rest of `unit/` excluding `network-v2` (3927 tests), and multiple individually-reproduced `unit/network-v2/` cases spanning unrelated failure categories (SSH session/connection-count timing, Windows Event Log "gap confirmé" tests) — identical results either way, confirming this change fixes the flakiness class without altering behavior of any currently-passing test.

## Conventions worth knowing

- Production builds set `esbuild.keepNames: true` and `build.minify: 'esbuild'` because the simulator dispatches on `instance.constructor.name` (e.g. `=== 'WindowsPC'`) to choose vendor-specific behavior — default minification would break this (see comment in `vite.config.ts`).
- Reactive protocol engines (OSPF, IPSec, DHCP, BGP, routing) follow a consistent shape: `<Protocol>Engine.ts` + `types.ts` + `events.ts` + `observables.ts` + `actors/` built on `src/events/` primitives — follow this pattern when adding a new protocol.
- `@typescript-eslint/no-unused-vars` is disabled project-wide in `eslint.config.js`.
