Le filtre ouvert

L'implémentation des listes de contrôle d'accès Cisco de ce simulateur affiche deny et rend permit. Dix-neuf constats mesurés, dont sept qui inversent la règle écrite par l'opérateur.

Les sept constats qui ouvraient le filtre — F-01, F-02, F-03, F-04, F-06, F-09, F-10 — sont traités, ainsi que F-18 par effet de bord. Une règle d'échec unique a été posée et documentée en tête de la fonction de correspondance : un critère que le moteur ne sait pas trancher fait échouer la correspondance — jamais réussir, jamais « sauter le critère ».

Onze constats restent ouverts, dont le plantage TypeError sur VTY/NTP/NAT (F-07) et la perte de configuration IPv6 (F-15). Le corps du rapport ci-dessous décrit l'état au moment de l'audit ; il est conservé tel quel comme constat daté. La colonne « État » du tableau et la section Remédiation donnent la situation à jour.

Verdict

Ce n'est pas une formule : sur les dix-neuf défauts mesurés, sept inversent le sens de la règle écrite. Et l'inversion ne demande aucune manipulation exotique — il suffit d'écrire un commentaire.

R1(config)# ip access-list extended BLOCK R1(config-ext-nacl)# remark bloque le VLAN invité ← ce commentaire annule les deux lignes suivantes R1(config-ext-nacl)# deny ip 10.0.0.0 0.0.0.255 any R1(config-ext-nacl)# permit ip any any

Paquet source 10.0.0.5 — la première règle de la liste dit explicitement « refuser ».

Écrit deny → Rendu par le moteur permit

Le remark est enregistré comme une entrée permit de source 0.0.0.0/255.255.255.255, et la fonction de correspondance ne teste jamais le champ remark. Le commentaire est donc la première règle, il correspond à tout, et il rend un permit. Toute ACL de ce simulateur contenant un commentaire est une ACL ouverte. Elle s'affiche correctement sous show access-lists, elle se relit correctement dans show running-config, et elle ne bloque rien.

C'est la pire catégorie de défaut qu'un dispositif de sécurité puisse avoir : il n'échoue pas, il ment. Un pare-feu absent est un risque connu ; un pare-feu qui affiche deny et rend permit est un risque que personne ne cherche.

Sur un simulateur pédagogique, la conséquence est directe : l'outil enseigne activement le contraire de ce qu'il prétend enseigner. Un étudiant qui écrit une ACL correcte, la commente comme on lui a appris à le faire, et observe que le trafic passe, en conclura que sa règle est fausse. Elle ne l'est pas. C'est le simulateur qui l'est.

Ce qui aggrave le jugement

Le moteur IPv6 du même dépôt, Ipv6AclEngine.ts, traite exactement les deux mêmes concepts — remark et evaluate — et les traite correctement :

// Ipv6AclEngine.ts:67-71 if (entry.remark !== undefined) return false; // A reflexive-list reference has no session table behind it here, so it // matches nothing rather than everything — failing an unbacked clause // CLOSED is the rule this repo already applies to `RoutePolicy`. if (entry.evaluate !== undefined) return false;

Le commentaire énonce la règle. Le fichier v4, à cent lignes de là, la viole.

Le commentaire dit explicitement : « faire échouer une clause non étayée en mode FERMÉ est la règle que ce dépôt applique déjà ». Cette règle est énoncée, justifiée, et appliquée dans le fichier IPv6 — et violée dans le fichier IPv4 d'à côté, celui qui porte la quasi-totalité du trafic.

Ce n'est donc pas une lacune de compétence. C'est une lacune de rigueur : la bonne réponse existait dans le dépôt, et n'a pas été propagée.

Le détail des bloquants

F-03Les drapeaux TCP sont décoratifs

Le CLI analyse match-any / match-all et remplit opts.tcpFlags. L'affichage le réaffiche fidèlement. aclEntryMatches ne le lit jamais.

Conséquence mesurée : deny tcp any any match-any rst refuse un paquet SYN. Le critère disparaît, la règle dégénère en deny tcp any any.

Le défaut est bidirectionnel : sur un deny il sur-bloque (déni de service silencieux), sur un permit il sur-autorise. L'ACE fait toujours autre chose que ce qui est écrit — et show access-lists réaffiche le texte d'origine, ce qui rend le diagnostic impossible depuis l'intérieur du simulateur.

F-09La numérotation Huawei contamine le routeur Cisco

// ACLEngine.ts:151 const type = (id < 100 || (id >= 2000 && id <= 2999)) ? 'standard' : 'extended';

2000–2999 est la plage des ACL de base Huawei. Sur IOS, 2000–2699 sont étendues.

Les deux conventions sont inversées. Une ACL 2500 est typée standard, donc la correspondance retourne true dès que la source correspond : destination, protocole et ports sont abandonnés sans un mot.

Mesuré : access-list 2500 permit tcp 10.0.0.0 0.0.0.255 host 192.168.1.1 eq 22 rend permit pour un paquet vers 8.8.8.8:443.

C'est le symptôme d'un défaut d'architecture : un moteur unique sert deux vendeurs aux conventions incompatibles, sans porter la moindre notion de vendeur. Le fichier trahit le mélange — ACLEngine.ts exporte formatHuaweiAclEntry(), une fonction de rendu VRP, depuis le module de moteur.

F-04 · F-06Le typo est une ouverture

// ACLEngine.ts:357-358 (ICMP) — DSCP et precedence suivent le même patron const expected = ACL_ICMP_KEYWORD_TO_TYPE[entry.icmpType]; if (expected !== undefined && expected !== pktType) return false;

Mot-clé absent de la table → undefined → le critère est purement sauté.

L'écart est large. Le validateur CLI accepte 23 mots-clés ICMP ; la table d'évaluation en connaît 11. Treize mots-clés parfaitement valides passent la validation puis sont abandonnés à l'évaluation : administratively-prohibited, source-quench, packet-too-big, parameter-problem, traceroute, router-advertisement, router-solicitation, mask-request, mask-reply, timestamp-request, timestamp-reply, information-request, information-reply.

Le CLI dit oui, le moteur oublie. Pire : les 11 mots-clés connus ne se projettent que sur 5 types distincts — la table écrase quatre variantes d'unreachable sur une seule valeur.

Mesuré : deny icmp any any administratively-prohibited refuse un echo-request. Le sens correct est l'inverse : un critère qu'on ne sait pas évaluer doit faire échouer la correspondance.

F-07Une ACL étendue sur VTY plante le routeur

// Router.ts:4461 — le `as never` supprime la seule protection qui aurait alerté evaluateAclPermit(acl: string, srcIp: string): boolean { return this.aclEngine.evaluateACLByName( acl, { type: 'ipv4', sourceIP: new IPAddress(srcIp) } as never) === 'permit'; }

Sonde sans destinationIP — sur une ACL étendue, la correspondance appelle .getOctets() sur undefined.

Mesuré : TypeError: Cannot read properties of undefined (reading 'getOctets').

Ce point d'évaluation est, d'après son propre commentaire, partagé par NAT, VTY et ntp access-group — la mutualisation est vantée comme une garantie de cohérence. L'exécution mutualise un défaut au lieu d'une réponse : les trois chemins plantent ensemble. Or une ACL NAT étendue (access-list 101 permit ip 10.0.0.0 0.0.0.255 any) est la forme canonique.

F-15Rentrer dans une ACL IPv6 l'efface

Mesuré : une ACL de 2 règles retombe à 0 règle au simple fait de retaper ipv6 access-list V6 pour l'éditer. Sur IOS, ré-entrer dans une ACL nommée ouvre la liste existante en ajout — c'est le geste le plus banal de l'édition d'ACL.

Comme l'ACL reste liée à l'interface, elle passe silencieusement de « filtre » à « liste vide », c'est-à-dire à permit inconditionnel.

La forme — comment on en est arrivé là

Le fond est grave ; la forme indique comment il l'est devenu.

// CiscoAclCommands.ts:437-439, au milieu d'une fonction d'enregistrement for (let n = 1; n <= 99; n++) { void n; }

Une boucle de 99 tours qui ne fait rien. Elle a survécu à la revue, au lint, et à tous les commits suivants.

Autres résidus dans le même fichier : parsePort() jamais appelée, consumedAfterSource() qui rend toujours 0 derrière un ?? dont l'opérande gauche n'est jamais nul, une variable bindings déclarée et jamais lue, un paramètre _aclType ignoré.

Le lint parle, personne n'écoute. CLAUDE.md affirme que no-unused-vars est « disabled project-wide ». C'est faux : eslint.config.js le règle sur warn, la règle tourne, et elle trouve exactement le code mort de cet audit — parsePort et bindings sont signalés nommément sur les seuls fichiers ACL.

Le constat est donc pire qu'un outil éteint, et différent : le signal existe, il est juste, et il est ignoré. Éteindre une règle est une décision ; laisser une règle crier dans le vide en est une aussi, moins avouée. S'y ajoute une documentation fausse : qui lit CLAUDE.md conclut que ce détecteur n'existe pas, et n'ira jamais voir ce qu'il dit.

Ce n'est pas un détail de style : dans un moteur de sécurité, un champ déclaré et jamais lu est la signature exacte de F-03, F-17, F-02 et F-05 — tcpFlags, log, evaluate, icmpCode. L'outil qui pointe vers la classe de bug dominante du projet tourne déjà ; il suffisait de le lire. (La boucle vide ci-dessus lui échappe légitimement : void n compte comme une utilisation. Celle-là, seul un relecteur humain pouvait l'arrêter.)

Neuf champs sur vingt-neuf sont des façades. Acceptés par le CLI, stockés, réaffichés par show et running-config, sans aucun effet : icmpCode, tcpFlags, reflect, reflectTimeout, evaluate, optionName, remark, log, logInput. Un tiers de la surface déclarée est décoratif — et comme le rendu est fidèle, rien dans le simulateur ne permet de distinguer un champ qui agit d'un champ qui décore.

Les compteurs sont pollués. evaluateACL incrémente matchCount à chaque appel, quel que soit l'appelant — IPSec, NAT, VTY, HTTP, et le filtre d'affichage de debug ip packet. Taper debug ip packet 101 fait donc monter les compteurs de l'ACL 101 : show access-lists cesse de mesurer le trafic pour mesurer l'activité de l'observateur. C'est exactement l'outil qu'un étudiant utilise pour vérifier si sa règle est atteinte, et il est faussé par l'acte de regarder.

Le dispositif de test

Quatre suites ACL, 83 tests, tous au vert. Elles détectent 0 des 19 défauts.

Ces 83 tests ne sont pas mauvais : ils vérifient consciencieusement que permit autorise et que deny refuse sur des ACL nominales. Ils partagent tous le même angle mort — ils n'écrivent que des ACL correctes et simples. Aucun n'ajoute de commentaire, aucun ne teste une clause non étayée, aucun ne fait une faute de frappe, aucun ne passe un paquet incomplet, aucun n'utilise 2500 comme numéro.

Or c'est exactement là que vit la totalité des défauts. Le banc de preuves joint établit qu'un contre-test coûte une dizaine de lignes. Le coût n'était pas l'obstacle. L'obstacle est méthodologique : la suite valide que la fonctionnalité marche, jamais qu'elle ne cède pas. Pour du filtrage, c'est la moitié du travail — et la moins importante.

Enfin, la couverture est configurée pour ne mesurer que src/network/protocols/ssh/**. Le moteur ACL — le composant de sécurité central de ce simulateur — n'est sous aucun seuil de couverture.

Ce qui est juste

Vérifié et correct

  • L'ordre des opérations ACL/NAT est exact, dans les deux sens. ACL entrante avant traduction entrante, ACL sortante après traduction sortante — précisément l'ordre documenté par Cisco, et un point que beaucoup d'implémentations manquent.
  • La correspondance par masque générique est correcte, y compris sur les masques non contigus.
  • established teste bien ACK ou RST — conforme.
  • Le refus produit un ICMP administratively-prohibited (code 13), correctement conditionné par no ip unreachables. Un raffinement que peu de simulateurs implémentent.
  • Le résolveur de plages horaires est correctement branché et applique la sémantique « ACE inactive → règle suivante ».
  • Ipv6AclEngine.ts est un bon fichier : la permission implicite des messages de découverte de voisins est correctement placée après la boucle de règles, la posture d'échec est fermée, et l'exposé du piège en tête de fichier est de qualité professionnelle.

La compétence n'est pas en cause. La discipline l'est.

Remédiation

Palier 0 · fait 16 août 2026

Une règle d'échec unique a été posée et documentée en tête de aclEntryMatches : un critère que le moteur ne sait pas trancher fait échouer la correspondance — jamais réussir, jamais « sauter le critère ». Les cinq points en découlent.

  1. F-01, F-02 — remark et evaluate ne correspondent plus à rien. Un commentaire redevient un commentaire ; une référence réflexive non étayée échoue fermé, comme dans Ipv6AclEngine.
  2. F-04, F-06 — mot-clé ICMP, DSCP, precedence ou ToS non résolu ⇒ pas de correspondance. La table ICMP porte désormais un commentaire expliquant que ICMPType ne modélise que cinq types, et pourquoi les autres échouent fermé plutôt que d'être inventés.
  3. F-03 — match-any / match-all sont évalués, préfixes + / - compris. Le mode est conservé (il était perdu : match-all était stocké comme match-any) et rendu correctement par show. Un nom de drapeau inconnu échoue fermé.
  4. F-09 — la numérotation devient une politique injectée (AclNumbering), IOS par défaut ; HuaweiRouter et HuaweiSwitch posent VRP_ACL_NUMBERING. Le moteur ne devine plus la convention d'un vendeur.
  5. F-10 — un critère de port sans couche 4 échoue fermé, tandis qu'une ACE sans critère de port continue de correspondre. La distinction est testée dans les deux sens.

Effet de bord : F-18 tombe avec F-01 — un remark n'accumule plus de compteur.
Vérification : 17 tests de non-régression, plus 134 fichiers / 2200 tests des suites ACL, NAT, IPSec, VTY, sécurité et pare-feu — tous verts. Aucune erreur de typage nouvelle.

Palier 1 court terme
  1. F-07 — sonde complète pour VTY/NTP/NAT ; supprimer as never et as any, puis réparer ce que le typage révélera.
  2. F-15 — ré-entrée en ajout, jamais en écrasement.
  3. F-16 — % Invalid input detected sur tout jeton inconnu. À faire avant les paliers suivants : sans cela, aucune correction ne sera visible pour l'utilisateur qui se trompe.
  4. F-17 — journaliser sur log/log-input, ou retirer les mots-clés du CLI.
Palier 2 fidélité IOS
  1. F-05, F-08, F-11, F-12, F-13, F-14, F-18, F-19.
Palier 3 structure · le seul qui empêche la récidive
  1. Écrire la règle d'échec dans CLAUDE.md : tout critère ACL non évaluable fait échouer la correspondance. Sans règle écrite, F-01 reviendra sous un autre nom.
  2. Séparer moteur et politique vendeur ; sortir formatHuaweiAclEntry du moteur.
  3. Supprimer le code mort et réactiver no-unused-vars au moins sur src/network/** — c'est le détecteur automatique des champs-façades.
  4. Étendre le seuil de couverture au moteur ACL.
  5. Convertir le banc de preuves en suite de non-régression : chaque test inversé devient la garantie que le défaut ne revient pas.

Le simulateur reproduit correctement la plomberie des ACL — l'ordre par rapport au NAT, les masques génériques, les ICMP de refus, les plages horaires. Ce sont les parties difficiles, et elles sont faites.

Il échoue sur la sémantique de sécurité, et il y échoue systématiquement dans la même direction : vers l'ouverture. Neuf champs déclarés sans effet, sept chemins qui inversent la règle écrite, un remark qui annule une liste, et 83 tests verts qui n'en voient aucun.

Le défaut racine n'est aucun des dix-neuf. C'est l'absence d'une règle écrite sur la posture d'échec — une règle que ce dépôt connaît, puisqu'elle est énoncée et justifiée dans Ipv6AclEngine.ts, et qu'il n'a jamais promue au rang de convention. Les dix-neuf constats sont les feuilles ; celle-là est la racine. Corriger les feuilles sans la racine garantit la repousse.

Recommandation initiale. Traiter le palier 0 comme un correctif bloquant. En l'état, l'implémentation ACL Cisco de ce simulateur n'est pas pédagogiquement utilisable : un étudiant qui suit les bonnes pratiques enseignées — commenter ses ACL — obtient une liste ouverte, sans le moindre signal.

Suite donnée — 16 août 2026

Le palier 0 est traité. Les sept chemins qui inversaient la règle écrite sont fermés, et la règle d'échec est posée noir sur blanc en tête de la fonction de correspondance. Une liste commentée filtre à nouveau, match-all veut dire match-all, et le moteur ne devine plus la convention de numérotation d'un vendeur.

Ce que cela ne règle pas. Onze constats restent ouverts, dont deux sérieux : le plantage TypeError sur toute ACL étendue évaluée par VTY, NTP ou NAT (F-07), et la perte silencieuse de configuration à la ré-entrée dans une ACL IPv6 (F-15). Et F-16 reste le multiplicateur : tant qu'un jeton inconnu est avalé sans un mot, une faute de frappe continue de produire une ACE silencieusement différente de ce qui a été tapé — un correctif de sémantique ne protège pas contre une commande mal lue.

Ce qui reste le vrai risque. Le défaut racine est structurel, pas ponctuel. La règle d'échec vit aujourd'hui dans un commentaire de ACLEngine.ts — soit exactement la situation qui prévalait dans Ipv6AclEngine.ts avant cet audit, et qui n'a pas empêché le moteur v4 de faire quatre fois le choix inverse. Tant que la règle n'est pas promue en convention de projet, rien ne garantit que le prochain critère ajouté à une ACE échouera fermé.
