**Version** : 1.0
**Date** : 2026-07-07
**Projet** : Ubuntu Sandbox — simulateur réseau navigateur
**Auteur** : Claude (agent), à la demande de l'utilisateur
**Références normatives** :
- IEEE 802.1Q-2018 (VLAN tagging — format du tag, TPID/TCI, Native VLAN, VLAN
  réservées)
- IEEE 802.1p (préséance/priorité — le champ PCP du tag 802.1Q, historiquement

- IEEE 802.1ad (« QinQ » / Provider Bridging — double tag S-VLAN/C-VLAN,

## 0. Contexte et portée du document

Ce PRD documente **le format d'encapsulation 802.1Q lui-même** : le tag à 4
octets inséré entre l'adresse source Ethernet et l'EtherType/longueur d'une
trame (TPID 0x8100 + TCI = PCP 3 bits + DEI 1 bit + VID 12 bits), son
utilisation pour désigner le VLAN natif d'un trunk, et l'extension QinQ
(802.1ad, double tag S-VLAN/C-VLAN). Il **ne couvre pas** la sémantique de
segmentation elle-même (base de données VLAN, ports access/trunk, VLAN
réservées côté device) : ce périmètre relève de `docs/PRD-VLAN.md`, qui
**consomme** ce PRD comme fondation d'encodage. Il ne couvre pas non plus la
synchronisation de la base VLAN entre commutateurs (VTP) : voir
`docs/PRD-VTP.md`.

Cette analyse est issue d'une lecture complète de `src/network/core/types.ts`
(la fonction `ethernetFrameBytes()` et le type `EthernetFrame`),
`src/network/devices/Switch.ts` (le type `Dot1QTag`/`TaggedEthernetFrame`, la
pose/dépose du tag dans le pipeline de trame), `src/network/devices/Router.ts`
(l'encapsulation `dot1Q` sur sous-interface, pour le routage inter-VLAN
« router-on-a-stick »),
`src/network/devices/linux/network/tcpdump/CaptureFrame.ts` (sérialisation
bas niveau du TCI pour la capture), `src/network/devices/shells/HuaweiSwitchShell.ts`
(le mot-clé `qinq` accepté en CLI) — et du gap-analysis déjà versé dans
`GAP.md` §2 (commutation L2), qui documente une partie des mêmes constats sous
un angle switch plutôt qu'encodage.

### 0.1 Chaîne de dépendances entre PRDs

```
PRD-802.1Q.md (IEEE 802.1Q/802.1ad)            ◄── VOUS ÊTES ICI
   │  fondation d'encodage : format du tag, TPID/TCI, Native VLAN, QinQ
   │  aucune dépendance vers un autre PRD de ce dépôt
   │
   ▼  trame taguée transportée sur les trunks, VID porté par le tag
PRD-VLAN.md (segmentation L2 : base VLAN, access/trunk, PVST+, SVI)
   │  dépend de PRD-802.1Q.md pour l'encodage du VID sur le fil
   │  interagit avec le moteur STP existant (PVST+, déjà solide — GAP.md §2.1,
   │    non remis en cause par ce trio de PRD)
   │
   ▼  base VLAN locale à synchroniser entre commutateurs d'un même domaine
PRD-VTP.md (synchronisation de la base VLAN entre commutateurs Cisco)
      dépend de PRD-VLAN.md pour la base VLAN à synchroniser, et de
      PRD-802.1Q.md pour la condition d'émission (VTP ne circule que sur
      des ports trunk, donc taggés 802.1Q)
```

Ce PRD n'a **aucune dépendance entrante** : c'est la fondation d'encodage la
plus basse de ce trio. Contrairement à `PRD-QUIC.md`/`PRD-TLS.md`, il n'y a
pas de dépendance vers TLS ou QUIC — 802.1Q est une encapsulation de couche 2
qui transporte indifféremment n'importe quel EtherType supérieur (IPv4, IPv6,
ARP, et donc à terme des flux TLS/QUIC eux-mêmes, mais sans coupler leur
sémantique). Toute future implémentation de 802.1p (priorité) pourrait à
terme informer un mécanisme de QoS générique, mais aucun tel mécanisme
n'existe aujourd'hui dans ce dépôt — non traité ici.

Aucune ligne de code n'est écrite dans le cadre de ce document — il sert de
base à la planification et à la revue avant le premier commit TDD.

### 1.2 Ce qui est déjà réel et solide (à ne pas casser)

- **Le tag lui-même est structurellement correct** : `Dot1QTag { tpid: 0x8100,
  pcp, dei, vid }` couvre les 4 champs normatifs (TPID 16 bits, PCP 3 bits,
  DEI 1 bit, VID 12 bits) — pas une approximation.
- **Pose/dépose du tag au forwarding** : `Switch.forwardToPort()` retire ou
  ajoute le tag selon que le port de sortie soit natif du VLAN ou non — c'est
  le cœur du comportement d'un trunk 802.1Q réel (untagged sur le native
  VLAN, tagged partout ailleurs).
- **Encodage bas niveau fidèle pour la capture** : `CaptureFrame.ts` produit
  un TCI packé bit-à-bit conforme à la norme, testé par
  `src/__tests__/unit/network-v2/tcpdump-byte-slice-vlan-filters.test.ts`
  (117 lignes) — un `tcpdump -e`/Wireshark verrait un tag byte-exact.
- **Router-on-a-stick** : `Router.ts` pose/dépose le tag correctement sur les
  sous-interfaces (`encapsulation dot1Q <vlan> [native]`), y compris pour
  l'ARP gratuit émis via le port physique parent — voir `PRD-VLAN.md` §1.2
  pour le détail fonctionnel (ce PRD ne documente que l'encodage consommé).

## 2. Objectifs

### 2.1 Objectifs de ce PRD (remédiation proposée, non encore engagée)

Chaque fonctionnalité ci-dessous est livrée **complète** (pas une variante
restreinte prévue pour être étendue plus tard) et, dès lors qu'un équipement
réel des deux vendors couverts par ce simulateur (Cisco IOS et Huawei VRP)
la supporte, elle est implémentée **pour les deux**, avec la syntaxe et la
sémantique propres à chaque vendor plutôt qu'un comportement générique
copié-collé de l'un vers l'autre.

1. **Unifier le type de tag en un seul point de vérité.** Faire de
   `Dot1QTag`/`TaggedEthernetFrame` (aujourd'hui défini dans `Switch.ts`) un
   type partagé importé par `Router.ts` (et tout futur consommateur), en
   remplacement des deux casts structurels équivalents mais dupliqués. Purement
   additif/renommage — aucun changement de comportement observable, aucune
   suite de tests ne doit voir son résultat changer. Vendor-neutre par
   nature (le type est déjà partagé entre commutateurs et routeurs des deux
   marques).

2. **Modèle complet de confiance/classification/remarquage 802.1p (PCP) —
   Cisco et Huawei.** Il ne s'agit pas seulement de porter une valeur de CoS
   figée, mais du **modèle de frontière de confiance complet** qu'un vrai
   commutateur applique :
   - **Cisco IOS** : `mls qos trust cos` / `mls qos trust dscp` (frontière de
     confiance par port), `mls qos cos <n>` (CoS par défaut d'un port non
     fiable), `switchport priority extend {cos <n>|trust}` (comportement
     spécifique au port voice VLAN — un téléphone IP peut soit remarquer,
     soit faire confiance au CoS du PC en aval), remarquage à l'égress selon
     la frontière de confiance du port de sortie. `mls qos`/`switchport
     priority` sont déjà reconnus comme mots-clés décoratifs par le shell
     Cisco (`CiscoSwitchShell.ts:1752,2134-2135`) — cette phase leur donne un
     effet réel au lieu de rester des lignes de config inertes.
   - **Huawei VRP** : `qos trust dot1p` / `qos trust dscp` (frontière de
     confiance par interface), `port priority <n>` (priorité 802.1p par
     défaut d'un port non fiable), `trust upstream` (équivalent VRP de la
     confiance étendue pour un téléphone IP en aval). `trust`/`qos` sont déjà
     reconnus comme mots-clés décoratifs (`HuaweiSwitchShell.ts:1752`) — même
     traitement : leur donner un effet réel.
   - **`show`/`display`** : `show queuing interface`/équivalent Cisco et
     `display qos`/équivalent Huawei doivent refléter la config de confiance
     et la valeur de CoS/priorité par défaut réellement appliquée, pas un
     gabarit statique.
   - **Hors périmètre explicite, et non une réduction du périmètre 802.1p
     lui-même** : l'ordonnancement de files d'attente différencié par
     priorité (scheduling strict/WRR, policing, WRED) relève d'un sous-système
     QoS de bout en bout distinct de l'encapsulation 802.1Q — cette phase
     livre la classification/le marquage/le remarquage complets du champ
     PCP, pas un moteur de qualité de service applicative, qui nécessiterait
     son propre PRD dédié.

3. **QinQ complet (802.1ad) — Cisco et Huawei, y compris QinQ sélectif et
   tunneling de protocoles L2.** Portée complète, pas une simple pose/dépose
   de tag basique :
   - **QinQ de base (tunnel dot1q)** : sur un port dédié, empilement d'un tag
     S-VLAN (EtherType `0x88a8`) autour de n'importe quel trafic client déjà
     tagué ou non, désempilement symétrique en sortie du domaine fournisseur.
     Cisco : `switchport mode dot1q-tunnel` + `switchport access vlan
     <s-vlan>`. Huawei : `qinq enable` (déjà reconnu décorativement,
     `HuaweiSwitchShell.ts:938-947`) + `port default vlan <s-vlan>`.
   - **QinQ sélectif / VLAN mapping (traduction 1:1 ou agrégation N:1)** :
     plusieurs VLAN client mappés vers un ou plusieurs VLAN de service selon
     des règles explicites par VLAN d'entrée, plutôt qu'un simple
     encapsulage uniforme. Cisco : `switchport mode dot1q-tunnel` combiné à
     `switchport vlan mapping <cvlan> <svlan>`. Huawei : `port vlan-mapping`
     (déjà reconnu décorativement comme mot-clé générique,
     `HuaweiSwitchShell.ts:885-886`, avec le commentaire du code lui-même
     l'identifiant comme la commande de mapping/translation VLAN réelle) +
     `qinq vlan-translation`/`qinq stacking` selon le mode retenu en
     conception détaillée.
   - **Tunneling de protocoles L2 (« L2PT »)** à travers le domaine QinQ : les
     BPDU STP/PVST+, trames CDP et VTP d'un client ne doivent pas être
     traitées par les commutateurs du fournisseur mais tunnelées de bout en
     bout jusqu'à l'autre extrémité du domaine client. Cisco :
     `l2protocol-tunnel {cdp|stp|vtp|lldp}` sur le port dot1q-tunnel — une
     vraie fonctionnalité IOS complète, pas optionnelle si l'on veut un QinQ
     réellement utilisable en topologie multi-client. Huawei : mécanisme BPDU
     tunneling équivalent (VRP encapsule les BPDU client dans une MAC de
     destination propriétaire réservée sur les liens QinQ).
   - Cette fonctionnalité interagit directement avec le moteur PVST+ déjà
     existant (`docs/PRD-VLAN.md` §1.2) et avec VTP (`docs/PRD-VTP.md`) :
     tunneler leurs BPDU/trames sans les traiter localement est une exigence
     de correction, pas une amélioration facultative, dès qu'un port est en
     mode dot1q-tunnel/qinq.

4. **VLAN réservées et VID spéciaux — vendor-explicite.** `createVLAN`/
   validation de VID (côté `PRD-VLAN.md`, la définition normative de la plage
   réside ici) rejette VID 0 (sauf comme priority-tag pur) et VID 4095 pour
   **les deux vendors** (limite normative IEEE 802.1Q, universelle). En
   revanche, la réservation par défaut des VLAN **1002-1005** est une
   **convention Cisco IOS historique** (VLAN FDDI/Token Ring hérités) sans
   équivalent réel côté Huawei VRP — cette partie de la fonctionnalité est
   donc explicitement scopée **Cisco uniquement**, pas généralisée aux deux
   vendors par souci de parité artificielle.

5. **Détection native VLAN mismatch — Cisco uniquement, justifié par la
   réalité du terrain.** Une fois confirmé absent (item 6 du gap analysis),
   ajouter la détection complète : à la réception d'un CDP portant le native
   VLAN annoncé par le voisin (TLV natif CDP, à ajouter côté `CdpAgent` si
   absent — à vérifier explicitement lors de la conception détaillée),
   comparer au native VLAN local du port trunk et journaliser un événement
   `dot1q.native-vlan-mismatch` si différent, suivant le pattern
   `<Protocol>Engine` + `events.ts` du projet. **Ce n'est pas une
   fonctionnalité commune aux deux vendors** : le mécanisme réel s'appuie sur
   CDP, un protocole propriétaire Cisco (`docs/PRD-VTP.md` §0.1 rappelle que
   DTP/VTP sont dans la même situation) — Huawei n'a pas d'équivalent
   documenté de cette détection automatique en pratique, et ce PRD ne
   propose donc pas d'en inventer un artificiellement pour VRP.

### 2.2 Hors périmètre (explicitement exclu)

- 802.1ak (MVRP — enregistrement dynamique de VLAN par port, distinct de
  VTP) — non demandé, non traité.
- Tout mécanisme d'ordonnancement de files d'attente/policing/WRED fondé sur
  le PCP — un sous-système QoS de bout en bout distinct, qui mériterait son
  propre PRD s'il est un jour demandé ; ce PRD livre la classification/le
  marquage/le remarquage complets (item 2), pas la politique de traitement
  différencié du trafic en aval.

## 3. Plan de remédiation détaillé

### Phase 1 — Unification du type de tag (item 2.1.1)

- **Fichiers touchés** : `src/network/devices/Switch.ts` (export du type déjà
  existant, aucun changement de définition), `src/network/devices/Router.ts`
  (remplacement des deux casts structurels par un import direct de
  `TaggedEthernetFrame`/`Dot1QTag`).
- **Non-régression** : purement un changement de type statique ; `tsc
  --noEmit` doit rester à zéro erreur, aucune suite de tests ne doit changer
  de résultat (le format runtime de l'objet `{ tpid, pcp, dei, vid }` est
  strictement identique avant/après).
- **Tests** : réutiliser la suite existante `tcpdump-byte-slice-vlan-filters.test.ts`
  et les suites `cisco-router-interfaces.debug.test.ts`/
  `huawei-router-interfaces.debug.test.ts` comme régression de non-casse.

### Phase 2 — Modèle complet de confiance/marquage 802.1p (item 2.1.2)

Scindée en deux sous-phases vendor par vendor (chacune livrable et testable
indépendamment, mais toutes deux requises pour clore l'objectif) :

- **Phase 2a — Cisco** : `SwitchportConfig` (frontière de confiance par
  port : `trustMode: 'cos' | 'dscp' | 'untrusted'`, `defaultCos`), CLI
  `mls qos trust cos/dscp`, `mls qos cos <n>`, `switchport priority extend
  {cos <n>|trust}`, `Switch.addTag()` (lecture de la config au lieu du
  littéral `0`), `show queuing interface` (ou commande d'affichage
  équivalente déjà présente dans `CiscoSwitchShell.ts`) reflétant l'état réel.
- **Phase 2b — Huawei** : mêmes champs de configuration côté
  `SwitchportConfig` réutilisés (le modèle de confiance par port est
  vendor-neutre dans sa structure de données, seule la CLI diffère), CLI
  `qos trust dot1p/dscp`, `port priority <n>`, `trust upstream`, `display
  qos` reflétant l'état réel.
- **Fichiers touchés** : `Switch.ts`, `CiscoSwitchShell.ts`,
  `HuaweiSwitchShell.ts`.
- **Tests** : nouveau fichier `dot1p-priority.test.ts` couvrant les deux
  vendors — pose du bon PCP selon configuration sur chacun, valeur par
  défaut `0` inchangée si non configuré, round-trip via `tcpdump -e`

### Phase 3 — QinQ de base (item 2.1.3, premier volet)

### Phase 4 — QinQ sélectif / VLAN mapping (item 2.1.3, second volet)

### Phase 5 — Tunneling de protocoles L2 sur domaine QinQ (item 2.1.3, troisième volet)

- **Fichiers touchés** : point d'entrée de traitement STP/CDP/VTP dans

### Phase 6 — VLAN réservées / VID spéciaux (item 2.1.4)

  (`createVLAN`) et tout point d'entrée CLI qui accepte un VID littéral.
- **Tests** : cas limites VID 0 (priority-tag) et VID 4095 (rejeté) pour les
  deux vendors ; 1002-1005 réservées par défaut et libérables explicitement
  **Cisco uniquement** (Huawei ne réserve pas cette plage — vérifié
  explicitement dans le test pour éviter toute régression de parité
  artificielle).

### Phase 7 — Détection native VLAN mismatch (item 2.1.5, Cisco uniquement, conditionnelle)

- **Préalable obligatoire** : vérifier d'abord si CDP porte déjà un TLV
  native VLAN (lecture de `src/network/cdp/`) avant tout développement — si
  absent, cette phase inclut son ajout côté CDP.
- **Tests** : nouveau fichier `native-vlan-mismatch.test.ts` (Cisco
  uniquement — un test explicite confirmant l'absence volontaire
  d'équivalent Huawei complète la couverture).

## 4. Exigences de non-régression

Comme pour `PRD-TCP.md`/`PRD-QUIC.md` : toute correction doit rester
**additive et testée**. Le comportement observable des suites déjà vertes
touchant VLAN/trunk/tcpdump (`vlan-advanced.test.ts`,
`tcpdump-byte-slice-vlan-filters.test.ts`, les suites `debug/cisco-l2/*` et
`debug/huawei/huawei-vlan.debug.test.ts`) ne doit pas régresser. Les Phases
2, 3/4/5 et 6 se déclinent chacune en un volet Cisco et un volet Huawei :
un volet ne doit jamais être considéré "fait" tant que l'autre vendor
concerné n'a pas sa propre suite de tests verte — livrer uniquement le
volet Cisco d'une fonctionnalité commune aux deux vendors constitue une
livraison incomplète de la phase, pas un premier incrément acceptable.
La Phase 4 dépend de la Phase 3 (la table de traduction VLAN mapping est
consultée par le pipeline de pose de tag établi en Phase 3) ; la Phase 5
dépend de la Phase 3 (le tunneling L2PT ne s'applique qu'à des ports déjà en
mode QinQ) mais est indépendante de la Phase 4. Les Phases 6 et 7
n'attendent aucune des précédentes.

---

## 5. Risques

- **Risque principal** : la Phase 1 (unification de type) touche
  `Router.ts`, un fichier volumineux et central — un cast mal remplacé
  pourrait silencieusement changer le comportement de détection de trame
  taguée dans `handleFrame`/`sendFrame`. Mitigation : exécuter la régression
  complète des suites `router-*`/`inter-vlan-routing.test.ts` avant/après.
- **Risque lié au périmètre multi-vendor élargi** : le passage d'un
  périmètre « minimal » à un périmètre complet double, pour les Phases 2 à 4
  et 6, la charge de travail par rapport à une implémentation Cisco seule
  (conception + CLI + tests dédiés par vendor). Ce risque est assumé
  explicitement par ce PRD (c'est l'objet de la présente révision) — la
  mitigation est le découpage en sous-phases vendor-explicites (2a/2b) plutôt
  qu'une seule phase fourre-tout qui masquerait un volet non terminé.
- **Risque secondaire** : QinQ (Phases 3-5) introduit un second niveau
  d'encapsulation qui peut interagir de façon inattendue avec le calcul de
  taille de trame (`ethernetFrameBytes()`) utilisé ailleurs (MTU effective,
  fragmentation), et le tunneling L2PT (Phase 5) touche directement les
  points d'entrée des agents STP/CDP/VTP déjà existants et solides
  (`docs/PRD-VLAN.md` §1.2, `docs/PRD-VTP.md` §1.2) — toute régression sur
  le traitement normal (hors tunnel) de ces protocoles serait une casse
  majeure. Mitigation : le chemin de traitement normal (port non-tunnel)
  reste physiquement le même code, seul un nouveau branchement conditionnel
  au mode tunnel est ajouté ; régression complète des suites STP/CDP/VTP
  existantes exigée avant tout commit de la Phase 5.
