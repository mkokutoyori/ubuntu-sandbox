# PRD — Encapsulation IEEE 802.1Q (trames taguées, VLAN tag, QinQ)

**Version** : 1.0
**Date** : 2026-07-07
**Projet** : Ubuntu Sandbox — simulateur réseau navigateur
**Auteur** : Claude (agent), à la demande de l'utilisateur
**Références normatives** :
- IEEE 802.1Q-2018 (VLAN tagging — format du tag, TPID/TCI, Native VLAN, VLAN
  réservées)
- IEEE 802.1p (préséance/priorité — le champ PCP du tag 802.1Q, historiquement
  une norme séparée fusionnée dans 802.1Q depuis 2005)
- IEEE 802.1ad (« QinQ » / Provider Bridging — double tag S-VLAN/C-VLAN,
  EtherType 0x88a8)
- RFC 9110/TLS/QUIC — **sans dépendance directe** (802.1Q est une
  encapsulation de couche 2, en dessous de la commutation par étiquette et de
  IPv4/IPv6 ; ce document ne redéfinit aucun protocole de couche 3+, cf. §0.1)

---

## 0. Contexte et portée du document

Ce PRD documente **le format d'encapsulation 802.1Q lui-même** : le tag à 4
octets inséré entre l'adresse source Ethernet et l'EtherType/longueur d'une
trame (TPID 0x8100 + TCI = PCP 3 bits + DEI 1 bit + VID 12 bits), son
utilisation pour désigner le VLAN natif d'un trunk, et l'extension QinQ
(802.1ad, double tag S-VLAN/C-VLAN). Il **ne couvre pas** la sémantique de
segmentation elle-même (base de données VLAN, ports access/trunk, VLAN
réservées côté device) : ce périmètre relève de `docs/PRD-VLAN.md`, qui
**consomme** ce PRD comme fondation d'encodage. Il ne couvre pas non plus la
synchronisation de la base VLAN entre commutateurs (VTP) : voir
`docs/PRD-VTP.md`.

Cette analyse est issue d'une lecture complète de `src/network/core/types.ts`
(la fonction `ethernetFrameBytes()` et le type `EthernetFrame`),
`src/network/devices/Switch.ts` (le type `Dot1QTag`/`TaggedEthernetFrame`, la
pose/dépose du tag dans le pipeline de trame), `src/network/devices/Router.ts`
(l'encapsulation `dot1Q` sur sous-interface, pour le routage inter-VLAN
« router-on-a-stick »),
`src/network/devices/linux/network/tcpdump/CaptureFrame.ts` (sérialisation
bas niveau du TCI pour la capture), `src/network/devices/shells/HuaweiSwitchShell.ts`
(le mot-clé `qinq` accepté en CLI) — et du gap-analysis déjà versé dans
`GAP.md` §2 (commutation L2), qui documente une partie des mêmes constats sous
un angle switch plutôt qu'encodage.

### 0.1 Chaîne de dépendances entre PRDs

```
PRD-802.1Q.md (IEEE 802.1Q/802.1ad)            ◄── VOUS ÊTES ICI
   │  fondation d'encodage : format du tag, TPID/TCI, Native VLAN, QinQ
   │  aucune dépendance vers un autre PRD de ce dépôt
   │
   ▼  trame taguée transportée sur les trunks, VID porté par le tag
PRD-VLAN.md (segmentation L2 : base VLAN, access/trunk, PVST+, SVI)
   │  dépend de PRD-802.1Q.md pour l'encodage du VID sur le fil
   │  interagit avec le moteur STP existant (PVST+, déjà solide — GAP.md §2.1,
   │    non remis en cause par ce trio de PRD)
   │
   ▼  base VLAN locale à synchroniser entre commutateurs d'un même domaine
PRD-VTP.md (synchronisation de la base VLAN entre commutateurs Cisco)
      dépend de PRD-VLAN.md pour la base VLAN à synchroniser, et de
      PRD-802.1Q.md pour la condition d'émission (VTP ne circule que sur
      des ports trunk, donc taggés 802.1Q)
```

Ce PRD n'a **aucune dépendance entrante** : c'est la fondation d'encodage la
plus basse de ce trio. Contrairement à `PRD-QUIC.md`/`PRD-TLS.md`, il n'y a
pas de dépendance vers TLS ou QUIC — 802.1Q est une encapsulation de couche 2
qui transporte indifféremment n'importe quel EtherType supérieur (IPv4, IPv6,
ARP, et donc à terme des flux TLS/QUIC eux-mêmes, mais sans coupler leur
sémantique). Toute future implémentation de 802.1p (priorité) pourrait à
terme informer un mécanisme de QoS générique, mais aucun tel mécanisme
n'existe aujourd'hui dans ce dépôt — non traité ici.

Aucune ligne de code n'est écrite dans le cadre de ce document — il sert de
base à la planification et à la revue avant le premier commit TDD.

## 1. Analyse de l'existant

### 1.1 Inventaire

| `src/network/devices/Router.ts` | Ré-implémente le même cast structurel `{ dot1q?: ... }` (l. 590, 1017) plutôt que d'importer `TaggedEthernetFrame` — deuxième source de vérité pour le même concept |
| `src/network/devices/linux/network/tcpdump/CaptureFrame.ts` | Seul point du code qui sérialise réellement le TCI 16 bits conforme à la norme (`(pcp&7)<<13 | (dei&1)<<12 | (vid&0xfff)`, précédé du TPID 2 octets) — l. 222-238 |
| `src/network/devices/shells/HuaweiSwitchShell.ts` | Mot-clé CLI `qinq` reconnu sur une interface (l. 938-947) et **stocké tel quel** pour réaffichage dans `display this` — aucune sémantique de second tag derrière |

### 1.2 Ce qui est déjà réel et solide (à ne pas casser)

- **Le tag lui-même est structurellement correct** : `Dot1QTag { tpid: 0x8100,
  pcp, dei, vid }` couvre les 4 champs normatifs (TPID 16 bits, PCP 3 bits,
  DEI 1 bit, VID 12 bits) — pas une approximation.
- **Pose/dépose du tag au forwarding** : `Switch.forwardToPort()` retire ou
  ajoute le tag selon que le port de sortie soit natif du VLAN ou non — c'est
  le cœur du comportement d'un trunk 802.1Q réel (untagged sur le native
  VLAN, tagged partout ailleurs).
- **Encodage bas niveau fidèle pour la capture** : `CaptureFrame.ts` produit
  un TCI packé bit-à-bit conforme à la norme, testé par
  `src/__tests__/unit/network-v2/tcpdump-byte-slice-vlan-filters.test.ts`
  (117 lignes) — un `tcpdump -e`/Wireshark verrait un tag byte-exact.
- **Router-on-a-stick** : `Router.ts` pose/dépose le tag correctement sur les
  sous-interfaces (`encapsulation dot1Q <vlan> [native]`), y compris pour
  l'ARP gratuit émis via le port physique parent — voir `PRD-VLAN.md` §1.2
  pour le détail fonctionnel (ce PRD ne documente que l'encodage consommé).

## 2. Objectifs

### 2.1 Objectifs de ce PRD (remédiation proposée, non encore engagée)

1. **Unifier le type de tag en un seul point de vérité.** Faire de
   `Dot1QTag`/`TaggedEthernetFrame` (aujourd'hui défini dans `Switch.ts`) un
   type partagé importé par `Router.ts` (et tout futur consommateur), en
   remplacement des deux casts structurels équivalents mais dupliqués. Purement
   additif/renommage — aucun changement de comportement observable, aucune
   suite de tests ne doit voir son résultat changer.
2. **Priorité 802.1p réelle (PCP).** Ajouter une configuration de CoS de
   confiance/remarquage minimale par port (`mls qos trust cos` / valeur de
   CoS par défaut assignée à un port non fiable, dans l'esprit de ce qui
   existe déjà pour d'autres notions de configuration par port dans
   `SwitchportConfig`), et faire porter cette valeur dans `pcp` à la pose du
   tag au lieu de `0` figé. Champ additif : les topologies existantes qui ne
   configurent rien continuent de voir `pcp: 0`, comportement inchangé.
3. **QinQ minimal (802.1ad).** Sur un port explicitement configuré `qinq
   enable` (déjà accepté en CLI Huawei, actuellement décoratif), pousser un
   second tag S-VLAN (EtherType `0x88a8`) autour du tag C-VLAN existant à
   l'entrée du réseau fournisseur, et le retirer symétriquement en sortie.
   Portée volontairement minimale : un seul niveau d'empilement
   supplémentaire, pas de négociation dynamique, pas de translation de VLAN
   (« VLAN mapping »/1:1 ou N:1) — juste l'encapsulation/désencapsulation de
   base.
4. **VLAN réservées et VID spéciaux.** `createVLAN`/validation de VID (côté
   `PRD-VLAN.md`, mais la définition normative de la plage réside ici)
   rejette VID 0 (sauf comme priority-tag pur) et VID 4095 ; documente
   1002-1005 comme réservées par défaut avec possibilité de les libérer via
   une commande explicite (parité avec le comportement réel où ces VLAN
   existent par défaut mais restent en général non affectées).
5. **Détection native VLAN mismatch (conditionnelle).** Une fois confirmé
   absent (item 6 du gap analysis), ajouter la détection : à la réception
   d'un CDP portant le native VLAN annoncé par le voisin (si ce TLV existe
   déjà côté CDP — à vérifier également), comparer au native VLAN local du
   port trunk et journaliser un événement de type `dot1q.native-vlan-mismatch`
   si différent, suivant le pattern `<Protocol>Engine` + `events.ts` du projet.

### 2.2 Hors périmètre (explicitement exclu)

- Toute négociation dynamique de QinQ (« Selective QinQ », VLAN mapping,
  translation N:1) — uniquement l'empilement/désempilement statique de base.
- 802.1ak (MVRP — enregistrement dynamique de VLAN par port, distinct de
  VTP) — non demandé, non traité.
- Tout lien avec un mécanisme de QoS de bout en bout (files d'attente par
  CoS, policing) — le PCP est porté et sérialisé fidèlement, mais aucune
  politique de traitement différencié du trafic par priorité n'est dans le
  périmètre de ce PRD.

## 3. Plan de remédiation détaillé

### Phase 1 — Unification du type de tag (item 2.1.1)

- **Fichiers touchés** : `src/network/devices/Switch.ts` (export du type déjà
  existant, aucun changement de définition), `src/network/devices/Router.ts`
  (remplacement des deux casts structurels par un import direct de
  `TaggedEthernetFrame`/`Dot1QTag`).
- **Non-régression** : purement un changement de type statique ; `tsc
  --noEmit` doit rester à zéro erreur, aucune suite de tests ne doit changer
  de résultat (le format runtime de l'objet `{ tpid, pcp, dei, vid }` est
  strictement identique avant/après).
- **Tests** : réutiliser la suite existante `tcpdump-byte-slice-vlan-filters.test.ts`
  et les suites `cisco-router-interfaces.debug.test.ts`/
  `huawei-router-interfaces.debug.test.ts` comme régression de non-casse.

### Phase 2 — Priorité 802.1p (PCP réel) (item 2.1.2)

- **Fichiers touchés** : `SwitchportConfig` (ajout d'un champ optionnel de CoS
  par défaut/confiance), `Switch.addTag()` (lecture de la config au lieu du
  littéral `0`), CLI Cisco/Huawei correspondante.
- **Tests** : nouveau fichier `dot1p-priority.test.ts` (pose du bon PCP selon
  configuration, valeur par défaut `0` inchangée si non configuré,
  round-trip via `tcpdump -e` affichant le bon PCP dans le TCI décodé).

### Phase 3 — QinQ minimal (item 2.1.3)

- **Fichiers touchés** : `Switch.ts` (structure `Dot1QTag` réutilisée pour un
  second niveau, ou nouveau type `QinQTag { outer: Dot1QTag, inner: Dot1QTag
  }` — à trancher en conception détaillée), pipeline de pose/dépose sur les
  ports marqués `qinq enable`.
- **Tests** : nouveau fichier `qinq-double-tag.test.ts` couvrant pose du tag
  S-VLAN à l'entrée, préservation du tag C-VLAN client intact à l'intérieur,
  dépose symétrique en sortie, et vérification EtherType `0x88a8` visible en
  capture.

### Phase 4 — VLAN réservées / VID spéciaux (item 2.1.4)

- **Fichiers touchés** : validation de VID partagée entre `Switch.ts`
  (`createVLAN`) et tout point d'entrée CLI qui accepte un VID littéral.
- **Tests** : cas limites VID 0 (priority-tag), VID 4095 (rejeté), 1002-1005
  (réservées par défaut, libérables explicitement).

### Phase 5 — Détection native VLAN mismatch (item 2.1.5, conditionnelle)

- **Préalable obligatoire** : vérifier d'abord si CDP porte déjà un TLV
  native VLAN (lecture de `src/network/cdp/`) avant tout développement — si
  absent, cette phase inclut son ajout minimal côté CDP.
- **Tests** : nouveau fichier `native-vlan-mismatch.test.ts`.

## 4. Exigences de non-régression

Comme pour `PRD-TCP.md`/`PRD-QUIC.md` : toute correction doit rester
**additive et testée**. Le comportement observable des suites déjà vertes
touchant VLAN/trunk/tcpdump (`vlan-advanced.test.ts`,
`tcpdump-byte-slice-vlan-filters.test.ts`, les suites `debug/cisco-l2/*` et
`debug/huawei/huawei-vlan.debug.test.ts`) ne doit pas régresser. Chaque phase
est livrable et testable indépendamment des autres (aucune phase ne bloque
les suivantes, contrairement à la dépendance TLS→QUIC d'autres PRDs de ce
dépôt).

## 5. Risques

- **Risque principal** : la Phase 1 (unification de type) touche
  `Router.ts`, un fichier volumineux et central — un cast mal remplacé
  pourrait silencieusement changer le comportement de détection de trame
  taguée dans `handleFrame`/`sendFrame`. Mitigation : exécuter la régression
  complète des suites `router-*`/`inter-vlan-routing.test.ts` avant/après.
- **Risque secondaire** : QinQ (Phase 3) introduit un second niveau
  d'encapsulation qui peut interagir de façon inattendue avec le calcul de
  taille de trame (`ethernetFrameBytes()`) utilisé ailleurs (MTU effective,
  fragmentation) — à vérifier explicitement dans les tests de cette phase.
